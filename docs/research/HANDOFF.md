## 1. Owner's constraints and decisions (stated 2026-09-28)

1. The product stays a web app (installable PWA). No native app for now: the owner wants ease of updating, testing and distribution among a small group of friends. Do not propose native or App Store paths.
2. Users are primarily on phones (iPhone and Android). Desktop is secondary. Anything that only works with a mouse, a bookmarks bar or select-all-copy on a desktop browser is a convenience, not a path the design may depend on.
3. The widest and least technical audience is the target. Pasting a URL into "Add from URL" must remain the primary import path and must work with no install, no setup, no token and no explanation.
4. The iOS Shortcut and a bookmarklet are welcome as optional accelerators (the owner would use one himself) but are never required and are not the fix for the 429 problem. They move to the last phase.
5. The paste-text import stays as it is. Reading the `text/html` clipboard flavour to enrich pasted content is low value on phones (select-all is fiddly, and whether iOS includes absolute image URLs in the HTML flavour was not verified), so implement it only if it is a trivial, feature-detected addition; do not plan around it.
6. No billing, as `CLAUDE.md` already says: Firestore on Spark, Workers Free, Gemini free tier. A third-party fetch service is acceptable only on a free tier that needs no card; if signing up requires a card, drop that item and say so.
7. Existing `CLAUDE.md` rules apply unchanged: design for the friends, never silently hand them a lower-quality result, call out manual steps with exact clicks, explain the why in one line, and never auto-provision KV (create a namespace explicitly and commit its id).
8. The usability goal is to eliminate the disruptions, delays and unpredictability that 429s currently cause. Predictability (bounded time, honest outcome) matters more than raw success rate.

## 2. Diagnosis in two paragraphs

Every outbound `fetch()` from a Worker leaves through a small pool of Cloudflare egress addresses shared by every Workers tenant, with a TLS/HTTP-2 fingerprint the runtime generates identically for everyone and, unless code sets one, no `User-Agent`. archive.org meters and firewall-blocks by source IP (IA staff: about 60 CDX requests per minute per IP, then a one-hour block that doubles each time 429s are ignored for more than a minute), so other tenants spend the address's budget before our first request lands, and nothing sent in the request (honest UA, Archive login cookies, patience) changes which counter it hits; only Save Page Now 2 is metered per account. The same shared address and fingerprint are why recipe sites behind Bot Fight Mode or DataDome refuse the direct fetch, and why the Chrome-125 `BROWSER_HEADERS` make it worse (a browser UA contradicting a non-browser fingerprint scores as spoofing). Since 15 September 2026 Cloudflare's defaults also block unverified "Agent" fetchers on ad-monetised pages, which is what a user-triggered importer is. Report sections 1–2 give the evidence; addendum F1 and F2 show how the code amplifies it.

The amplification is the part the code controls. The Worker never classifies a 429 (no `memento-datetime` check to distinguish a replayed site 429 from IA's throttle), logs `Retry-After` but cannot act on it (the acting branch is unreachable because no caller passes retries), keeps no breaker state, and on a refused availability lookup still fires the `now` replay and the CDX query, so one throttled attempt costs three rationed requests. The client then waits 40, 50 and 60 seconds and re-runs the entire Worker ladder each time, so a blocked site costs roughly a dozen archive.org requests, eight Jina requests and four Gemini URL-context calls in three minutes from an address that is already blocked, and each try spends 60–90 seconds of its own before the countdown even starts. The ladder is also "JSON-LD or bust": a perfectly usable 200 page without structured data still triggers Jina and the archive before being used, and a first-come `fallback` lets a soft-block page outrank a real one. The result is exactly the unpredictability the owner wants gone: the same link can take 4 seconds or 8 minutes depending on what strangers did to a shared IP in the previous hour.

## 3. Design principles for the rework

The import gets a fixed contract. Every rung has a hard time budget, the whole ladder is capped at about 30 seconds, and the outcome is always one of three: full recipe with photos; recipe text with a visible note that photos could not be fetched (with the add-your-own-photo control right there); or "this site won't let us read it" with the paste path shown immediately. No countdowns, ever.

Per-IP-throttled services never sit on the critical path uncoordinated. archive.org runs behind a breaker, sequentially, at most two requests per import, and is skipped in zero time while the breaker is open. Jina, once keyed, is metered per key rather than per shared IP and can be used freely.

Cheap rungs are hedged, the expensive ones are gated. The direct fetch and Jina run concurrently (a delayed hedge: start Jina if the direct fetch has not returned within about three seconds), and the first response with recipe signals wins and cancels the other. A rung whose address and fingerprint differ from the Worker's (Jina, an unlocker) comes before the archive, because it changes the variable the blocks key on; the archive comes last among automated rungs because it changes nothing about that variable and is the least predictable.

Photos never block the recipe. The editor opens on text; photos attach afterwards under a deadline; a friend can always add their own.

Transient failures become delayed successes. A 429 or 503 on every rung produces a placeholder recipe that fills itself in later, not an error.

The system learns per host. A short static denylist gives instant, specific messages for sites known to refuse everything (NYT Cooking); a host-health record skips the slow rungs for a day after repeated hard failures; per-host outcomes are logged so the owner can see which five sites the friends actually use.

## 4. Work plan

Each item names what to change, why (the mechanism), where (from the addendum), and how to know it is done. Phases are ordered by impact on a friend importing a recipe on a phone; within a phase the order is a suggestion.

### Phase 1 — Stop the bleeding (Worker and client; no new accounts, no manual setup beyond `wrangler deploy`)

**1.1 Classify archive 429s and add a breaker (F1, F15).** In `fetchText`/`fetchRecipePage`: a 429 carrying `memento-datetime` is a replayed capture of the site's own 429 and must not count; honour `Retry-After` when present but never depend on it; otherwise open a module-level breaker with the schedule the report documents (first strike 60 s, then 1 h, doubling, capped at 4 h, with jitter) and skip every archive rung while it is open, returning `archive_busy` immediately with a `retryAfterMs` field derived from the breaker. Treat a timeout on a replay as a refusal, not `'missing'`, so a struggling archive does not proceed to CDX and two more replays. Reset strikes on any 200. The sketch in addendum item 1 is a starting point. Module memory is per isolate, so two Worker copies can hold different breaker states; that is acceptable for Phase 1 (each copy learns within one refused request), and if shared state is wanted later, a SQLite-backed Durable Object is available on the Free plan (100,000 requests per day) and its alarm can flip the breaker to half-open. Done when: with the breaker open, a link import makes zero archive.org requests and logs why; a single throttled attempt makes at most one archive request; a synthetic 429 with `memento-datetime` leaves the breaker closed; a 20 s abort on a replay ends the archive rung.

**1.2 Confine and bound the client retry (F2).** Remove the 40/50/60 s loop in `readLink` and `archiveBusy.ts`. Allow at most one retry, only of the archive rung (a request parameter that skips direct and Jina), only after the Worker-supplied `retryAfterMs`, and never when that exceeds about 90 s. Stop the `/url` fallback from re-running the ladder after a Worker call that already fetched the page: have `handleLink` include the extracted JSON-LD blocks in its error body so the client converts locally with `recipeFromJsonLd` and shows the degraded result with its label (see 1.6). Done when: the worst-case wall time for a fully blocked site is under 40 s and ends in the paste message; a Gemini 502 no longer causes a second fetch of the page.

**1.3 Per-rung budgets and a delayed hedge (F2).** Direct fetch about 8 s, Jina about 10 s, archive about 5 s and two requests, URL context about 10 s; total about 30 s. Start Jina if the direct fetch has not returned within about 3 s and cancel the loser with `AbortController`. Until 2.1 lands, keep the hedge delayed (not simultaneous) so the keyless 20 RPM per-IP Jina budget is not spent on pages the direct fetch would have got. Done when: a WPRM blog imports in the direct fetch's time; a site that blocks the Worker but not Jina imports in about Jina's time rather than direct-timeout plus Jina.

**1.4 Accept signal-bearing pages; score the fallback; widen challenge detection (F3, F5).** In `consider`, treat a 2xx body as final when it has any recipe signal (schema.org Recipe microdata, `wprm-recipe`, `tasty-recipes`, an Ingredients heading, `recipeIngredient`), not only a JSON-LD Recipe node; escalate only on non-2xx, a challenge, or a tiny body. Replace first-come `fallback` with a signal-strength score so a signal-bearing Jina page replaces a signal-free direct page. Extend the challenge regex beyond five phrases (HUMAN/PerimeterX "Press & Hold", Kasada, Imperva, cookie-consent walls) and make a 200 challenge escalate rather than win. In the deterministic pass (Worker `findRecipe` and client `findRecipeNode`), descend into `WebPage.mainEntity`, compare `@type` case-insensitively, decode HTML entities in ingredient and instruction strings, and add `__NEXT_DATA__` recipe-object search and microdata as last deterministic resorts. Report section 4 lists every polymorphic shape observed in 48 real pages; they are the test cases. Done when: a microdata-only page and a structured-data-free blog both import without an archive request; the fixtures in 6 below pass.

**1.5 Identify honestly (F4).** Replace `BROWSER_HEADERS` with a product User-Agent carrying a contact URL (the `ALLOWED_ORIGIN` site), browser-typical `Accept` and `Accept-Language`, and use it on the direct fetch, the `/img` site route and the Jina calls (which currently send no UA at all). Say so in the commit: this will not get past Bot Fight Mode (nothing from a Worker does), but it removes the spoofing signal, avoids the intra-layer contradiction (a Chrome UA without Chrome's client hints), and is the precondition for any future verified-bot or signed-agent path. Done when: no request from the Worker claims to be Chrome.

**1.6 Carry `via` and label every downgrade (F12).** Add `via` (`direct | reader | unlocker | archive | google | jsonld-fallback`) to the link route's response and the `/url` path. In the editor, show one line for a text-only import ("read as text; the site wouldn't let us fetch its photos") and for the JSON-LD fallback, with the add-photo control adjacent. Make the terminal failure message name the paste path (and, after Phase 4, the Shortcut). Done when: no import opens the editor without photos silently.

**1.7 Photos never block (F9).** Open the editor as soon as the recipe text is validated; attach photos afterwards with a per-photo deadline (about 20 s) and an overall cap (about 45 s), showing placeholders that fill in. In `handleImageProxy`, sniff magic bytes in addition to the `Content-Type` prefix, and handle a missing `Content-Length` explicitly instead of letting `size` be 0. Done when: a recipe whose photos all fail still opens within the ladder's budget and shows the note from 1.6.

**1.8 Denylist and host health (F10).** A static denylist (start with `cooking.nytimes.com`) returns an instant, site-specific message with the paste path. A host-health map (module memory now; KV in 2.5) records consecutive hard failures per host and skips the slow rungs for 24 h after a threshold. Log a one-line outcome per import (`host, via, ms, photos`) so the owner can see which sites friends use. Done when: an NYT link fails in under a second with the right message.

**1.9 Housekeeping (F11, F13, F14).** Cache the JWKS in module memory keyed by `kid`, wrap the fetch in `try/catch` with a timeout so a hiccup returns a CORS-bearing 503 instead of an uncaught 500. Add `[observability] enabled = true` to `wrangler.toml` (Workers Logs on the Free plan: 3-day retention, 200,000 events per day, as of the notes' Sept 2026 read; log one structured object per import so `host`, `via`, `status` and `elapsedMs` are filterable fields) and bump `compatibility_date`. Fix `worker/README.md` (the placeholder line it references no longer exists; it still says the Worker "waits out" 429s). Delete `.github/workflows/import-recipe.yml` and `scripts/import-url.ts`, or keep them explicitly as owner-only tooling with the `${{ inputs.url }}` expression injection fixed; they are not a viable route (datacenter IP, same UA contradiction, output nothing consumes).

### Phase 2 — Reach (free accounts; one-time owner setup)

**2.1 Jina API key.** Store `JINA_API_KEY` as a Worker secret and send `Authorization: Bearer …` plus `X-Timeout` on both Jina calls. The keyless limit is 20 requests per minute per IP, shared with every Workers tenant; a free key gives 500 per minute per key and 10M free tokens (report, ladder table). Manual step for the owner: create the key at jina.ai, then `cd worker && npx wrangler secret put JINA_API_KEY`. Once keyed, the hedge in 1.3 can start simultaneously rather than delayed.

**2.2 An unlocker rung between Jina and the archive.** The one server-side channel whose IP and fingerprint are not the Worker's. Candidates from the notes (Sept 2026 prices): Firecrawl (`/scrape` with `proxy: auto`; Free plan 1,000 credits per month, 10 requests per minute, 2 concurrent browsers, 1 credit per page); Scrapfly (`asp=true` with the residential pool; 1,000 free credits with no card per its own docs, but a protected page costs about 25–30 credits, so roughly 30–40 protected pages per month); Bright Data Web Unlocker (5,000 requests per month free, then $1.50 per 1,000, pay-only-for-success; whether a card is required was not verified). Check each pricing page and whether a card is required before building on it; if every option needs a card, skip this item and note it. Prefer whichever is card-free with the largest allowance; at a friend group's volume any of them covers the protected-site imports. One call per import, only after direct and Jina fail, never for denylisted hosts, with its own 15 s budget. Sketch in addendum item 8. Manual step: account creation and a secret.

**2.3 One streaming pass with `HTMLRewriter` (F6, F7).** Replace `res.text()` plus the five or six regex passes with a single collector (JSON-LD blocks, `og:*`, canonical, `img`/`source` attributes including lazy-load variants, visible text) fed from the response stream, then reuse its output in `pageForAi` and `findLinkPhotos` instead of re-deriving. This is where the Free plan's 10 ms CPU goes on ad-heavy pages. Before stringifying the Recipe node for Gemini, drop `review`, `comment`, `aggregateRating`, `video`, `publisher`, `isPartOf`, `mainEntityOfPage`. When there is no JSON-LD and text is the only input, truncate from the head only after locating the recipe region (Ingredients heading) so the card at the bottom of a long blog is not what gets cut. Sketch in addendum item 5; note its caveat about nested `li > p` double-collection.

**2.4 Gemini hardening (F8).** Let a 429 on one model fall through to the next (quotas are per model). Give the schema-less retry a chance by appending a compact key skeleton to the prompt when the schema is dropped; today the key names live only in the schema, so that retry cannot produce output `sanitizeAiRecipe` accepts. Flatten the response schema to depth three (`alt` and `temperature` as scalar fields, optional numbers as `["number","null"]`), keep the tag enum, mark only title, ingredients and steps required. Remove the "by calling the save_recipe tool" sentence from `SYSTEM` for the Gemini path. Keep `parseRecipe` and `sanitizeAiRecipe` as the real validators; the report's finding is that only syntactic validity is guaranteed.

**2.5 Cache by canonical URL.** Create a KV namespace explicitly, commit its id, and use `archiveKey`-style normalisation as the key: fetched page bundles (TTL about 7 days), Availability/CDX answers and snapshot bodies (immutable, long TTL), Gemini results keyed by a hash of the input, and the host-health map from 1.8. Mind the Free-plan KV limits from the notes (100,000 reads and 1,000 writes per day, one write per second per key): write one bundle per import rather than one entry per rung, and never write on a cache hit. Add a client-side "already in your kitchen" check before importing (query recipes by normalised `source.url`) that offers to open or copy instead. Done when: a second import of the same URL by anyone in the household completes without a network fetch.

### Phase 3 — Background completion

**3.1 Pending imports.** When every rung fails transiently (429/503/timeouts, not a challenge or 403), return `{ pending: true, id }`; the app saves a placeholder recipe ("We'll keep trying and fill this in") and the Worker stores `{ uid, householdId, url, attempts, nextAt }` in KV. Two ways to run the retries, both on the Free plan: a Cron Trigger (minute granularity, 15-minute CPU ceiling per run) that sweeps pending entries in KV while the relevant breaker is closed, with the same budgets; or Cloudflare Workflows, which the research notes recommend as the better fit for a per-import pipeline because each `step.do()` is checkpointed with configurable retries, `step.sleep()` implements a `Retry-After` wait of any length without burning CPU, and it is free on Workers Free (1,024 steps per instance, 3,000 steps per day, a 1 MiB cap per step result, so keep fetched HTML in KV and return the key). Cron plus KV is simpler and enough for a friend group; choose Workflows if durable per-step retries are wanted. To complete the save without a service account, have the Worker store the finished recipe bundle in KV and let the app collect it: the Add screen and app launch call `GET /pending`, and the client performs the Firestore write under the existing rules, then deletes the stash. The placeholder shows "still trying" or "ready to review". Done when: a transient failure produces a placeholder that becomes a real recipe on a later app open, and a permanent failure (denylist, challenge) never produces a placeholder.

**3.2 Optional: Save Page Now 2 as a background source.** SPN2 is the only archive surface metered per account (authenticated: 7 captures per minute, 30,000 per day) and IA's own crawler does the fetch, so it can capture pages the Worker cannot read; captures take seconds to minutes, per-IP error codes still exist (`error:blocked-client-ip`), and reading the capture is still a per-IP replay (route it through Jina as the code already does for archive URLs). Only worth adding if 3.1's logs show the archive actually yields recipes; the report explains why coverage of recipe sites is opportunistic and shrinking.

### Phase 4 — Optional accelerators (after the primary path is predictable)

**4.1 A `/capture` route.** Accepts `{ token, url, jsonld, og, images, text }`, verifies an HMAC capture token minted per member (sketch in addendum item 10), stashes the capture in KV for an hour, and the Add screen collects it ("1 page waiting") into the normal parse, Gemini and `/img` path. Settings shows the member's token embedded in an install link. Because the PWA cannot receive a share on iOS (`CLAUDE.md` share-target note), the stash-and-collect shape is required rather than a direct hand-off.

**4.2 The iOS Shortcut** ("Run JavaScript on Web Page" from Safari's share sheet) posting the page's JSON-LD, `og:image`, canonical URL and deduplicated image URLs. It fetches from the user's residential IP with real Safari, which defeats every signal in report section 1 at once; it is the web-app equivalent of the native-app advantage the owner mentioned. Photos still flow through `/img`.

**4.3 A bookmarklet** as a second thin client of `/capture` for desktop and Android Chrome. Same payload, same route.

**4.4 Only if trivial:** read the `text/html` clipboard flavour in the paste importer behind a feature check, and verify on iOS Safari whether image URLs arrive absolute before showing any photo affordance from it.

## 5. Anti-patterns (do not reintroduce)

Countdown retries against archive.org from the Worker's address, in any form; the report documents that ignoring 429s for more than a minute is what opens and doubles the block. Concurrent archive requests. Any retry that re-runs the whole ladder. Browser impersonation in any header. Treating a 200 with a challenge or consent body as success. Opening the editor with a silent downgrade. Reviving the GitHub Actions import path as a route. Auto-provisioned KV. Sending a member's authenticated cookies to a paywalled site. Any rung without a time budget.
