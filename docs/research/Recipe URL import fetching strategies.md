# Move recipe fetching off Cloudflare's shared IPs

The archive.org 429s are not a Worker bug and cannot be fixed in Worker code: every outbound `fetch()` from Workers leaves through a small pool of Cloudflare-owned egress addresses shared by every Workers tenant, archive.org meters and firewall-blocks by source IP (IA staff: about **60 CDX requests/min per IP, then a 1-hour block that doubles on repeat**), and nothing the Worker can send — an honest User-Agent, Archive login cookies, patient backoff — changes which counter its request lands in. The same shared address, plus a TLS/HTTP-2 fingerprint the runtime generates identically for every tenant and a header set with no default User-Agent (the app's browser-imitating `BROWSER_HEADERS` fill that gap only to contradict the fingerprint), is why recipe sites behind Cloudflare Bot Fight Mode or DataDome refuse the Worker; since **15 September 2026** Cloudflare's own defaults also block unverified "Agent" fetchers on ad-monetised pages, which is exactly what a user-triggered importer is. The reliable design therefore moves the hard fetches to origins that own their IP budget — the user's phone (an iOS Shortcut run from Safari's share sheet that posts the page's JSON-LD and image URLs to the Worker), a third-party fetcher with residential addresses (Bright Data's unlocker gives **5,000 requests/month free**), or a relay with its own IP for archive.org calls — and keeps the Worker for what it does well: a streaming JSON-LD/microdata parse (**47 of 48** real recipe pages in the recipe-scrapers corpus carry a schema.org Recipe), Gemini as a *normaliser* over that structured data rather than as the fetcher, and photo re-hosting. archive.org should drop to a late, circuit-broken rung: its coverage of recipe pages is opportunistic, its image copies cost extra rationed requests, and its per-IP model is structurally incompatible with shared egress. Prices and limits below were read on 2026-09-28 (Gemini 3.8 Flash's price doubles on 2027-01-01), and a closing table lists what the researchers could not verify. Everything said here about the app's own behaviour — its versions, routes, headers and retry timings — comes from the project's documentation (`CLAUDE.md`), the only project file the researchers had; the source itself was not read.

## Three runtime-fixed tells brand every Worker fetch as a bot

A destination classifies a Worker's `fetch()` on three layers before it reads a single header the code set, and all three are fixed by the runtime. The first is the source address. Cloudflare does not publish the ranges Workers egress from — the `cloudflare.com/ips` list covers the proxy-to-origin path for proxied zones, not Worker subrequests — and the only documented way to influence origin is a Durable Object location hint, which changes the colo, not the sharing ([Cloudflare Community](https://community.cloudflare.com/t/what-are-cf-worker-egress-ip-ranges/911150)). The address that recurs across years of reports is **`2a06:98c0:3600::103`**, seen by origins as `CF-Connecting-IP` on Worker subrequests since July 2020 regardless of the real client, with attempts to override it "overwritten later by Cloudflare" ([Cloudflare Community](https://community.cloudflare.com/t/workers-always-pass-cf-connecting-ip-2a063600-103/189944)). That address carries AbuseIPDB reports filed by operators who received malicious traffic from *other* tenants ([AbuseIPDB](https://www.abuseipdb.com/check/2a06:98c0:3600::103)), and origin WAFs have already 403'd it under a "fake Googlebot" ModSecurity rule because its reverse DNS matches nothing ([Cloudflare Community](https://community.cloudflare.com/t/cf-worker-ip-2a063600-103-with-googlebot-triggering-modsec-rule/512125)). Dedicated or static egress for Workers exists only on Enterprise contracts (Static IPs, BYOIP, Aegis); "sharing IP addresses is normal across hosting and CDNs" is the official answer to everyone else ([Cloudflare Community](https://community.cloudflare.com/t/dedicated-ip-static-ip-fixed-egress-ip-for-workers/795286)).

The second tell is the transport fingerprint. Cloudflare's own bot products hash the TLS ClientHello into JA3/JA4, treat it as "a stable identifier across different destination IPs, ports, and certificates," and compute JA4 Signals per fingerprint per hour across the whole network (`browser_ratio_1h`, `reqs_rank_1h`, `ips_rank_1h`, and so on) ([Cloudflare Docs](https://developers.cloudflare.com/bots/additional-configurations/ja3-ja4-fingerprint/)). Akamai's passive HTTP/2 fingerprint reads the SETTINGS frame's parameter order and values, the WINDOW_UPDATE increment, PRIORITY frames and pseudo-header order — Chrome is `1:65536;3:1000;4:6291456|15663105|0`, Firefox and curl differ — and its stated purpose is catching "spoofed User-Agent strings" from tools that "claim browser identity while implementing different HTTP/2 patterns" ([Akamai, Black Hat EU 2017](https://blackhat.com/docs/eu-17/materials/eu-17-Shuster-Passive-Fingerprinting-Of-HTTP2-Clients-wp.pdf)). DataDome-class stacks add TCP/IP characteristics and header order, and the durable signal is inconsistency between layers: "these fingerprints, and the headers, do not describe the same client" ([crawlex](https://blog.crawlex.net/blog/datadome-http2-fingerprinting/)). A Worker's TLS and HTTP/2 framing come from Cloudflare's egress stack, identical for every tenant and invisible to code, so the shared fingerprint's hourly reputation is whatever every other Workers script earned that hour, and the `BROWSER_HEADERS` the Worker sends to sites produce precisely the cross-layer contradiction these systems weight most.

The third tell is the header set. The production runtime sends **no `User-Agent` at all** unless code sets one; an unmodified Worker fetch carries only `accept-encoding: gzip`, `cf-connecting-ip`, `cf-ipcountry`, `cf-ray`, `cf-visitor`, `connection`, `host`, `x-forwarded-proto` and `x-real-ip` ([miniflare #139](https://github.com/cloudflare/miniflare/issues/139)), which is why GitHub's API rejected next-auth on Workers until a UA was added ([next-auth #6741](https://github.com/nextauthjs/next-auth/issues/6741)). Every subrequest is stamped **`CF-Worker: <your zone>`** ([Cloudflare Docs](https://developers.cloudflare.com/fundamentals/reference/http-request-headers/)), and a Cloudflare-hosted destination can match it with the `cf.worker.upstream_zone` rules field, usable in Transform Rules since June 2025 with a documented example that tags external Workers subrequests ([Cloudflare Changelog](https://developers.cloudflare.com/changelog/post/2025-06-09-transform-rule-subrequest-matching/)). `cf-ipcountry` is stripped for non-Cloudflare origins, and the `cache` option on `fetch()` accepts only `no-store` and `no-cache` ([Cloudflare Docs](https://developers.cloudflare.com/workers/runtime-apis/fetch/)).

Two policies then act on those tells. Bot Fight Mode — the Free-plan toggle many food blogs run — issues a JavaScript challenge with mandatory JavaScript Detections, and "you cannot bypass or skip Bot Fight Mode using WAF custom rules or Page Rules"; not even the site owner can exempt a client, and only Super Bot Fight Mode (Pro and up) supports Skip rules ([Cloudflare Docs](https://developers.cloudflare.com/bots/get-started/bot-fight-mode/)). A Worker cannot run the challenge, so no header change helps; a Cloudflare engineer's 2022 answer to API clients hit by it was "we don't have a good way today to allow exceptions" ([Cloudflare Community](https://community.cloudflare.com/t/the-never-ending-nightmare-of-bot-fight-mode-blocking-legitimate-apis/421070)). Cloudflare's own headless-browser product concedes the same: "Browser Run requests are always identified as bot traffic by Cloudflare," and it "cannot configure per-request IP rotation" ([Cloudflare Docs](https://developers.cloudflare.com/browser-run/faq/)). Second, from **15 September 2026**, for new domains — and, the announcement implies, for existing zones whose owners did not opt out beforehand — Cloudflare blocks bots classified as Training or Agent by default on pages that display ads, "non-verified bots are still default blocked," and Agent explicitly covers "chat fetch bots" and "browser-use agents" acting in real time on a person's behalf ([Cloudflare Blog](https://blog.cloudflare.com/content-independence-day-ai-options/)). The escape route Cloudflare offers is Web Bot Auth — Ed25519 HTTP Message Signatures per RFC 9421 over at least `@authority`, a JWKS at `/.well-known/http-message-signatures-directory`, and a dashboard submission ([Cloudflare Docs](https://developers.cloudflare.com/bots/concepts/bot/verified-bots/web-bot-auth/)) — but the policy demands robots.txt compliance and "reasonable request rates," publishes no acceptance threshold, helps only on Cloudflare-protected zones whose owners have not chosen Block for Agents, and is incompatible with browser impersonation ([Cloudflare Docs](https://developers.cloudflare.com/bots/concepts/bot/verified-bots/policy/)).

| Layer | Controllable from Worker code | Fixed by the runtime |
|---|---|---|
| Source IP / ASN | Which colo, via Durable Object location hints (still a shared pool) | Shared, unpublished Cloudflare egress; no proxy setting for `fetch()` ("not possible as workers run on Cloudflare's hardware & network") ([Cloudflare Community](https://community.cloudflare.com/t/is-it-possible-to-fetch-from-workers-via-proxy/441457)) |
| TCP/IP, TLS ClientHello (JA3/JA4), HTTP/2 SETTINGS and pseudo-header order, HTTP version | Nothing | Generated by the egress stack; no published fingerprint value; HTTP version to arbitrary origins undocumented |
| Request headers | `User-Agent`, `Accept`, `Accept-Language`, `Referer`, cookies, `Sec-CH-UA*` strings | `CF-Worker` added; `CF-Connecting-IP` overwritten; `cf-ipcountry` stripped; brotli/gzip requested automatically |
| Behaviour | Pacing, per-host concurrency, `AbortSignal.timeout`, retries, caching, choice of third-party endpoint | Free plan: 50 subrequests and **10 ms CPU** per request, 6 connections in the headers-wait phase, 128 MB ([Cloudflare Docs](https://developers.cloudflare.com/workers/platform/limits/)); fetches are reported to die at roughly 90–125 s (the 125 s proxy read timeout behind error 524) ([Cloudflare Docs](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-5xx-errors/error-524)) |
| JavaScript challenges | Nothing | No JS execution; Bot Fight Mode cannot be passed |
| Tunnelling | Raw TCP via `connect()` from `cloudflare:sockets` ([Cloudflare Docs](https://developers.cloudflare.com/workers/runtime-apis/tcp-sockets/)) | `startTls()` verifies the proxy hostname, so a CONNECT/SOCKS tunnel needs userland TLS — `tunnelfetch` does it at 36–102 ms CPU per MB, unaudited, and far over the Free plan's 10 ms ([tunnelfetch](https://github.com/latentharbor/tunnelfetch)) |

The practical consequence is a header policy, not a header trick: identify honestly (a product `User-Agent` with a URL, browser-typical `Accept` and `Accept-Language`) rather than impersonating Chrome, because impersonation cannot be made consistent across the layers you do not control and converts a "generic automation" score into a "spoofing" score. Honest identification is still refused by JS-challenge and IP-reputation rules, and Cloudflare's September 2026 defaults mean an *identified* Agent is blocked on ad-monetised pages of new zones while an *unidentified* fetch sometimes passes — a tension the research could not resolve and that is ultimately a product decision. What it settles is that sites which block the Worker today will keep blocking it, and the fix is to fetch from somewhere else.

## archive.org meters by IP, and the Worker's IP belongs to everyone

Internet Archive staff, quoted by the maintainers of the edgi `wayback` client, state the rule plainly: CDX requests "are limited to an average of 60/min. Over that and we start sending 429s"; if a client ignores 429s for more than a minute, the requesting IP receives a **1-hour firewall block**, and every subsequent violation **doubles** the block ([edgi wayback #137](https://github.com/edgi-govdata-archiving/wayback/issues/137)). The library's defaults encode that lesson — **0.4 CDX calls/s** and **8 replay calls/s** — and it raises `RateLimitError` with a `retry_after` attribute only "if provided by the server," which is the closest thing to documentation that `Retry-After` is often absent ([wayback docs](https://wayback.readthedocs.io/en/stable/usage.html)). Escalation to a timed block on the IP is what produces the forum genre "429 Too Many Requests despite no requests": the address is inside a block window, not over a sliding budget, and reports run continuously from 2019 through 2 September 2026 ([archive.org forum](https://archive.org/post/1103558/error-429-too-many-requests-despite-no-requests)); the block page tells users to email `info@archive.org` about "why are you being blocked" ([archive.org forum](https://archive.org/post/1103806/reason-for-new-strict-wayback-data-cap-http-429-too-many-requests)). On **15 September 2026** the Wayback Machine's director confirmed new protections against "waves of high-volume automated traffic," a rewritten 429 page, and that "those protections sometimes catch real people by mistake"; the sole remedy is an email with your operating system, browser and IP address ([blog.archive.org](https://blog.archive.org/2026/09/15/an-update-on-wayback-machine-access/)). No number, no API key, no allow-list.

Compose that with the previous section and the Worker's failure is mechanical. archive.org counts by source IP; the Worker's source IP is one of a handful of shared egress addresses; any other tenant hammering `web.archive.org` from that address consumes its 60/min and can push it into a 1 h, 2 h, 4 h block; the app's first request of the day lands inside the window. Two documented cases show the same collision on other per-IP services: the ntfy.sh free tier (`"basis": "ip"`) was exhausted for a Worker sending one or two messages a day because "Cloudflare Workers' shared egress IPs routinely exhaust the ntfy.sh free-tier daily quota for unrelated users," and creating an account did not change the basis ([ntfy #1963](https://github.com/binwiederhier/ntfy/issues/1963)); a brand-new isolated Worker got a 429 from the adsb.lol API "on its first identified request" despite a contact User-Agent and `From` header ([adsblol #272](https://github.com/adsblol/website/issues/272)). This is the model that explains the Worker's own diagnostics: a fresh sign-in refused from the same outgoing address that succeeded minutes earlier means neighbours spent the address's allowance in between, and if a fresh Worker copy gets through where a warm one was refused — the case the project's diagnostics were added to test — it egressed from an address with budget left.

It also explains why signing in did nothing. Only Save Page Now 2 is per-account — authenticated users get 7 captures/min and 30,000/day versus 3/min and 200/day anonymous, and it has its own per-IP errors (`error:blocked-client-ip`, `error:max-daily-bandwidth-from-ip`) on top ([SPN2 API doc](https://docs.google.com/document/d/1Nsv52MvSjbLb2PCpHlat0gkzw0EvtSgpKHu4mk0MnrA/edit)). The read surfaces have no documented account tier: CDX authentication is a `cdx-auth-token` cookie for *restricted* URLs and fields, an access-control mechanism rather than a rate tier ([CDX README](https://github.com/internetarchive/wayback/blob/master/wayback-cdx-server/README.md)), and the Availability API page, last updated in 2013, mentions no authentication or usage policy at all ([archive.org](https://archive.org/help/wayback_api.php)). The honest `ARCHIVE_UA` and the `logged-in-user`/`logged-in-sig` cookies are good manners; they are not a different counter.

One consequence deserves emphasis because the app currently does the opposite. IA's rule is that *ignoring* 429s for over a minute triggers the block and that repeats double it, so the app-level retries at 40, 50 and 60 seconds (four tries over three minutes) are, from the same egress address, the pattern IA's rule penalises in slow motion: each retry is another request against an address that is already blocked, and it can only succeed if the Worker copy servicing it happens to egress from a different address. The Worker-side retry removal in v0.42.5 was right; the app-side loop re-creates the pattern one layer up. A useful detection detail while fixing this: a 429 that carries a **`memento-datetime`** header is a replayed capture of the *target site's* 429, not IA's throttle, and must not trip the breaker ([edgi wayback #158](https://github.com/edgi-govdata-archiving/wayback/issues/158)).

## Use archive.org correctly, then use it less

The four programmatic surfaces are the Availability API, the CDX index, direct replay, and Save Page Now 2, and only the first three matter for reading. Availability is `GET https://archive.org/wayback/available?url=<url>` with optional `timestamp=YYYYMMDDhhmmss`, returning `archived_snapshots.closest{available,url,timestamp,status}` or an empty `archived_snapshots` object when nothing exists; because `closest` can be a 3xx/4xx capture, the `status` field must be checked before fetching ([archive.org](https://archive.org/help/wayback_api.php)). CDX is `GET https://web.archive.org/cdx/search/cdx?url=<url>` with `output=json`, `fl=` to pick fields, `from=`/`to=` (inclusive, `yyyyMMddhhmmss`), `filter=<field>:<regex>` (a leading `!` inverts, e.g. `filter=statuscode:200`), `collapse=`, `fastLatest=true` for exact matches, and `limit=-N` for the *last* N rows; the default cap is 150,000 records and the README specifies no rate limit ([CDX README](https://github.com/internetarchive/wayback/blob/master/wayback-cdx-server/README.md)). The Worker's `fl=timestamp,statuscode,mimetype&fastLatest=true&limit=-10` with client-side filtering is a sound shape; the project's note that a live `filter=` query returned 400 (v0.42.3) is not explained by the documentation, and the Worker's logging of the server's stated reason for any 400 is the right instrument. Replay is `https://web.archive.org/web/<timestamp>id_/<url>`: `id_` returns "the original document as retrieved from the website" with links unchanged and no toolbar, so embedded JSON-LD and `<img>` URLs are the live-web originals; `im_` is the image hint and `if_` the iframe form ([archive.org forum](https://archive.org/post/1008502/faq-on-id_-wayback-toolbar-removal)), and pywb, which shares the modifier vocabulary, documents `id_` as "no content rewriting is performed" ([pywb docs](https://pywb.readthedocs.io/en/latest/manual/rewriter.html)). SPN2 (`POST https://web.archive.org/save/<url>`, `Authorization: LOW key:secret`, `if_not_archived_within=…`, then poll `/save/status/<job_id>`, results kept about an hour) is the only per-account surface, but a capture takes seconds to minutes, is capped at single-digit captures per minute, and cannot capture what the live site refuses to serve to IA's crawler either ([SPN2 API doc](https://docs.google.com/document/d/1Nsv52MvSjbLb2PCpHlat0gkzw0EvtSgpKHu4mk0MnrA/edit)).

The backoff protocol the sources support is: on any 429, first check `memento-datetime`; honour `Retry-After` when present but never depend on it; otherwise stop for at least 60 s and probe once, and if the probe also 429s treat the egress address as firewall-blocked for at least an hour, doubling on repeat, with jitter and never a tight loop ([edgi wayback #137](https://github.com/edgi-govdata-archiving/wayback/issues/137)). Keep replay concurrency at three or fewer per address — downloader users saw 429s "above 4" and clean runs at `-c 3` ([wayback-machine-downloader #160](https://github.com/hartator/wayback-machine-downloader/issues/160)). Cache every Availability and CDX answer and every fetched snapshot indefinitely, since captures are immutable, so a given recipe URL costs IA at most two requests ever. The breaker state ("this egress address is blocked until T") lives naturally in the module memory the Worker already uses for its session; if it must survive across Worker copies, a SQLite-backed Durable Object is on the Free plan (100,000 requests/day) and its single alarm can flip the breaker from open to half-open, with the caveat that alarms retry at most six times so the handler should catch and reschedule itself ([Cloudflare Docs](https://developers.cloudflare.com/durable-objects/platform/pricing/); [Cloudflare Docs](https://developers.cloudflare.com/durable-objects/api/alarms/)).

Even used perfectly, the Archive is a weak fallback for recipe pages. Coverage is opportunistic: pages "may not be archived due to robots exclusions and some sites are excluded by direct site owner request," and dynamic pages lose their functionality ([help.archive.org](https://help.archive.org/help/wayback-machine-general-information/)). Publishers are opting out in a wave — the New York Times hard-blocks IA's crawlers, Gannett's network added `archive.org_bot` and `ia_archiver-web.archive.org` to robots.txt in 2025, and the Guardian, FT, Reddit and others block — over AI-scraping concerns ([Nieman Lab](https://www.niemanlab.org/2026/01/news-publishers-limit-internet-archive-access-due-to-ai-scraping-concerns/)); NYT Cooking presumably sits inside that block (an inference from its parent's policy, not verified for the subdomain), and Dotdash Meredith's status for Serious Eats could not be verified because the researchers' fetches were refused (the one recipe robots.txt they could read, foodnetwork.com, carries no IA rule ([foodnetwork.com](https://www.foodnetwork.com/robots.txt))). The closest capture can be stale or non-200. Images are the expensive part: an `id_` body's image URLs point at the live CDN that already blocks the Worker, while the Archive's `im_` copies each cost another rationed request from the same throttled address — the exact reason the `/img` route now goes through wsrv.nl. And since the September 2026 protections, a datacenter address is *less* welcome at the Archive than at many of the sites the Archive was meant to route around.

There is no drop-in replacement. Google removed the cache link from results in January 2024 and killed the `cache:` operator by September 2024 ([Search Engine Land](https://searchengineland.com/google-search-completely-kills-the-cache-feature-446904)); Bing removed its cache links in December 2024 ([Search Engine Land](https://searchengineland.com/bing-officially-removes-cache-link-from-search-results-449220)). archive.today has no API and serves users of Cloudflare's 1.1.1.1 resolver a different A record and an infinite CAPTCHA loop, unresolved since 2019 with reports through August 2026 ([ardislu gist](https://gist.github.com/ardislu/b2f2b4b439c5da2f7ccb6bb42e7a8882)). Common Crawl's index "is frequently abused and therefore heavily rate limited," answers with 503s and 24-hour IP blocks, and asks for one thread per IP and no proxy networks ([Common Crawl FAQ](https://commoncrawl.org/faq)); staff recommend one index request per second ([Common Crawl group](https://groups.google.com/g/common-crawl/c/BvMGYUY-dro)), and it is a monthly batch crawl with no on-demand capture, so from a shared Worker address it inherits the same tenant collision. The real alternatives change *where the request comes from*: a relay outside Cloudflare (a small VPS, or a home box reachable through a Cloudflare Tunnel) makes the archive.org calls with its own per-IP budget, which solves the throttle but not residential-versus-datacenter scoring at recipe sites; Jina Reader can fetch `r.jina.ai/<archive url>` from its own addresses, as the Worker already tries, subject to Jina's own refusal list; and the user's phone, covered below, needs no archive at all.

## A streaming JSON-LD parse covers 47 of 48 real recipe pages

Google's Recipe rich-result contract is what plugin authors target: `name` and `image` required; `recipeIngredient` as text lines with "only the ingredient text that is necessary"; `recipeInstructions` as `HowToStep` or `HowToSection` ("We recommend using HowToStep," and no "Directions" or "Step 1" prose); `recipeYield` as text or integer, e.g. `["6", "24 cookies"]`; ISO-8601 `prepTime`/`cookTime` (always together) or `totalTime`; `author`, `description`, `keywords`, `nutrition`, `video`, `datePublished` ([Google Search Central](https://developers.google.com/search/docs/appearance/structured-data/recipe)). Recipe is a top-ten schema.org class in the October 2021 Web Data Commons corpus, whose top-ten Recipe properties are name, image, datePublished, description, author, totalTime, recipeYield, recipeIngredient, recipeInstructions and keywords ([ISWC 2023](https://ceur-ws.org/Vol-3632/ISWC2023_paper_445.pdf)), and "since 2020, more PLDs use the JSON-LD syntax than Microdata" ([Brinkmann et al., WWW 2023](https://www.uni-mannheim.de/media/Einrichtungen/dws/Files_Research/Web-based_Systems/pub/Brinkmann-etal-TheWDCSchemaorgDataSetSeries-WWW2023.pdf)). The researchers parsed 48 saved publisher pages from the `recipe-scrapers` test corpus: **47 carried a Recipe in JSON-LD, one (Epicurious) was microdata-only** with the superseded `itemprop="ingredients"`, every page had an `og:image`, and no block failed to parse ([recipe-scrapers test corpus](https://github.com/hhursev/recipe-scrapers/tree/main/tests/test_data); [Epicurious fixture](https://raw.githubusercontent.com/hhursev/recipe-scrapers/main/tests/test_data/epicurious.com/epicurious.testhtml)).

The Recipe hides in three container shapes and the finder must handle all of them: a bare object; a top-level JSON array whose first element has `"@type": ["Recipe"]` (Dotdash Meredith: Serious Eats, Simply Recipes, EatingWell, Martha Stewart, with EatingWell using `["Recipe","NewsArticle"]`); and a Yoast or Rank Math `@graph` where the Recipe sits beside Article, WebPage, ImageObject, Person and Organization nodes and `author` is only an `@id` reference to resolve (every WP Recipe Maker and Tasty Recipes blog sampled) ([Budget Bytes fixture](https://raw.githubusercontent.com/hhursev/recipe-scrapers/main/tests/test_data/budgetbytes.com/budgetbytes.testhtml); [Serious Eats fixture](https://raw.githubusercontent.com/hhursev/recipe-scrapers/main/tests/test_data/seriouseats.com/seriouseats.testhtml)). Kinboard's importer missed every Yoast page because it "only examined the top-level object's `@type`" ([kinboard #283](https://github.com/svenger87/kinboard/issues/283)); the reference Python library checks a Recipe entity, then `WebPage.mainEntity`, then every `@graph` entry, comparing `@type` case-insensitively as string or list ([recipe-scrapers `_schemaorg.py`](https://raw.githubusercontent.com/hhursev/recipe-scrapers/main/recipe_scrapers/_schemaorg.py)). Multiple `ld+json` blocks per page are normal (Food Network UK puts the Recipe in the third), so parse all of them and, when several Recipe objects exist, score by completeness rather than taking the first ([MealPlan #20](https://github.com/holgerkrupp/MealPlan/issues/20)).

Every recipe field is polymorphic in the wild, and the observed variants are the test suite a Worker parser needs. `recipeInstructions` appears as one plain string with sentences run together (Jamie Oliver), one string of HTML paragraphs (King Arthur), `HowToStep{name,text,url}` with `name` equal to `text` (WPRM), `HowToStep{text,url}` (Tasty), `HowToStep{image:[ImageObject…],text}` (Dotdash), `HowToSection{name,itemListElement}` (WPRM ingredient groups; Hearst's Delish and Pioneer Woman), a list nested inside a list (Food52), an empty array (one Pioneer Woman page), and entirely absent (Food Network UK's JSON-LD has no `recipeInstructions` key at all) ([Jamie Oliver fixture](https://raw.githubusercontent.com/hhursev/recipe-scrapers/main/tests/test_data/jamieoliver.com/jamieoliver_1.testhtml); [King Arthur fixture](https://raw.githubusercontent.com/hhursev/recipe-scrapers/main/tests/test_data/kingarthurbaking.com/kingarthur.testhtml); [Food52 fixture](https://raw.githubusercontent.com/hhursev/recipe-scrapers/main/tests/test_data/food52.com/food52.testhtml); [Food Network UK fixture](https://raw.githubusercontent.com/hhursev/recipe-scrapers/main/tests/test_data/foodnetwork.co.uk/foodnetwork.testhtml)). `image` is a string, an array of four size-suffixed crops (WPRM), eight strings (Bon Appétit), an `ImageObject{url,width,height}`, or an array of them. `recipeYield` ranges over `2`, `"8"`, `["6"]`, `["4","4 burgers"]`, `"Makes 12"`, `"Serves 2 to 4"`, `"8 - 10 serving(s)"`, `"4-5"` and `"5 cups (about 120 to 160 crackers)"`; durations are mostly ISO-8601 but include Hearst's `PT0S` placeholder and Bon Appétit's total absence of any time; ingredient strings carry undecoded entities (`"2 &frac12; pounds ripe peaches"`), shop links with `data-sku` attributes, price annotations, and section headers mixed into the list (`"For the roasted parsnips:"`, `"FOR THE MARINADE"`) ([Bon Appétit fixture](https://raw.githubusercontent.com/hhursev/recipe-scrapers/main/tests/test_data/bonappetit.com/bonappetit.testhtml); [Cookie and Kate fixture](https://raw.githubusercontent.com/hhursev/recipe-scrapers/main/tests/test_data/cookieandkate.com/cookieandkate_2.testhtml); [Delish fixture](https://raw.githubusercontent.com/hhursev/recipe-scrapers/main/tests/test_data/delish.com/delish_1.testhtml)). The mature normaliser unescapes entities until stable, strips tags, collapses whitespace, parses yields by picking the list element with a unit word and taking the upper bound of ranges, and parses durations with `isodate` when the string starts with `P` and a natural-language regex otherwise ([recipe-scrapers `_utils.py`](https://raw.githubusercontent.com/hhursev/recipe-scrapers/main/recipe_scrapers/_utils.py)). Ingredient *groups* are almost never in the JSON-LD; they are reconstructed from the DOM by walking headings and items under the plugin hooks `.wprm-recipe-ingredient-group h4` and `.tasty-recipes-ingredients h4` and fuzzy-matching each DOM line back to a schema string with a bigram Dice score ([recipe-scrapers `_grouping_utils.py`](https://raw.githubusercontent.com/hhursev/recipe-scrapers/main/recipe_scrapers/_grouping_utils.py)). WPRM's visible card is actually richer than its JSON-LD — `wprm-recipe-ingredient-amount`, `-unit`, `-name` and `-notes` spans are already split the way the app's `Ingredient` shape wants ([Natasha's Kitchen fixture](https://raw.githubusercontent.com/hhursev/recipe-scrapers/main/tests/test_data/natashaskitchen.com/natashaskitchen_2.testhtml)). Paywall flags are a signal, not a verdict: NYT Cooking marks `isAccessibleForFree: "False"` as a string, yet the fixture's JSON-LD holds all ten ingredients and nine steps while a vendor reports the unauthenticated DOM shows "only the first few ingredients" ([NYT fixture](https://raw.githubusercontent.com/hhursev/recipe-scrapers/main/tests/test_data/cooking.nytimes.com/nytimes.testhtml); [recipe-manager.app](https://www.recipe-manager.app/blog/import-recipes-allrecipes-nyt-bbc)). For Next.js publishers (BBC Good Food, NYT, Delish, the Kitchn, tasty.co) a recursive search of `__NEXT_DATA__` for recipe-shaped objects is a documented last deterministic resort ([MealPlan #20](https://github.com/holgerkrupp/MealPlan/issues/20)).

On the Free plan the binding constraint is the 10 ms CPU budget, and the right tool is the native `HTMLRewriter`: it does "zero-copy streaming parsing," `.on('script[type="application/ld+json"]', …)` delivers text in chunks that must be concatenated, handlers only fire once the transformed stream is drained, and a handler that throws truncates the response ([Cloudflare Docs](https://developers.cloudflare.com/workers/runtime-apis/html-rewriter/); [qwtel](https://qwtel.com/posts/software/how-to-use-htmlrewriter-for-web-scraping/)). Cheerio in a Worker measured 78.7 ms at the 99th percentile in the one published test, with the advice to stream with `htmlparser2` instead ([Cloudflare Community](https://community.cloudflare.com/t/parsing-html-with-cheerio-using-too-much-cpu-time/24831)). The JSON-LD pass needs no DOM at all; the microdata, OpenGraph and plugin-hook passes do, and `linkedom` ships a `linkedom/worker` export that names Cloudflare Workers as a supported runtime ([linkedom](https://github.com/WebReflection/linkedom)). A TypeScript port of `recipe-scrapers` exists — 3.1.0 published 2026-09-23, JSON-LD plus microdata plus OpenGraph plus site rules, 14 custom scrapers and 346 schema-only hosts, `inspectRecipeEvidence(html, url)` to detect a recipe cheaply — but it declares `cheerio ^1` and `zod ^4.5` as peers and `node >= 22`, and nobody has documented it running on Workers ([recipe-scrapers TS](https://github.com/recipe-scrapers/recipe-scrapers); [npm registry](https://registry.npmjs.org/recipe-scrapers)). Its value to a Worker is as a catalogue of edge cases to port, not as a dependency. Readability-style main-content extraction (Defuddle, which also returns `schemaOrgData` ([Defuddle](https://github.com/kepano/defuddle))) is LLM *input* for pages without structure, not a source of fields, because ingredient and step boundaries are not recoverable from prose deterministically.

## Gemini earns its keep as a normaliser, not a fetcher

The URL-context tool is enabled with `tools: [{url_context: {}}]` on `generateContent` and "employs a two-step retrieval process": it "first attempts to fetch the content from an internal index cache" and only on a miss "automatically falls back to do a live fetch" ([Google AI](https://ai.google.dev/gemini-api/docs/generate-content/url-context)). It takes up to **20 URLs per request and 34 MB per URL**, refuses paywalled content and private hosts, and is supported by every 3.x and 2.5 model ([Google AI](https://ai.google.dev/gemini-api/docs/url-context)). Each URL comes back with a `url_retrieval_status` of `SUCCESS`, `ERROR`, `PAYWALL` or `UNSAFE` ([js-genai types](https://raw.githubusercontent.com/googleapis/js-genai/main/src/types.ts)), and the fetched page is billed as ordinary input tokens under `usage_metadata.tool_use_prompt_token_count` — the Interactions-API example shows **10,309 tool-use tokens** for a single page against 27 prompt tokens ([Google AI](https://ai.google.dev/gemini-api/docs/interactions/url-context.md.txt)); the GA announcement is explicit that "you are charged for the added input tokens" at the model's standard rate ([Google Developers Blog](https://developers.googleblog.com/url-context-tool-for-gemini-api-now-generally-available/)). The index cache is the tool's real advantage: a page Google has already crawled is served without any live request to the site, so the site's bot blocking is irrelevant on a hit. The live-fetch path is where the uncertainty lives. Google documents no user agent, IP range, JavaScript rendering, redirect handling, cache TTL or robots.txt behaviour for it; the most plausible identity is `Google-Agent` from the user-triggered-fetchers list, which "generally ignore robots.txt rules" and publish IP ranges in `user-triggered-agents.json` ([Google](https://developers.google.com/crawling/docs/crawlers-fetchers/google-user-triggered-fetchers)), but Google never says so. Serious Eats returning `URL_RETRIEVAL_STATUS_ERROR` in the Worker's logs therefore means both that the page was not served from the index and that the live fetch was refused, and nothing in the response distinguishes the two. An hour with a server you control — point the tool at it and read the access log — would settle the fetcher's identity empirically.

That asymmetry settles the "fetch then pass" versus "let Gemini fetch" question. Fetch-then-pass is the primary path because it is the only one that yields the page's image URLs, keeps freshness and token volume under your control, and can be verified deterministically; URL context is a labelled last resort whose output is text-only. The legacy `generateContent` surface says function calling cannot be combined with URL context, but a JSON response schema can, which is what the Worker already does; on the Interactions surface (documented as GA since June 2026 on one page and "currently in Beta" on another) combining tools with `response_format` is supported for Gemini 3 ([Google AI](https://ai.google.dev/gemini-api/docs/structured-output); [Google AI](https://ai.google.dev/gemini-api/docs/interactions)).

| | Fetch, then pass content (primary) | URL context (last resort) |
|---|---|---|
| Who fetches | Your ladder: Worker, Jina, unlocker, or the user's phone | Google's index cache; else an undocumented live fetcher |
| Bot blocking | Your problem, solved by choosing the origin | Irrelevant on a cache hit; unknown on a live fetch |
| Photos | Yes — you hold the HTML, JSON-LD `image` and step images | Only what the model reports; the retrieved representation is undocumented |
| Freshness | Live page | Cache TTL undocumented |
| Tokens (Sept 2026) | Your choice: JSON-LD only is low thousands; cleaned text tens of thousands; raw HTML a median 7.4× the text | About 10k per page, pre-cleaned, billed as input |
| Verification | Cross-check output against the source you hold | Check `url_retrieval_status`; on `ERROR` the model may recite from memory |
| Failure modes | 403/429/challenge → next rung | `ERROR`/`PAYWALL`/`UNSAFE`; contention 503s on the free tier |

Within fetch-then-pass, the cheapest robust ordering is the one Mealie ships: deterministic scraper first, and the LLM only as a fallback fed "the webpage contents" as cleaned text plus every `application/ld+json` block, asked to emit schema.org JSON-LD that is re-parsed by the same deterministic code ([Mealie `scraper_strategies.py`](https://github.com/mealie-recipes/mealie/blob/mealie-next/mealie/services/scraper/scraper_strategies.py)). For this app the normaliser role is even more natural than Mealie's, because the hard work — splitting `"1 (14 oz) can black beans"` into quantity, unit, item, `canonical`, `category` and `alt`, writing `brief` lines with `{{ }}` tokens, setting `handsOff`, choosing tags from the fixed list — is exactly what an LLM does well over an already-extracted list, and the deterministic pass gives it a source of truth to be held to. When JSON-LD exists, send the Recipe object (a few thousand tokens) as the primary source and the visible ingredient and instruction text as secondary, instruct the model to prefer JSON-LD values and use the text only for section headings and obviously broken fields, and then run checks that need no model: every ingredient's verbatim `raw` line must appear in the source, the step count must sit within one of the `HowToStep` count (a looser cousin of the exact-count rule that already gates step-photo attachment), `quantity` must clear a sanity bound, and total time should roughly equal prep plus cook when all three exist. Schema.org's flat `recipeIngredient` has no group concept, so a house schema with `ingredientGroups` and `instructionGroups` — each with an optional `heading` — is the better output shape, converted to schema.org only for export.

The structured-output subset dictates the schema's shape. Supported: types including `null`, `required`, `additionalProperties`, `enum`, `minItems`/`maxItems`, `anyOf`, `$ref` recursion, and `format: date-time`; the page says only a subset of JSON Schema is supported, and the researchers recorded `oneOf`, `allOf`, `not`, `pattern`, `propertyNames`, `patternProperties` and `propertyOrdering` as the unsupported keywords (a re-read on 2026-09-28 could not reproduce that list verbatim, so treat it as reported). The schema counts against input tokens ([Firebase](https://firebase.google.com/docs/ai-logic/generate-structured-output)), "very large or deeply nested schemas may be rejected," and only syntactic validity is guaranteed ([Google AI](https://ai.google.dev/gemini-api/docs/structured-output)). That rejection is what the Worker's "400 → retry once without `responseSchema`" handles, and it argues for keeping the schema two levels deep, expressing optionality as `["type","null"]` unions, storing times as integer minutes (there is no `pattern` to hold the model to `PT30M`), keeping the app's tag `enum`, and marking only title, ingredients and steps as required, because over-marking fields as required is reported to raise hallucination and quality degrades with nesting depth ([fastCRW](https://fastcrw.com/blog/firecrawl-extract-endpoint-deep-dive)). Keep `parseRecipe` and `sanitizeAiRecipe` as the real validators; a practitioner's TikTok-recipe pipeline got schema-conforming output "most of the time," which is the honest expectation ([Nick Felker](https://fleker.medium.com/gemini-api-and-structured-outputs-turning-tiktok-recipes-into-a-database-of-recipes-ab203fd48679)).

Token economics reward the cleaning. Gemini counts roughly four characters per token ([Google AI](https://ai.google.dev/gemini-api/docs/tokens)); a ten-page measurement found raw HTML costs a **median 7.4× the tokens of the extracted text** (Wikipedia 48,975 → 6,658; BBC News 112,721 → 2,356, or 47.8×), with a further 6–42% saved by dropping `script, style, nav, header, footer, aside, noscript, svg, form` first — measured with an OpenAI tokenizer, so the ratio transfers and the absolute counts do not ([DEV Community](https://dev.to/0012303/feeding-raw-html-to-your-llm-is-a-token-tax-i-measured-it-on-10-real-pages-median-74x-and-it-gcd)). At the prices read on 2026-09-28 — Gemini 3.5 Flash-Lite **$0.30 in / $2.50 out** per million tokens, 3.5 Flash $1.50 / $9.00, 3.8 Flash **$0.75 / $3.75 through 31 December 2026 and $1.50 / $7.50 from 1 January 2027**, 3.1 Flash-Lite $0.25 / $1.50, cached input at a tenth of the input price ([Google AI](https://ai.google.dev/gemini-api/docs/pricing)) — a cleaned 30k-token page plus 1.5k tokens of JSON on Flash-Lite is about **$0.013**, a JSON-LD-only prompt well under a tenth of a cent, and a raw 200k-token HTML dump about $0.06 of input alone with more room for the model to get lost in ad markup. Implicit caching needs a **4,096-token** prefix on the 3.x Flash models before it pays anything, so a one-kilobyte system prompt earns no discount ([Google AI](https://ai.google.dev/gemini-api/docs/caching)). Screenshots remain cheap: 258 tokens per 768×768 tile, so a downscaled phone capture is a few thousand tokens ([Google AI](https://ai.google.dev/gemini-api/docs/image-understanding)).

The model lineup and the tier matter as much as the prompt. Google now steers new projects to `gemini-3.5-flash-lite` (positioned for "simple data extraction") and `gemini-3.8-flash`, is "limiting access to the 2.5 models to users who have actively used them in the past," and has shut down `gemini-2.0-*` ([Google AI](https://ai.google.dev/gemini-api/docs/models); [Gemini 3.5 Flash-Lite card](https://ai.google.dev/gemini-api/docs/models/gemini-3.5-flash-lite)) — the Worker's Flash-Lite default with a Flash fallback matches that guidance. Numeric rate limits moved behind the AI Studio login; the public page documents only the tier ladder (Free; Tier 1 on linking billing, with a $250 spend cap), per-project enforcement, midnight-Pacific daily resets, `429 RESOURCE_EXHAUSTED`, and that "specified rate limits are not guaranteed and actual capacity may vary" ([Google AI](https://ai.google.dev/gemini-api/docs/rate-limits)); a third-party snapshot for September 2026 puts the free tier at **20 requests/day for each 3.x Flash model and 500/day for Flash-Lite**, unverified against Google's own table ([ScriptByAI](https://www.scriptbyai.com/gemini-api-free-tier-limits/)). Two consequences: the free-tier contention the Worker's 30-second aborts and model fallback work around is by design, and the free tier's terms (effective 2026-03-23) let Google use content to "provide, improve, and develop Google products" with human reviewers who "may read, annotate, and process your API input and output," while paid-tier content is not used that way and is logged only for abuse detection ([Google AI](https://ai.google.dev/gemini-api/terms)). Friends' private recipes are the argument for Tier 1 if the owner's no-billing preference is ever relaxed; the pennies per import are not. Calling Gemini by plain `fetch` to `generativelanguage.googleapis.com` is the zero-risk choice — `@google/genai` targets Node 20+ with no Workers statement ([js-genai](https://github.com/googleapis/js-genai)) — and routing through Cloudflare AI Gateway's `google-ai-studio` provider (`https://gateway.ai.cloudflare.com/v1/{account_id}/{gateway_id}/google-ai-studio/v1/models/{model}:generateContent`) adds per-request token logs, which is the easiest way to watch `tool_use_prompt_token_count` drift ([Cloudflare Docs](https://developers.cloudflare.com/ai-gateway/usage/providers/google-ai-studio/)). Search grounding (5,000 free queries a month, then $14 per 1,000) adds nothing to a pasted-URL import ([Google AI](https://ai.google.dev/gemini-api/docs/google-search)).

## The recommended ladder demotes the archive and adds the phone

The ladder below orders channels by the quality they deliver and the address they fetch from, with archive.org demoted and the user's own device promoted; costs are September 2026 list prices.

| Rung | Channel | Address and fingerprint seen by the site | Defeats | Fails on | Cost | Photos |
|---|---|---|---|---|---|---|
| 0 | Cache by canonical URL (the `archiveKey` normalisation, stored) | none | Repeat imports of the same page | — | free | stored |
| 1 | Direct Worker fetch, honest UA, 15–20 s abort, `HTMLRewriter` collecting `ld+json`, `og:*` and the image index | Shared Cloudflare egress; runtime TLS/H2 | Nothing; works on unprotected sites (most WordPress blogs) | Bot Fight Mode, IP reputation, AI-Agent defaults | free; 1–3 subrequests | URLs from JSON-LD and `<img>` |
| 2 | Deterministic parse → Gemini normalise (or Readability text → Gemini extract) | — | Every polymorphic JSON-LD shape | Pages with no structure and no clean prose | ≈$0.001–0.013 per import | — |
| 3a | Jina Reader `r.jina.ai/<url>` | Jina's addresses, headless browser | JS-rendered pages; Cloudflare-Worker-specific blocks | Anti-bot: it "does not actively circumvent" defences and 451s sites that block it | 20 RPM without a key, **500 RPM and 10M tokens with a free key** ([Jina](https://jina.ai/reader/)) | markdown with image links |
| 3b | Unlocker API (Bright Data Web Unlocker; Scrapfly `asp`; Firecrawl `proxy: auto`) | Residential IPs, real browser fingerprints, CAPTCHA solving | Most anti-bot stacks | Paywalls; ToS exposure (below) | Bright Data **5,000 requests/month free, then $1.50 per 1,000** ([Bright Data](https://brightdata.com/pricing/web-unlocker)); Scrapfly 1,000 free credits, 25 per residential request ([Scrapfly](https://scrapfly.io/docs/scrape-api/billing)); Firecrawl 1,000 credits/month free at 10 RPM ([Firecrawl](https://www.firecrawl.dev/pricing)) | HTML or markdown |

| 4 | archive.org `id_` under a per-address circuit breaker, ideally from a relay with its own IP | Shared egress (or the relay's) | Sites that block the Worker but not IA | Per-IP 429/blocks; missing, stale or excluded captures | free | `im_` copies via wsrv.nl (its addresses, not the Worker's) |
| 5 | Gemini URL context | Google's index cache; else an undocumented fetcher | Blocking, on a cache hit | Live-fetch refusals; no photos | ≈10k input tokens | no |
| 6 | User-assisted capture: iOS Shortcut from Safari's share sheet posting the page's JSON-LD, `og:image` and image URLs (or the HTML) to the Worker | The user's residential IP and real Safari, logged in | Everything the user can see, paywalls included | Requires a one-time install; Safari-only | free | URLs, fetched through `/img` |
| 7 | Paste text, screenshot or PDF (shipped) | n/a | Everything | Manual effort | Gemini tokens | screenshots |

Rung 1 should stream. On the Free plan the fetch itself costs no CPU while waiting, but a 500 KB page cannot be regex-scanned twice inside 10 ms, which is the constraint the single-pass `pageImageIndex` already respects; `HTMLRewriter` handlers for `script[type="application/ld+json"]`, `meta[property^="og:"]`, `link[rel="canonical"]`, `img` and `source` pull everything the later rungs need in one pass with no buffered DOM. A 200 response whose body is a challenge page is a soft failure that must escalate, not a success, and 403, 401 and 451 are terminal for this rung rather than retryable (standard practice, not a Cloudflare rule). Rung 3a needs one owner step: Jina's rate limit is 20 requests per minute without a key and 500 with a free one, every new key carries 10 million free tokens, and the average latency is 7.9 s ([Jina](https://jina.ai/reader/)); a key stored as a Worker secret is a 25× headroom increase for nothing. Rung 3b is the only server-side channel whose *fingerprint and address* differ from the Worker's, which is why it succeeds where 3c cannot: Browser Run defeats client-side rendering but is "always identified as bot traffic" and shares the egress pool. The unlocker vendors bill only successful responses (Bright Data "Pay only for success"; Scrapfly withholds that protection above a 30% hourly failure rate) ([Bright Data](https://brightdata.com/pricing/web-unlocker); [Scrapfly](https://scrapfly.io/docs/scrape-api/billing)), and for a few friends' imports the free allowances never run out. Rung 5 must be surfaced as what it is — text without photos — because the owner's rule against silently degrading quality is sound and the tool provides no photo path.

Rung 6 is where the industry landed a decade ago. Paprika ships a built-in browser with a Download button, a Safari share extension and a per-account bookmarklet ([Paprika](https://www.paprikaapp.com/help/ios/)); AnyList ships Chrome, Firefox and Safari extensions plus an iOS share-sheet extension ([AnyList](https://help.anylist.com/articles/recipe-extension/)); Copy Me That is a bookmarklet you drag to the toolbar ([Copy Me That](https://www.copymethat.com/info/button/)); Plan to Eat retired its bookmarklet for extensions and share extensions ([Plan to Eat](https://www.plantoeat.com/recipe-clipper/)); Crouton accepts pasted schema.org Recipe JSON outright ([App Store](https://apps.apple.com/us/app/crouton-recipe-manager/id1461650987)). The reason is mechanical: a script running inside the user's page sees the fully rendered DOM — the `ld+json` blocks, `og:image`, every lazy-loaded `data-src` — from the user's residential IP with the user's real browser fingerprint and session, which defeats every signal in the first section at once, and it scales with the users' own addresses at no cost to the operator. For an installed iPhone PWA the channel is an iOS Shortcut using "Run JavaScript on Web Page": it has full DOM access (`document.querySelectorAll`), returns any JSON via `completion(result)`, but only from the share sheet of Safari (or `SFSafariViewController`), under a time limit, and without synchronous dialogs ([Apple Support](https://support.apple.com/en-in/guide/shortcuts/apd218e2187d/ios)). A PWA `share_target` cannot substitute — it receives only `title`, `text`, `url` and files, never the DOM, and is not Baseline ([MDN](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Manifest/Reference/share_target)) — which matches the project's finding that WebKit does not implement it anyway. The Shortcut returns the JSON-LD text, `og:image`, the canonical URL and the deduplicated image URLs (the same fields rung 1 collects), and posts them to a new Worker route that feeds the identical parse-and-normalise path, so the imported recipe is indistinguishable from a direct import. Two design notes follow from the app's own constraints: the Worker authenticates callers by Firebase ID token, which a Shortcut cannot mint, so the route needs a per-member capture token generated in Settings and embedded in the Shortcut the member installs from a shared link; and photo bytes should still flow through `/img` (or wsrv.nl), because a cross-origin image fetched from inside the PWA is CORS-opaque and cannot be compressed, whereas the image CDNs that block the Worker's HTML request may still serve the images, a point the next section covers. Fetching from the user's device also happens to be the posture the Ninth Circuit treated most favourably in August 2026, as the legal section explains.

The order of operations for the Worker is then: cache; direct fetch with streaming extraction; deterministic parse and Gemini normalisation; on 403, 429, 451 or a challenge body, Jina, then the unlocker's free tier; archive.org only when its breaker is closed and only from an address with budget; URL context as an explicitly labelled text-only import; and, for the sites that fail all of it (Serious Eats blocks the direct fetch, Google's reader and Jina alike, per the project's own notes), a plain message that names the Shortcut and the paste and screenshot paths rather than a three-minute countdown against an archive address that is already blocked.

## Photos: discover them in JSON-LD, fetch with a blank Referer, keep re-hosting

Recipe pages expose the hero image redundantly and deliberately. Google requires `image` on Recipe, asks for "multiple high-resolution images (minimum of 50K pixels when multiplying width and height)" in 16:9, 4:3 and 1:1, and treats them as the publisher's chosen crops of the dish ([Google Search Central](https://developers.google.com/search/docs/appearance/structured-data/recipe)); `og:image` follows, where "the first tag (from top to bottom) is given preference" and `og:image:width`/`og:image:height` allow a size check without fetching ([ogp.me](https://ogp.me/)). Step images ride `HowToStep.image` — recommended by Google, emitted by Tasty Recipes and WP Recipe Maker, and present as `ImageObject` arrays on Dotdash pages including Serious Eats ([WP Tasty](https://support.wptasty.com/en/articles/3746446-how-do-i-add-step-by-step-videos-and-images-to-my-recipe-card); [Serious Eats fixture](https://raw.githubusercontent.com/hhursev/recipe-scrapers/main/tests/test_data/seriouseats.com/seriouseats.testhtml)). The discovery order that falls out is JSON-LD `image` (any entry of the crop array is a valid hero and the rest are free thumbnails), then the first `og:image`, then in-card `<img>` elements read as `data-lazy-src`, `data-src`, the largest `w` descriptor in `data-srcset`/`srcset`, then `src`, plus `<picture><source>` variants. WordPress 5.5+ adds native `loading="lazy"` only when `width` and `height` are present and leaves the real `src` in place, so a non-JS fetcher sees the true URLs ([Make WordPress Core](https://make.wordpress.org/core/2020/07/14/lazy-loading-images-in-5-5/)); ad-heavy blogs on JavaScript lazy-loaders such as lazysizes park the real URL in `data-src` behind a placeholder ([lazysizes](https://afarkas.github.io/lazysizes/index.html)). The `pageImageVariants` stem-matching already in the Worker is the right answer to the Archive-only-saves-shown-sizes problem, and Photon-served blogs (`https://i0.wp.com/<domain>/<path>?w=…&resize=…`) accept `w`, `h`, `resize`, `fit`, `quality` and `strip` parameters, so stripping or rewriting the query string yields the original or any width from the same URL ([WordPress.com Developer](https://developer.wordpress.com/docs/photon/api/)). Junk is rejected cheaply: anything under Google's own 50K-pixel floor (which also kills tracking pixels), SVG and ICO, filenames matching logo, icon, avatar, badge, sprite, pixel, ad, banner, placeholder or spacer, aspect ratios outside 1:2–2:1, and tiny `data:` placeholders.

Fetching images is a different problem from fetching HTML, and usually an easier one. Cloudflare Hotlink Protection — common on blogs — "denies access to requests when the HTTP referer does not include your website domain name (and is not blank)," covers only `gif, ico, jpg, jpeg, png`, and therefore *allows* a request with no `Referer`; sending the app's own domain as `Referer` is exactly what gets blocked ([Cloudflare Docs](https://developers.cloudflare.com/waf/tools/scrape-shield/hotlink-protection/)). Send `Accept: image/avif,image/webp,image/*,*/*;q=0.8` so negotiating CDNs return a modern format, and treat the response as an image only if `Content-Type` starts with `image/` and the first bytes match a known magic number — Cloudflare's own transformation service has a dedicated error, 9412, for "origin returned non-image content (HTML, error page, etc.)," and 9408 for an origin 4xx, because challenge pages arrive with status 200 ([Cloudflare Docs](https://developers.cloudflare.com/images/reference/troubleshooting/)). URLs carrying `expires=`, `X-Amz-Signature`, `sig=` or `token=` are signed and must be fetched during the import or lost. Whether image CDNs bot-block as aggressively as HTML routes is not something the researchers found data on; mechanistically, WAF rules are written against HTML paths and image CDNs are often separate hostnames with their own policies, so the expectation is less blocking, except on zones running Super Bot Fight Mode or the AI-bot block across the whole zone.

The storage decision is already made correctly for the constraints. Firebase Storage is unavailable on the Spark plan for both bucket generations; Blaze's no-cost quota is 5 GB stored and 1 GB/day downloaded on legacy buckets, then $0.026/GB stored and $0.12/GB downloaded ([Firebase](https://firebase.google.com/pricing)), so Firestore data-URL photo documents avoid a billing account at the price of a ~1 MB ceiling that `compressToDataUrl` enforces. If volume ever outgrows that, the Cloudflare-side exit is R2 — **$0.015/GB-month, egress free, Class A writes $4.50 per million, Class B reads $0.36 per million, with 10 GB, one million Class A and ten million Class B free each month** ([Cloudflare Docs](https://developers.cloudflare.com/r2/pricing/)) — paired with the Images binding, whose `env.IMAGES.input(stream).transform({width}).output({format:"image/webp"})` chain accepts inputs up to 20 MB, whose `.info()` size check is free, and whose first **5,000 unique transformations per month are free, then $0.50 per 1,000** ([Cloudflare Docs](https://developers.cloudflare.com/images/transform-images/bindings/); [Cloudflare Docs](https://developers.cloudflare.com/images/pricing/)). A content-addressed key (`img/<sha256 of the normalised original>.webp`) dedupes the same photo across recipes and sites; R2 has no content addressing of its own, and concurrent writes to one key are limited to one per second ([Cloudflare Docs](https://developers.cloudflare.com/r2/platform/limits/)). Whether R2's free tier requires a payment method on file was not checked and should be confirmed before treating it as billing-free. Re-hosting rather than hotlinking is the right default technically — it survives CDN URL rotation and hotlink rules and stops every recipe view from sending the reader's IP and cookies to the source site's ad-tech CDN — and it has a legal dimension the next section addresses.

## Legal and etiquette boundaries (background, not legal advice)

This section is background for an engineering decision, not legal advice; the reader is in Georgia, several of the controlling cases are from other circuits, and the researchers could not retrieve several primary texts. With that said, the copyright picture for recipe *text* is unusually favourable. The Copyright Office states that "a mere listing of ingredients is not protected under copyright law," while "substantial literary expression in the form of an explanation or directions" may be ([U.S. Copyright Office](https://www.copyright.gov/help/faq/faq-protect.html)). The Seventh Circuit excluded a cookbook's recipes from protection under §102(b) in *Publications International v. Meredith* (1996), the Sixth Circuit called recipes "functional directions for achieving a result" in *Lambing v. Godiva* (1998), and *Tomaydo-Tomahhdo v. Vozary* (N.D. Ohio 2015) held that "the identification of ingredients necessary for the preparation of food is a statement of facts"; the caution is *Barbour v. Head* (S.D. Tex. 2001), which declined to rule recipes unprotectable where they carried "light-hearted or helpful commentary" ([National Law Review](https://natlawreview.com/article/mixing-things-let-s-talk-recipes-part-one-four-part-series-copyright)). An LLM normaliser that discards headnotes and rewrites steps tersely reduces copied expression; it does not touch photographs, which are fully protected. Embedding a photo hosted elsewhere is not direct infringement under the Ninth Circuit's server test (*Perfect 10 v. Amazon*, reaffirmed in *Hunley v. Instagram*, 2023), but S.D.N.Y. courts have rejected that test in *Goldman v. Breitbart*, *Nicklen v. Sinclair* and *McGucken v. Newsweek* ([Davis Wright Tremaine](https://www.dwt.com/insights/2023/08/server-test-instagram-case-ninth-circuit)), the Eleventh Circuit has no controlling decision the researchers could find, and re-hosting makes a copy either way. For a private, per-user archive the closest analogy is a reader saving a photo to their own device; for any *public* surface the analogy is Recipeasly, the 2021 site that stripped ads and introductions from food-blog recipes, drew a backlash over "stealing content, eliminating context and creator revenue," and was offline within days ([Yahoo News](https://ca.news.yahoo.com/food-website-fixed-recipes-removing-222534398.html)). Keep imported content inside the kitchen, store and show source URL and author, and never build discovery or SEO pages from it.

Access law has moved decisively toward the fetch being lawful and the *terms* being the live risk. *Van Buren* (2021) confined the CFAA to entering off-limits areas, and *hiQ v. LinkedIn* (9th Cir. 2022) held that "access to public information online likely cannot be a violation of the CFAA" because a site with no login "has erected no gates to lift or lower" ([EFF](https://www.eff.org/deeplinks/2022/04/scraping-public-websites-still-isnt-crime-court-appeals-declares)); LinkedIn nonetheless prevailed on breach of contract, and "contract-based enforcement [is] the primary legal tool for data owners" now ([Ropes & Gray](https://www.ropesgray.com/en/insights/alerts/2026/05/web-scraping-in-the-age-of-ai-guidance-for-data-owners-and-scrapers)). *Meta v. Bright Data* (N.D. Cal., January 2024) held Meta's anti-scraping terms bind only logged-in users, so a logged-out scraper stands "in the same shoes as a visitor" ([Farella Braun + Martel](https://www.fbm.com/publications/major-decision-affects-law-of-scraping-and-online-data-collection-meta-platforms-v-bright-data/)), and *Ryanair v. Booking* ended at the district court in January 2025 with judgment as a matter of law for Booking because the CFAA "loss" claimed was not technological harm ([Eric Goldman blog](https://blog.ericgoldman.org/archives/2025/03/court-overturns-a-bad-jury-verdict-against-scraping-ryanair-v-booking-guest-blog-post.htm)). Most relevant to the ladder, *Amazon v. Perplexity* (9th Cir., **4 August 2026**) vacated an injunction against an agentic browser because "it is the user who 'accesses' Amazon's computers," on the critical fact that "Perplexity itself does not directly communicate with Amazon's servers" — communications ran through the user's machine — while expressly leaving terms-of-service theories open and noting the outcome could differ if the company's servers spoke to the site directly ([Cooley](https://www.cooley.com/news/insight/2026/2026-08-06-ninth-circuit-rules-on-ai-agent-access-to-third-party-websites-under-cfaa); [Justia](https://law.justia.com/cases/federal/appellate-courts/ca9/26-1444/26-1444-2026-08-04.html)). A Worker fetch is the operator's servers communicating directly; the Shortcut path is the user's device — the same distinction the court drew. Publisher terms do bar automation: the Warner Bros. Discovery visitor agreement (Food Network's corporate family) forbids using "an automatic device (such as a robot or spider) or manual process to copy or 'scrape'" content without written permission ([WBD](https://www.wbd.com/visitor-agreement)), and NYT's terms prohibit using content to train AI ([Gizmodo](https://gizmodo.com/nyt-no-ai-data-scraping-terms-of-service-chatgpt-1850734918)); Allrecipes' current terms could not be retrieved. Never import through a member's authenticated cookies for a paywalled site, honour any cease-and-desist naming the app by denylisting the host, and note that the researchers found no reported action against Paprika, Mealie or AnyList — absence of evidence, not evidence of absence.

robots.txt is etiquette with legal weight, not authorisation. RFC 9309 addresses "automated clients" that crawl, says its rules "are not a form of access authorization," caps cache age at 24 hours, lets a crawler proceed when robots.txt is *unavailable* (4xx) and requires it to assume complete disallow when the file is *unreachable* (5xx) ([RFC 9309](https://www.rfc-editor.org/rfc/rfc9309.html)); it "is not a law, not a contract, and not an enforceable directive," but ignoring it "functions as evidence of intent" in CFAA, copyright and contract disputes ([ByteTunnels](https://bytetunnels.com/posts/is-robots-txt-legally-binding-scraping-law-explained/)), and Cloudflare's verified-bot policy makes obeying it and `crawl-delay` a condition of being let through by identity ([Cloudflare Docs](https://developers.cloudflare.com/bots/concepts/bot/verified-bots/policy/)). A single page fetched on a member's tap is closer to a browser than a crawler, so the reasonable line is: read robots.txt, cache it a day, respect any rule naming the app's product token or a blanket `Disallow: /`, tell the member why an import was refused, and never crawl, prefetch or follow links. The newer signals — the IETF `aipref` vocabulary's `train-ai`, `ai-use` and `search` preferences (draft -08, 14 September 2026) ([IETF](https://datatracker.ietf.org/doc/draft-ietf-aipref-vocab/)) and the `noai`/`noimageai` meta tags ([Foundation Web Dev](https://www.foundationwebdev.com/2022/11/noai-noimageai-meta-tag-how-to-install/)) — concern AI use of content; cheap compliance is to skip the Gemini step and the photo re-host on pages that carry them and say so. Cloudflare's Pay Per Crawl (HTTP 402 with `crawler-price`, settled with `crawler-exact-price`, registered through Web Bot Auth) remained a private beta in every source ([Cloudflare Blog](https://blog.cloudflare.com/introducing-pay-per-crawl/)). The operational etiquette that follows costs nothing: an honest `User-Agent` with a contact URL, one in-flight request per host, cached fetches so re-imports never refetch, `Retry-After` honoured, query strings redacted in logs, fetched HTML retained only as long as the import needs it, and a deletion path that cascades to photos.

## Conclusion

The unifying insight is that every failure the app has fought from v0.39 to v0.45 — recipe sites refusing the Worker, the Archive's 429s, Google's reader failing on the same hosts — traces to one variable the Worker cannot set: the address and fingerprint its requests carry. Header tuning, honest identification, Archive logins and countdown retries all operate on layers the classifiers weight least, and the Archive's per-IP escalation means the retries are net negative. The import problem is therefore not a scraping problem at all but a routing problem, and the two routes that change the variable are the user's phone and a third party's residential addresses; everything else is arranging for the Worker to do the deterministic work well once the bytes arrive.

That reframing also changes what "reliable" means for the friends who use the app. Reliability is no longer the depth of the fallback chain but the honesty of its outcomes: a direct or unlocker import delivers structure plus photos, a URL-context import delivers text and says so, and a blocked site hands the member a Shortcut and a paste path instead of a spinner. The Sept 2026 shifts — Cloudflare blocking Agents by default on ad-monetised pages, the Archive tightening against datacenter traffic, and the Ninth Circuit treating user-directed fetching as the user's own access — all point the same direction: the ecosystem is being rebuilt to prefer requests that come from a person's own device, and an importer designed around that will keep working as server-side channels keep closing.
