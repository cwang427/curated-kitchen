# Cloudflare Workers fetch(): why third-party sites block it, and reliable alternatives for fetching user-supplied recipe URLs (state as of 2026-09-28)

Scope note: covers the direct-fetch problem from a Worker, what can/cannot be changed in Worker code, Cloudflare's own page-fetching product (Browser Rendering, now renamed "Browser Run"), third-party fetch/reader/scrape APIs, proxying, and client-side (on-device) alternatives. archive.org, schema.org parsing, Gemini prompting and image storage are out of scope (covered by other researchers).

---

## KQ1. What does a Worker's outbound fetch() look like to the destination server, and why is it classified as bot traffic?

### Takeaway
A Worker subrequest arrives from a Cloudflare-owned IP that is shared by every Workers customer (the well-known IPv6 egress `2a06:98c0:3600::103` recurs across a decade of reports), carries no `User-Agent` at all unless the code sets one, and — when the destination is another Cloudflare zone — is stamped with a `CF-Worker: <your-zone>` header and exposed to that zone's rules as `cf.worker.upstream_zone`. Cloudflare's own Browser Run FAQ states flatly that traffic from its rendering service "is always identified as bot traffic by Cloudflare", and Bot Fight Mode's core mechanism (a JavaScript challenge that a non-browser client can never solve) is why fetch() from a Worker to a BFM-protected site fails regardless of headers.

### Cited Findings

**Egress IPs (shared, unpublished, Cloudflare ASN)**
- Cloudflare Community (March 26, 2026 thread): "The IPs specifically used by Workers outgoing requests are not published." The published cloudflare.com/ips list covers only the proxy-to-origin path for DNS-proxied zones, not Worker egress; the recommended way to influence where requests originate is Durable Objects with location hints (e.g. `weur`, `eu`) — not IP allowlisting. — [Cloudflare Community: What are CF worker egress IP ranges?](https://community.cloudflare.com/t/what-are-cf-worker-egress-ip-ranges/911150)
- Since July 13, 2020 (approx. 11:15 UTC) multiple Workers users observed that subrequests reaching origins carried `CF-Connecting-IP: 2a06:98c0:3600::103` "regardless of true client IP, even with IPv4", and attempts to override the header were "overwritten later by Cloudflare". — [Cloudflare Community: Workers always pass CF-Connecting-IP 2a06:98c0:3600::103](https://community.cloudflare.com/t/workers-always-pass-cf-connecting-ip-2a063600-103/189944)
- The same IP `2a06:98c0:3600::103` is used by other Cloudflare features (Automatic Signed Exchanges), and origin-side WAFs (Atomicorp ModSecurity rule 303800 "Fake Googlebot") have returned 403 to it because reverse/forward DNS did not match — i.e. origin WAFs already treat this address as suspicious infrastructure traffic. — [Cloudflare Community: CF worker IP 2a06:98c0:3600::103 with Googlebot triggering ModSec rule](https://community.cloudflare.com/t/cf-worker-ip-2a063600-103-with-googlebot-triggering-modsec-rule/512125)
- The address is registered to "Cloudflare, Inc." and has abuse reports filed against it on AbuseIPDB (reputation is shared by everyone who egresses through it). — [AbuseIPDB: 2a06:98c0:3600::103](https://www.abuseipdb.com/check/2a06:98c0:3600::103); operator complaints about "malicious requests coming from Cloudflare Workers (2a06:98c0:3600::103)" appear on the Cloudflare forum — [Cloudflare Community: URGENT: Malicious requests coming from Cloudflare Workers](https://community.cloudflare.com/t/urgent-malicious-requests-coming-from-cloudflare-workers-2a063600-103/809347) — and on hosting-panel forums — [DirectAdmin Forums: About CloudFlare workers.dev, IPv6, and malicious HTTPS requests](https://forum.directadmin.com/threads/about-cloudflare-workers-dev-ipv6-and-malicious-https-requests.72658/)
- Browser Run (the headless-Chrome product) egresses the same way: "Browser Run requests originate from Cloudflare's global network and you cannot configure per-request IP rotation"; its requests carry identifying headers `cf-biso-request-id` and `cf-biso-devtools`. — [Cloudflare Docs: Browser Run FAQ](https://developers.cloudflare.com/browser-run/faq/)

**Dedicated / static egress IPs**
- Community answer (thread opened May 5, 2025): "Any dedicated IP addressing requires an Enterprise plan. You will need to contact Cloudflare Sales for pricing." Options named: Static IPs, BYOIP, and Aegis — all Enterprise. "Sharing IP addresses is normal across hosting and CDNs." — [Cloudflare Community: Dedicated IP / Static IP / Fixed egress IP for workers](https://community.cloudflare.com/t/dedicated-ip-static-ip-fixed-egress-ip-for-workers/795286)
- Cloudflare's dedicated-egress-IP products that are documented are Cloudflare One / Gateway egress policies (Zero Trust, for user/device traffic), not Workers fetch(). — [Cloudflare Docs: Dedicated egress IPs (Cloudflare One)](https://developers.cloudflare.com/cloudflare-one/traffic-policies/egress-policies/dedicated-egress-ips/)

**Default headers on a Worker subrequest**
- Header dump from a production Worker fetch() with no headers set (reported in the Miniflare repo; Miniflare 2.0.0 changed its local behaviour to match): `accept-encoding: gzip`, `cf-connecting-ip`, `cf-ipcountry`, `cf-ray`, `cf-visitor: {"scheme":"https"}`, `connection: Keep-Alive`, `host`, `x-forwarded-proto: https`, `x-real-ip`. "The production Cloudflare Workers runtime notably does not send a User-Agent header by default." — [GitHub cloudflare/miniflare#139](https://github.com/cloudflare/miniflare/issues/139)
- Corroboration (2023): next-auth's GitHub provider broke on Workers/Pages because GitHub's API requires a User-Agent and "the cloudflare worker platform ... doesn't provide a default user-agent"; fix was to set `User-Agent` explicitly. — [GitHub nextauthjs/next-auth#6741](https://github.com/nextauthjs/next-auth/issues/6741)
- Current Fetch docs: "brotli or gzip compression is automatically requested when fetching from an origin"; only `cache: 'no-store'` and `cache: 'no-cache'` are accepted (`TypeError` otherwise). — [Cloudflare Docs: Workers Fetch API](https://developers.cloudflare.com/workers/runtime-apis/fetch/)
- `CF-Connecting-IP` on a Worker subrequest "reflects `x-real-ip` (same-zone) or a Worker client IP for security (cross-zone)"; `CF-IPCountry` is "Removed from Worker requests to non-Cloudflare origins". — [Cloudflare Docs: Cloudflare HTTP headers](https://developers.cloudflare.com/fundamentals/reference/http-headers/)

**The `CF-Worker` header and `cf.worker.upstream_zone`**
- "The `CF-Worker` request header is added to an edge Worker subrequest that identifies the host that spawned the subrequest", value = the zone name owning the Worker (e.g. `CF-Worker: example.com`). — [Cloudflare Docs: Cloudflare HTTP headers](https://developers.cloudflare.com/fundamentals/reference/http-headers/)
- Reliability discussion of the header exists on the forum (title: "Is the CF-Worker header from worker fetch() reliable?"). — [Cloudflare Community](https://community.cloudflare.com/t/is-the-cf-worker-header-from-worker-fetch-reliable/185560)
- Ruleset Engine field `cf.worker.upstream_zone` (String) "identifies whether a request comes from a worker or not"; contains the zone name when the request originates from a Worker, empty otherwise. — [Cloudflare Docs: cf.worker.upstream_zone](https://developers.cloudflare.com/ruleset-engine/rules-language/fields/reference/cf.worker.upstream_zone/)
- June 9, 2025 changelog: `cf.worker.upstream_zone` became usable in Transform Rules; documented example `(cf.worker.upstream_zone != "" and cf.worker.upstream_zone != "myappexample.com")` to tag external Workers subrequests with `X-External-Workers-Subrequest: 1`. Stated use case: "Skip or apply logic conditionally when handling Workers subrequests". — [Cloudflare Changelog 2025-06-09](https://developers.cloudflare.com/changelog/post/2025-06-09-transform-rule-subrequest-matching/)
- WAF FAQ: when "a request goes through a Cloudflare Worker ... Cloudflare considers the client details, including its IP address, for triggering security settings. However, the IP displayed in Security Events will be a Cloudflare IP address." — [Cloudflare Docs: WAF FAQ](https://developers.cloudflare.com/waf/troubleshooting/faq/)
- `wrangler dev --remote` adds `cf-workers-preview-token` to all outgoing requests, and "making HTTP requests to other Cloudflare zones is currently discarded for security reasons" unless the header is deleted (`request.headers.delete('cf-workers-preview-token')`). — [Cloudflare Docs: Workers known issues](https://developers.cloudflare.com/workers/platform/known-issues/)

**Bot Fight Mode (BFM) vs. Worker subrequests to other Cloudflare zones**
- BFM "Identifies traffic matching patterns of known bots" and "Issues computationally expensive challenges that force the requesting client to perform CPU-intensive calculations"; "For Bot Fight Mode customers, JavaScript Detections is automatically enabled and cannot be disabled"; and critically "You cannot bypass or skip Bot Fight Mode using WAF custom rules or Page Rules ... Skip, Bypass, and Allow actions have no effect." Cloudflare's advice: "use Super Bot Fight Mode instead. Super Bot Fight Mode runs on the Ruleset Engine and supports Skip rules." — [Cloudflare Docs: Get started with Bot Fight Mode](https://developers.cloudflare.com/bots/get-started/bot-fight-mode/)
- Community thread (Sept 21–27, 2022) on BFM blocking legitimate API clients: BFM assumes "if it's a human, it has a browser running JavaScript" and non-browser clients "will fail such challenges"; a Cloudflare team member replied "we don't have a good way today to allow exceptions ... we're working on a solution." — [Cloudflare Community: The Never-Ending Nightmare of Bot Fight Mode blocking legitimate APIs](https://community.cloudflare.com/t/the-never-ending-nightmare-of-bot-fight-mode-blocking-legitimate-apis/421070)
- Community thread on "bot fight mode blocks CF requests?": "Cloudflare services accessing your site via a proxied host seem to be treated the same as any external bot." — [Cloudflare Community](https://community.cloudflare.com/t/bot-fight-mode-blocks-cf-requests/572124)
- Super Bot Fight Mode (Pro/Business/Enterprise): "Custom rules are executed before Super Bot Fight Mode. To configure exceptions to Super Bot Fight Mode, create a custom rule with the Skip action." Documented analog for automated infrastructure traffic: "If your organization also uses Cloudflare Tunnel, keep Definitely Automated set to Allow. Otherwise, Super Bot Fight Mode may block tunnel connections". — [Cloudflare Docs: Get started with Super Bot Fight Mode](https://developers.cloudflare.com/bots/get-started/super-bot-fight-mode/)
- Cloudflare's own headless browser product is classified the same way: "Yes, Browser Run requests are always identified as bot traffic by Cloudflare." (with the caveat that "Cloudflare does not enforce bot protection by default — that is the customer's choice"). — [Cloudflare Docs: Browser Run FAQ](https://developers.cloudflare.com/browser-run/faq/)

**HTTP version to origin**
- Cloudflare's proxy: "At Cloudflare, HTTP/2 connection to the origin is enabled by default", falling back to HTTP/1.1 via ALPN; available on all plans. The page does not address Workers subrequests. — [Cloudflare Docs: HTTP/2 to Origin](https://developers.cloudflare.com/speed/optimization/protocol/http2-to-origin/)
- A user testing a deployed Worker in Aug 2022 reported that both the playground and a webhook tester "reports 1.1" for fetch() subrequests; no staff answer. — [Cloudflare Community: HTTP/2 fetch to Origin from Workers](https://community.cloudflare.com/t/http-2-fetch-to-origin-from-workers/413317); a June 2022 thread likewise has no official statement. — [Cloudflare Community: Workers: fetch, and HTTP/2](https://community.cloudflare.com/t/workers-fetch-and-http-2/389945)
- A workerd feature request asserts (user claim, not Cloudflare) that "Currently `fetch` in a real Worker uses HTTP/2 when possible, but when developing locally this doesn't seems to be supported." — [GitHub cloudflare/workerd#5266](https://github.com/cloudflare/workerd/issues/5266)

### Inferences
- Mechanistically, a destination sees three independent tells before it reads a single byte of your headers: (1) source IP in Cloudflare's AS13335 space with a shared, pre-existing abuse history; (2) a TLS ClientHello and HTTP/2 SETTINGS/pseudo-header profile generated by Cloudflare's egress stack, identical for every Workers customer and unlike any browser; (3) no `User-Agent` and a minimal header set (`accept-encoding: gzip`, no `Accept`, no `Accept-Language`, no `Sec-CH-UA`). Adding a browser-like `User-Agent` in code fixes only (3) and creates a *contradiction* with (2), which is exactly the signal modern anti-bot vendors weight most (see KQ2).
- Because egress IPs are shared and unpublished, any per-IP rate limit at a destination (e.g. a 429 from a recipe site or from archive.org) is a budget shared with every other Workers script on the planet hitting that host from the same colo; your own request volume can be near zero and you still get throttled. Durable Object location hints change *which* colo/IPs you egress from but not that they are shared.
- For a recipe site that itself sits behind Cloudflare Free-plan Bot Fight Mode, a Worker fetch() cannot succeed by any header change: BFM's decision is JS-challenge based and cannot be skipped even by the site owner's WAF rules; only the site owner turning BFM off or moving to Super Bot Fight Mode with "Definitely automated = Allow" (or a Skip rule matching `cf.worker.upstream_zone`) would let it through. A third-party recipe blog will not do this for you.
- The presence of `CF-Worker`/`cf.worker.upstream_zone` means a Cloudflare-protected recipe site could match Worker traffic explicitly, but nothing in the docs says Bot Fight Mode uses it; the blocking is explained sufficiently by the JS-challenge mechanism.

### Gaps
- No official statement was found on which HTTP version production Workers fetch() negotiates with arbitrary origins (observations conflict: HTTP/1.1 observed in 2022; a 2026 issue claims HTTP/2 "when possible"). Treat as unknown; either way the fingerprint is Cloudflare's, not a browser's.
- No published JA3/JA4 or Akamai-format HTTP/2 fingerprint value for Workers fetch() egress was found in any source.
- The header dump proving "no User-Agent" is from 2021 (Miniflare issue) with 2023 corroboration (next-auth); no 2026 re-verification was found. Behaviour is consistent across all sources located.
- Cloudflare's docs no longer contain an explicit "Bot Fight Mode blocks Workers subrequests" known-issue entry (checked Workers known issues, Bots FAQ, WAF FAQ, WAF interoperability page); the behaviour is evidenced by the BFM mechanism description and community threads only.

## KQ2. Which bot-detection signals do recipe sites and their CDNs/WAFs use, and which can a Worker control?

### Takeaway
Detection stacks (Cloudflare Bot Management, DataDome, Akamai, etc.) fingerprint the TLS ClientHello (JA3/JA4), the HTTP/2 connection preface (SETTINGS values/order, WINDOW_UPDATE, PRIORITY, pseudo-header order), TCP/IP characteristics, header set/order, IP/ASN reputation and JS-executed device signals — and score *inconsistency* between layers rather than any single "bad" value. From Worker code you control only the HTTP header layer (and even there some CF-* headers are overwritten); TLS, HTTP/2 framing, TCP and source IP are fixed by the runtime, so a browser `User-Agent` on a Worker fetch produces the exact cross-layer mismatch these systems are built to catch.

### Cited Findings
- Cloudflare: JA3/JA4 "identify TLS clients based on how they initiate connections"; the fingerprint is "a stable identifier across different destination IPs, ports, and certificates"; JA4 sorts ClientHello extensions to reduce browser fingerprint churn; fingerprints are exposed to WAF custom rules, Transform Rules and Workers; "JA4 Signals" add aggregate behavioural metrics per fingerprint over 1 h windows (`h2h3_ratio_1h`, `browser_ratio_1h`, `cache_ratio_1h`, `heuristic_ratio_1h`, `uas_rank_1h`, `paths_rank_1h`, `reqs_rank_1h`, `ips_rank_1h`, `reqs_quantile_1h`, `ips_quantile_1h`). — [Cloudflare Docs: JA3/JA4 fingerprint](https://developers.cloudflare.com/bots/additional-configurations/ja3-ja4-fingerprint/)
- Cloudflare Bot Management exposes variables such as `cf.bot_management.score`, `cf.bot_management.verified_bot`, `ja3_hash`, `ja4` for rules. — [Cloudflare Docs: Bot Management variables](https://developers.cloudflare.com/bots/reference/bot-management-variables/); example rule from Cloudflare: `(cf.bot_management.score lt 30 and not cf.bot_management.verified_bot and http.request.uri.path eq "/login")`. — [Cloudflare Docs: Bots custom rules](https://developers.cloudflare.com/bots/additional-configurations/custom-rules/)
- Order of evaluation described by a scraping-tooling vendor: "Cloudflare hashes the ClientHello (JA3, JA4) and compares to known browser fingerprints" before it reads the User-Agent; "The cipher order, the extensions, the GREASE values, the HTTP/2 SETTINGS, all of those tell Cloudflare you are not Chrome". HTTP/2-level surface listed: SETTINGS parameter order, `INITIAL_WINDOW_SIZE`/`MAX_HEADER_LIST_SIZE` values, pseudo-header order (`:method`, `:authority`, `:scheme`, `:path`), regular header order, use of PRIORITY frames. — [webclaw: JA4 fingerprints decoded](https://webclaw.io/blog/tls-fingerprint-vs-browser-cloudflare)
- Akamai's HTTP/2 passive-fingerprint format is `S[;]|WU|P[,]#|PS[,]`: SETTINGS key:value pairs, WINDOW_UPDATE increment, PRIORITY frames, pseudo-header order. Six SETTINGS IDs vary by client (0x1–0x6). Example values: Chrome (Mac/Windows) `1:65536;3:1000;4:6291456|15663105|0`; Firefox `1:65536;4:131072;5:16384|12517377|3:0:0:201,5:0:0:101,7:0:0:1,9:0:7:1,11:0:3:1|m,p,a,s`; curl/Go differ significantly. Stated purpose: detecting "spoofed User-Agent strings" where tools "claim browser identity while implementing different HTTP/2 patterns". — [Akamai white paper (Black Hat EU 2017): Passive Fingerprinting of HTTP/2 Clients](https://blackhat.com/docs/eu-17/materials/eu-17-Shuster-Passive-Fingerprinting-Of-HTTP2-Clients-wp.pdf)
- DataDome-style signal inventory: TLS fingerprint (JA3/JA4), HTTP/2 profile (SETTINGS, WINDOW_UPDATE, pseudo-header order variants m,a,s,p), TCP/IP fingerprint (initial TTL, window size, TCP options, MSS), header order, header-set composition (`Accept`, `accept-encoding`, `accept-language` ordering), User-Agent cross-layer consistency, behavioural request frequency; "The signal that holds up is not 'this fingerprint is bad.' It is 'these fingerprints, and the headers, do not describe the same client.'" IP/ASN reputation is listed as an input. — [crawlex: How DataDome uses HTTP/2 and network fingerprints](https://blog.crawlex.net/blog/datadome-http2-fingerprinting/)
- Bot Fight Mode adds JavaScript Detections (mandatory) and CPU-intensive challenges (see KQ1). — [Cloudflare Docs: Bot Fight Mode](https://developers.cloudflare.com/bots/get-started/bot-fight-mode/)
- What a Worker can and cannot change: Worker code sets request headers via the Fetch API; the runtime overwrites `CF-Connecting-IP` on subrequests ("overwritten later by Cloudflare") — [Cloudflare Community](https://community.cloudflare.com/t/workers-always-pass-cf-connecting-ip-2a063600-103/189944); there is no proxy configuration for fetch() ("This is not possible as workers run on Cloudflare's hardware & network", Dec 5, 2022) — [Cloudflare Community: Is it possible to fetch from workers via proxy?](https://community.cloudflare.com/t/is-it-possible-to-fetch-from-workers-via-proxy/441457); TLS for fetch() is terminated by the runtime, and the only userland escape hatch is raw TCP via `connect()` — [Cloudflare Docs: TCP sockets](https://developers.cloudflare.com/workers/runtime-apis/tcp-sockets/) (see KQ6).
- ScraperAPI's pricing page names the vendors that trigger its surcharge — "Sites behind bot protection like Cloudflare, Datadome, or PerimeterX add 10 credits per request when we bypass them" — which is a useful proxy for which WAFs are hardest to fetch through. — [ScraperAPI pricing](https://www.scraperapi.com/pricing/)

### Inferences
- Controllable from Worker code: `User-Agent`, `Accept`, `Accept-Language`, `Referer`, cookies, `Sec-CH-UA*` strings, request pacing and concurrency, retries. Not controllable: source IP/ASN, TCP/IP stack characteristics, TLS ClientHello (cipher suites, extensions, GREASE, ALPN), HTTP/2 SETTINGS/WINDOW_UPDATE/PRIORITY/pseudo-header order, and whether HTTP/1.1 or HTTP/2 is used.
- The most defensible header strategy for a Worker is therefore *honest* identification (a distinctive product `User-Agent` with a URL, plus browser-typical `Accept`/`Accept-Language`) rather than Chrome impersonation: impersonation cannot be made consistent across layers, so it converts a "generic automation" score into a "spoofing" score. Honest identification will still be blocked by JS-challenge systems (BFM) and by IP-reputation rules, but it avoids the worst outcome and is what the verified-bot/Web Bot Auth ecosystem assumes (KQ3).
- Because JA4 Signals are computed per fingerprint per hour across Cloudflare's network, the shared Workers egress fingerprint accumulates behaviour from every Workers customer — a single well-behaved importer cannot improve its own fingerprint reputation.

### Gaps
- No vendor publishes the numeric weight given to "datacenter ASN" vs "residential" IP, nor how AS13335 specifically is scored; sources confirm ASN reputation is an input but not the scoring.
- No published measurement of the JA3/JA4 or HTTP/2 fingerprint of Cloudflare's Workers egress was found.

## KQ3. Do Cloudflare's AI-crawler defaults (July 2025 →), Pay Per Crawl, Web Bot Auth, and the Verified Bots program help or hurt a small recipe importer?

### Takeaway
They mostly hurt by default and help only if you invest in the verified-bot path: since July 1, 2025 new Cloudflare zones are asked at onboarding whether to allow AI crawlers, and from Sept 15, 2026 the network-wide default blocks bots classified as Training or Agent on ad-monetised pages (most recipe blogs are ad-monetised) while "Unverified bots remain blocked by default". A small app *can* implement Web Bot Auth (Ed25519 HTTP Message Signatures, RFC 9421) and apply through the Cloudflare dashboard, but the policy requires published documentation, honest identity, robots.txt compliance and rate discipline, and no published traffic threshold or SLA was found.

### Cited Findings
- July 1, 2025 press release: "Upon sign-up with Cloudflare, every new domain will now be asked if they want to allow AI crawlers, giving customers the choice upfront to explicitly allow or deny AI crawlers access"; existing customers "can easily check their settings and enable crawling at any time"; Cloudflare is "participating in the development of a new protocol to provide bot owners and AI agent developers with a public, standard way to identify themselves"; Pay Per Crawl launched in beta. — [Cloudflare press release, July 1, 2025](https://www.cloudflare.com/press/press-releases/2025/cloudflare-just-changed-how-ai-crawlers-scrape-the-internet-at-large/); companion blog: "changing the default to block AI crawlers unless they pay creators for their content". — [Cloudflare Blog: Content Independence Day](https://blog.cloudflare.com/content-independence-day-no-ai-crawl-without-compensation/)
- July 1, 2026 blog (defaults effective Sept 15, 2026, for all new domains and for existing customers who have not customised settings by that date): Training bots and Agent bots "Blocked by default on ad-monetized pages"; Search bots allowed; available on all plans including Free; multi-purpose crawlers follow the most restrictive rule; "Unverified bots remain blocked by default"; "Verified" now means "allowable with its relevant category"; ad presence treated as "a signal that a website owner meant for a person to land there"; introduces `Forwarded: for="openai";use="reference"` (RFC 7239) for transitive intent. — [Cloudflare Blog: Your site, your rules: new AI traffic options](https://blog.cloudflare.com/content-independence-day-ai-options/)
- Docs (AI bot blocking, as of Sept 15, 2026): categories Search / Agent / Training; options "Block on all pages", "Block on pages with ads", "Allow"; each option targets "Verified bots classified with that behavior, plus additional unverified bots that fall under these classifications". — [Cloudflare Docs: Block AI bots](https://developers.cloudflare.com/bots/additional-configurations/block-ai-bots/)
- AI Crawl Control: dashboard to "Monitor and control how AI services access your website content"; Pay Per Crawl "private beta"; robots.txt health tracking. — [Cloudflare Docs: AI Crawl Control](https://developers.cloudflare.com/ai-crawl-control/)
- Pay Per Crawl mechanics: publisher returns HTTP 402 with `crawler-price`; crawler pre-declares `crawler-max-price` or accepts with `crawler-exact-price`; success returns 200 with `crawler-charged`; crawlers "must register as verified bots using Web Bot Auth" (Ed25519 keys, JWK directory, `signature-agent`/`signature-input`/`signature` headers per RFC 9421); per-crawler Allow/Charge/Block; "private beta as of July 2025". — [Cloudflare Blog: Introducing pay per crawl](https://blog.cloudflare.com/introducing-pay-per-crawl/)
- Web Bot Auth mechanics: required headers `Signature-Input` (params `tag="web-bot-auth"`, `keyid` = JWK thumbprint, `created`, `expires`, optional `nonce`), `Signature`, `Signature-Agent` (URL of key directory); key directory at `/.well-known/http-message-signatures-directory` over HTTPS serving a JWKS, itself signed; only Ed25519 supported; must sign at least `@authority`; `@query-params` and `@status` unsupported; registration via the dashboard Bot Submission Form. — [Cloudflare Docs: Web Bot Auth](https://developers.cloudflare.com/bots/concepts/bot/verified-bots/web-bot-auth/)
- Verified Bots policy: identity via "cryptographic Web Bot Auth signature", published IP list with stable user-agent, or reverse DNS; must "obey robots.txt and crawl directives, maintain reasonable request rates"; breaches include undisclosed IP blocks, misrepresented purpose, and an "AI Crawler that does not respect the crawl-delay directive in robots.txt"; legacy categories include Search Engine Crawler, AI Crawler, Feed Fetcher, Page Preview, Aggregators, AI Assistant, AI Search, Archiver, Other. — [Cloudflare Docs: Verified bots policy](https://developers.cloudflare.com/bots/concepts/bot/verified-bots/policy/); newer behaviour taxonomy (Search, Agent, Training, Transact, Data Collection, ...) with operational labels Direct vs Intermediary ("Service operated by one entity but driven by multiple end users"). — [Cloudflare Docs: Verified bots](https://developers.cloudflare.com/bots/concepts/bot/verified-bots/)
- Cloudflare's guidance for site owners: "Start by creating an exception for verified bots so they are protected before you deploy any blocking rules." — [Cloudflare Docs: Stop malicious bots](https://developers.cloudflare.com/use-cases/solutions/stop-malicious-bots/)

### Inferences
- A user-triggered recipe importer is closest to Cloudflare's "Intermediary" operational label and the "Agent" behaviour (real-time fetch on a user's behalf) — precisely the category the Sept 2026 default blocks on ad-monetised pages. Unverified, it is "blocked by default" on any Cloudflare zone that has kept the defaults; verified with the right category it becomes "allowable" only where the site owner has not chosen Block for Agents.
- Web Bot Auth is technically cheap to implement in a Worker (an Ed25519 signature over `@authority` plus a static JSON directory on your domain), but it only helps on Cloudflare-protected destinations *after* Cloudflare accepts your submission; it does nothing for Akamai/DataDome/Imperva-protected sites, which have their own allowlisting processes.
- Web Bot Auth requires honest identification, which is incompatible with the "browser User-Agent" approach; you have to pick one strategy.

### Gaps
- No published minimum traffic volume, number of zones, review time, or acceptance criteria for Verified Bot applications was found in the policy or Web Bot Auth pages; anecdotal reports of small bots being accepted/rejected were not located.
- Whether Cloudflare's "additional unverified bots that fall under these classifications" heuristics would classify a Worker with a custom `User-Agent` such as `RecipeImporter/1.0 (+https://...)` as an "Agent" is not documented.
- Pay Per Crawl remained "private beta" in every source found; no pricing observed in the wild.

## KQ4. Cloudflare Browser Rendering (renamed "Browser Run"): bindings, REST endpoints, limits, pricing, and whether it evades blocks

### Takeaway
Browser Run (docs at `developers.cloudflare.com/browser-run/`, formerly Browser Rendering) offers Puppeteer/Playwright bindings plus "Quick Actions" REST endpoints (`/content`, `/screenshot`, `/pdf`, `/markdown`, `/snapshot`, `/accessibilityTree`, `/scrape`, `/json`, `/links`, `/crawl`). Free plan: 10 min of browser time/day, 3 concurrent browsers, 1 Quick Action per 10 s; Paid: 10 h/month included then $0.09/browser-hour, 10 concurrent included then $2/browser, Quick Actions billed by browser time only. It defeats JS-challenge and client-rendered pages but egresses from the same Cloudflare IPs with no rotation, carries `cf-biso-*` identifying headers, and Cloudflare itself says it "is always identified as bot traffic" — so IP/ASN-based blocks and Bot Fight Mode on the destination are not solved.

### Cited Findings
- Product name is now "Browser Run"; limits page last updated Sept 26, 2026. Workers Free: browser time "10 minutes per day", 3 concurrent browsers per account, 1 new browser instance every 20 s, 60 s browser timeout, Quick Actions 1 request every 10 s, `/crawl` 5 jobs/day, 100 pages per crawl. - Cost model for a recipe importer: one `/markdown` Quick Action for a typical recipe page plausibly consumes 5–15 s of browser time (not measured; use `X-Browser-Ms-Used` to calibrate). ## KQ6. Can a Worker use an HTTP/residential proxy for fetch()? What is the realistic pattern?

### Takeaway
No: fetch() in Workers has no proxy configuration and Cloudflare staff/MVPs have said "This is not possible as workers run on Cloudflare's hardware & network." The only in-runtime workaround is raw TCP via `connect()` from `cloudflare:sockets`, and because the runtime's `startTls()` verifies the certificate against the proxy hostname rather than the tunnelled origin, a working CONNECT/SOCKS5 tunnel requires implementing TLS in JavaScript (the `tunnelfetch` library does this, at 36–102 ms CPU per 1 MB and without a security audit). The realistic production pattern is to call a proxy provider's HTTPS API endpoint (Bright Data Web Unlocker, Scrapfly, ScraperAPI, etc.) from the Worker instead of speaking the proxy protocol.

### Cited Findings
- "This is not possible as workers run on Cloudflare's hardware & network." (Dec 5, 2022); a June 12, 2023 reply identifies the motivating use case as "getting data from sites and APIs that have blocked workers IP address ranges". — [Cloudflare Community: Is it possible to fetch from workers via proxy?](https://community.cloudflare.com/t/is-it-possible-to-fetch-from-workers-via-proxy/441457); related threads: [Can I use a proxy in workers](https://community.cloudflare.com/t/can-i-use-a-proxy-in-workers/402833), [Worker fetch will not use the system proxy (workers-sdk#6443)](https://github.com/cloudflare/workers-sdk/issues/6443)
- TCP sockets: `connect()` from `cloudflare:sockets` with `secureTransport` `"off"` (default) | `"on"` | `"starttls"` and a `startTls()` upgrade; "Outbound TCP sockets to Cloudflare IP ranges are blocked"; localhost/private IPs blocked; port 25 blocked; "it is not possible to make an inbound TCP connection to your Worker, for example, by using the CONNECT HTTP method"; each socket counts toward the simultaneous-connection limit; Durable Objects keep sockets alive up to 15 minutes. — [Cloudflare Docs: TCP sockets](https://developers.cloudflare.com/workers/runtime-apis/tcp-sockets/)
- `tunnelfetch`: "A fetch-shaped HTTP client that tunnels HTTPS through HTTP CONNECT / SOCKS5 proxies on Cloudflare Workers — TLS 1.3 and 1.2 implemented in userland, because the runtime cannot verify a tunnelled peer." `startTls()` verifies against the hostname passed to `connect()` (the proxy), and "even with the `expectedServerHostname` option, the verification still fails for tunneled connections". Supports HTTP CONNECT/HTTPS/SOCKS5 with credentials, ALPN h2/h1.1, connection pooling, cookie jar, gzip/deflate; measured 36.3 ms (warm) to 102 ms (cold) CPU per 1 MB body; ≈$1,027/month CPU at 1B requests; no CBC suites, no mTLS, buffers request bodies, no HTTP/3; "This is a new implementation, not a battle-tested one ... It has not had an external security audit." — [GitHub latentharbor/tunnelfetch](https://github.com/latentharbor/tunnelfetch)
- Workers CPU limits that bound this approach: Free 10 ms CPU per request; Paid default 30 s (configurable to 5 min). — [Cloudflare Docs: Workers limits](https://developers.cloudflare.com/workers/platform/limits/)
- Provider API pattern: Bright Data Web Unlocker is an HTTPS API/proxy that returns the page (optionally as markdown) and is explicitly "not made for use on browsers or third party tools". — [Bright Data: Web Unlocker pricing](https://brightdata.com/pricing/web-unlocker)

### Inferences
- Userland-TLS tunnelling is infeasible on the Workers Free plan (10 ms CPU) and marginal on Paid for large pages; its only advantage over calling a provider API is protocol-level control (e.g. bring-your-own residential proxy). For a recipe importer, calling an unlocker's HTTPS endpoint is strictly simpler and lets the *provider's* browser-grade TLS/H2 fingerprint and residential IP do the work.
- Alternatively, run a tiny relay outside Cloudflare (a VPS or a home box) that the Worker calls; this changes the egress ASN but a datacenter VPS ASN is scored much like Cloudflare's, so this only helps against *Cloudflare-specific* blocks (e.g. `2a06:98c0:3600::103` denylists, Bot Fight Mode treating Cloudflare service IPs as bots), not against residential-vs-datacenter scoring.

### Gaps
- No Cloudflare roadmap item for proxy support in fetch() was found.
- The `expectedServerHostname` behaviour claim comes from the tunnelfetch README, not Cloudflare docs.

## KQ7. Client-side alternatives that move the fetch to the user's device

### Takeaway
Established recipe apps avoid the server-side fetch problem by reading the page *inside the user's browser or an in-app browser*: Paprika ships a built-in browser with a "Download" button plus a Safari share extension and a per-account bookmarklet; AnyList ships desktop extensions (Chrome/Safari) and an iOS share-sheet extension; Copy Me That uses a bookmarklet/button. On iOS, Shortcuts' "Run JavaScript on Web Page" gives full DOM access (`document.querySelectorAll`, `completion(result)`) but only from Safari's share sheet; a PWA `share_target` receives only `title`/`text`/`url` (and files), never the page DOM, and is not Baseline.

### Cited Findings
- Paprika iOS: includes a built-in browser to "browse for recipes online, and clip your favorite recipes into Paprika"; "Press the Download button in the lower right corner of the toolbar" and Paprika "attempt[s] to download the recipe from the page"; Share extension saves "directly from Safari" via the "Paprika 3 icon"; manual clipboard tools populate fields when automatic detection fails; "Paprika supports downloading recipes from hundreds of different recipe sites". — [Paprika: iOS user guide](https://www.paprikaapp.com/help/ios/); bookmarklet "download recipes to your Paprika account from any web browser", generated per logged-in account. — [Paprika: Bookmarklet](https://www.paprikaapp.com/bookmarklet/); a Chrome-store listing of the bookmarklet-as-extension exists. — [chrome-stats: Paprika Bookmarklet](https://chrome-stats.com/d/bcenfdemnafogogkmacneifjiknnakop)
- AnyList: desktop browser extensions — "click the AnyList icon in your browser's toolbar while on a recipe page to import the recipe"; fallback "you can manually copy and paste the recipe into AnyList". — [AnyList Help: Import from the web on Mac/PC](https://help.anylist.com/articles/recipe-desktop-extensions/); install pages for [Chrome](https://www.anylist.com/recipes/browser-extensions/chrome) and [Safari](https://www.anylist.com/recipes/browser-extensions/safari); iOS share-sheet extension from Safari and other apps — [AnyList Help: Import from iOS browsers](https://help.anylist.com/articles/recipe-extension/); Android import — [AnyList Help: Android](https://help.anylist.com/articles/feature-overview-recipe-import-android/)
- Copy Me That: "Click to copy any recipe from any website"; "Add the Copy Me That button to your browser or use the app browser. Works on phones, tablets, and computers." — [Copy Me That: Recipe manager](https://www.copymethat.com/features/recipe-manager/); the button is a bookmarklet ("Drag this button to your bookmarks toolbar"; "Go to the webpage and click the button. You'll then find the recipe in 'Recipes.'"), also installable in mobile browsers. — [Copy Me That: Adding the button](https://www.copymethat.com/info/button/); Chrome/Firefox extensions exist — [Chrome Web Store](https://chromewebstore.google.com/detail/copy-me-that/lgjinjcobiflbbnhenlfkcjpeeacklfl?hl=en-US), [Firefox Add-ons](https://addons.mozilla.org/en-US/firefox/addon/cmt/)
- iOS Shortcuts "Run JavaScript on Web Page": runs custom JS against the page DOM (e.g. `document.querySelectorAll()`), returns data via `completion(result)` as any JSON type; input "must be an active Safari web page" and the shortcut must be run "from the share sheet (specifically from Safari, SFSafariViewController or ASWebAuthenticationSession)"; cannot be triggered from other apps; subject to a time limit ("JavaScript Timeout error"); synchronous dialogs (`alert`, `prompt`) fail. — [Apple Support: Run JavaScript on Web Page](https://support.apple.com/en-in/guide/shortcuts/apd218e2187d/ios); usage guide — [Apple Support: Use the Run JavaScript on Web Page action](https://support.apple.com/en-ie/guide/shortcuts/apdb71a01d93/ios)
- PWA `share_target`: receives `title`, `text`, `url`, and `files`; GET with query params or POST `multipart/form-data`; MDN marks it "not Baseline" / "Experimental" and it "does not work in some widely-used browsers". — [MDN: share_target](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Manifest/Reference/share_target)

### Inferences
- Data each channel can capture: browser extension content script → full rendered DOM (including `<script type="application/ld+json">` blocks and content behind logins/paywalls the user has access to), from the user's residential IP with the user's real browser fingerprint — the only channel that defeats every server-side signal in KQ2 simultaneously. Bookmarklet → same DOM access as an extension but blocked by CSP on some sites and inconvenient on mobile. iOS Shortcut (Safari share sheet) → DOM via JS, can POST the JSON-LD or `document.documentElement.outerHTML` to your Worker; Android share intents and PWA `share_target` → URL/title/text only, so the server-side fetch problem returns (they are a UX convenience for *submitting* a URL, not for retrieving content).
- The vendors' fallback instructions ("copy and paste the recipe") indicate that even device-side import is imperfect; a robust app offers URL import (server fetch chain) *and* a paste-HTML/paste-text path *and* an extension/shortcut.
- Cost of the client-side channel to the app operator is ≈$0 per import and it scales with users' own IPs, which is why decade-old recipe apps standardised on it.

### Gaps
- Neither AnyList nor Paprika documents publicly whether their extension posts the DOM or only the URL to their servers; inferred from the "works with any website"/in-app-browser framing and the existence of a Safari extension (which only makes sense if it reads the loaded page).
- No source located for Mela's or Crouton's import mechanics.
- MDN's browser-compatibility table for `share_target` (Chrome Android vs Safari iOS status) was not captured in the fetched content.

## KQ8. Etiquette that reduces blocking (identification, headers, rate limits, caching, robots.txt legal status, backoff)

### Takeaway
robots.txt (RFC 9309) is a voluntary protocol — "not a law, not a contract, and not an enforceable directive" — but ignoring it is treated as evidence of intent in CFAA/copyright/ToS disputes, and Cloudflare's Verified Bots policy makes obeying robots.txt, crawl-delay and "reasonable request rates" a hard requirement for being allowed through by identity rather than by evasion. Concretely for a Worker: send an honest `User-Agent` with a contact URL, browser-typical `Accept`/`Accept-Language`, one in-flight request per host, cache successful fetches, and honour `Retry-After` on 429/503 (Cloudflare's own rate-limit responses include it).

### Cited Findings
- "robots.txt is not legally binding. It is not a law, not a contract, and not an enforceable directive." It is formalised in RFC 9309 (IETF, Sept 2022) as voluntary and "relies entirely on the good faith of the crawler to read it and comply"; ignoring it can still create exposure via computer-fraud statutes (CFAA), copyright, privacy law and ToS/contract claims, functioning as "evidence of intent rather than a legal instrument in its own right". — [ByteTunnels: Is robots.txt legally binding?](https://bytetunnels.com/posts/is-robots-txt-legally-binding-scraping-law-explained/)
- Cloudflare Verified Bots policy requires bots to "obey robots.txt and crawl directives, maintain reasonable request rates", and lists an "AI Crawler that does not respect the crawl-delay directive in robots.txt" as a policy breach. — [Cloudflare Docs: Verified bots policy](https://developers.cloudflare.com/bots/concepts/bot/verified-bots/policy/)
- Cloudflare's AI Crawl Control tracks "which crawlers are violating your directives" in robots.txt (i.e. site owners now see violations in a dashboard). — [Cloudflare Docs: AI Crawl Control](https://developers.cloudflare.com/ai-crawl-control/)
- Cloudflare's own rate limiting on Browser Run: "Rate limit responses include 'Retry-After' headers for graceful handling". — [Cloudflare Docs: Browser Run limits](https://developers.cloudflare.com/browser-run/limits/)
- Bright Data, Scrapfly, ScrapingBee and Zyte all bill only successful responses and Scrapfly disables that protection above a 30% hourly failure rate — a commercial incentive structure that implicitly penalises hammering failing hosts. — [Scrapfly billing](https://scrapfly.io/docs/scrape-api/billing); [ScrapingBee pricing](https://www.scrapingbee.com/pricing/); [Zyte pricing](https://docs.zyte.com/zyte-api/pricing.html); [Bright Data](https://brightdata.com/pricing/web-unlocker)
- Firecrawl defaults to a 2-day cache (`maxAge` 172,800,000 ms) — [Firecrawl API](https://docs.firecrawl.dev/api-reference/endpoint/scrape); Scrapfly charges 1 credit for a cache hit — [Scrapfly billing](https://scrapfly.io/docs/scrape-api/billing); Workers fetch supports `cache: 'no-store'|'no-cache'` only. — [Cloudflare Docs: Fetch](https://developers.cloudflare.com/workers/runtime-apis/fetch/)
- Workers' default subrequest sends no `User-Agent` (see KQ1) — [GitHub miniflare#139](https://github.com/cloudflare/miniflare/issues/139) — and some APIs (GitHub) reject UA-less requests outright. — [GitHub next-auth#6741](https://github.com/nextauthjs/next-auth/issues/6741)

### Inferences
- A user-initiated single-page import is not "crawling" in the robots.txt sense (RFC 9309 addresses automated crawlers), but a Worker fetching on a user's click is still an automated client; honouring a `Disallow` for your UA token is cheap and is what the verified-bot path requires anyway. Whether to honour it for one-off user-requested fetches is a product/legal decision, not a technical one.
- Retry policy that fits Workers: treat 429/503 with `Retry-After` as authoritative; without it, exponential backoff with jitter capped at a few attempts, then fall through the chain (direct → reader API → unlocker → ask the user to use the extension/shortcut). Because egress IP is shared (KQ1), a 429 from a host may persist regardless of your own backoff — persistence of 429 is a signal to switch channel, not to retry.
- Per-host concurrency of 1 and a small in-app cache (Workers KV/R2/Cache API keyed by canonical URL) reduce both blocking and cost across all paid providers.

### Gaps
- The hiQ v. LinkedIn (9th Cir.) and Ziff Davis v. OpenAI robots.txt analyses surfaced in search but their pages were not successfully fetched (Harvard tagteam returned 503), so no holdings are cited here.
- No primary source was fetched on EU DSM Directive Art. 4 machine-readable TDM opt-outs; not relied upon.

## KQ9. Workers platform limits relevant to fetching pages (subrequests, CPU, memory, body sizes, timeouts, streaming)

### Takeaway
Per the limits page (last updated Sept 5, 2026): Free = 50 subrequests/request, 10 ms CPU, 100,000 requests/day; Paid = 10,000 subrequests/request, 30 s CPU by default (configurable to 5 min), no daily cap; both = 128 MB memory, 6 simultaneous connections in the "waiting for headers" phase, no wall-clock duration limit on HTTP handlers, and no enforced response-body size limit. In practice fetch() to a slow origin fails around 90–125 s (community reports of 524s; Cloudflare's proxy read timeout is documented at 125 s), and `HTMLRewriter` lets you stream-parse large pages without buffering them into the 128 MB heap.

### Cited Findings
- Limits table (Free vs Paid): subrequests "50/request" vs "10,000/request (up to 10M)"; simultaneous connections 6 (both); CPU time (HTTP) "10 ms" vs "5 min (default: 30 seconds)"; memory "128 MB" (both); daily requests "100,000/day" vs no limit; Worker size 64 MiB; duration (HTTP) no limit; duration (Cron/Queue/Alarm) 15 min; request body size per Cloudflare plan (100 MB–5 GB); "each subrequest in a redirect chain counts against this limit"; response body "no enforced limit" (cache limits 512 MB–5 GB apply separately); "a Worker can have many connections open simultaneously, as long as no more than six are in the initial 'waiting for headers' phase." — [Cloudflare Docs: Workers limits](https://developers.cloudflare.com/workers/platform/limits/)
- Community reports: fetch() subrequests timing out at ~90 s (Jan 29, 2025), a 504 at ~60 s under Wrangler (Mar 14, 2025), and a 524 at ~90 s (Mar 18, 2026), versus the doc statement "There is no set limit on the amount of real time a Worker may use." — [Cloudflare Community: Worker subrequest fetch 90 sec timeout](https://community.cloudflare.com/t/worker-subrequest-fetch-90-sec-timeout/763362)
- Error 524 arises when "the origin did not provide an HTTP response before the default 125 seconds Proxy Read Timeout"; Enterprise can raise it to 6,000 s. — [Cloudflare Docs: Error 524](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-5xx-errors/error-524); a Worker can surface a 522 from the origin connection instead of running its own error handling. — [Cloudflare Community: Worker returns 522](https://community.cloudflare.com/t/cloudflare-worker-returns-522-origin-connection-timeout-instead-of-executing-error-handling-code/204961)
- `HTMLRewriter` performs "zero-copy streaming parsing": `.on(selector, handler)`, `.onDocument(handler)`, `.transform(response)`; text nodes may arrive in multiple chunks; handlers may be async; if a handler throws, "parsing is immediately halted" and an already-streaming response is truncated. — [Cloudflare Docs: HTMLRewriter](https://developers.cloudflare.com/workers/runtime-apis/html-rewriter/)
- Fetch: brotli/gzip requested automatically; preserving `Content-Encoding` passes encoded bytes through without recompression. — [Cloudflare Docs: Fetch](https://developers.cloudflare.com/workers/runtime-apis/fetch/)
- Browser Run per-request browser time is exposed via `X-Browser-Ms-Used`. — [Cloudflare Docs: Quick Actions](https://developers.cloudflare.com/browser-run/quick-actions/)

### Inferences
- The Free plan's 10 ms CPU budget is the binding constraint for *processing* fetched HTML in-Worker (HTML→markdown conversion, JSON-LD parsing of a 500 KB page can exceed it); the fetch itself is I/O and does not consume CPU while waiting. This favours delegating extraction to a reader API/Browser Run `/markdown` or to Gemini rather than converting in the Worker — or upgrading to Paid ($5/month) for 30 s CPU.
- Use `AbortSignal.timeout(…)` on fetch() well under 90 s (e.g. 15–20 s for a recipe page) so the importer fails fast into its fallback chain instead of hitting the proxy read timeout; use `HTMLRewriter` to extract only `<script type="application/ld+json">`, `<title>`, and main-content elements from the stream rather than `await response.text()` on ad-heavy pages.
- Redirect chains count against subrequest limits; recipe URLs frequently redirect (AMP, `www`, trailing-slash), so budget 2–3 subrequests per import plus provider calls.

### Gaps
- The fetched limits page reports 10,000 subrequests per request on Paid; older documentation stated 1,000. Re-verify before relying on it.
- No official documentation ties the observed ~90–125 s fetch() failure specifically to Workers subrequests (the 524 doc describes the general proxy read timeout).
