# Internet Archive / Wayback Machine as a programmatic fallback: endpoints, 429 behavior, limits, Cloudflare Workers interaction, suitability for recipe sites, and alternatives (state as of 2026-09-28)

Method note: all archive.org / web.archive.org documentation and forum pages were read through the WebFetch tool. The sandbox's egress proxy refused direct `curl` CONNECTs to `archive.org`, `blog.archive.org`, and every recipe-site host tried, so **no live empirical probing of 429 headers/bodies or of recipe-site `robots.txt` files was possible in this session** (see Gaps). Anything below marked "(anecdotal)" comes from user reports in GitHub issues or archive.org forums, not from Internet Archive (IA) staff.

## Key Question 1 — Which Wayback Machine access methods exist, and what does each one accept?

### Takeaway
There are four distinct programmatic surfaces: the Availability JSON API (`archive.org/wayback/available`), the CDX Server API (`web.archive.org/cdx/search/cdx`), direct replay fetches (`web.archive.org/web/{timestamp}{modifier}/{url}`, where the `id_` modifier returns the original unrewritten bytes), and Save Page Now 2 (`POST web.archive.org/save`, S3-style `Authorization: LOW key:secret`). Only SPN2 is documented with authentication and explicit per-user quotas; the three read surfaces have no published rate limits at all.

### Cited Findings

**Availability API**
- Endpoint `http://archive.org/wayback/available?url=example.com`; optional `timestamp` (1–14 digits, `YYYYMMDDhhmmss`) and `callback` (JSONP). Response when found: `{"archived_snapshots":{"closest":{"available":true,"url":"http://web.archive.org/web/20130919044612/http://example.com/","timestamp":"20130919044612","status":"200"}}}`; when nothing is archived: `{"archived_snapshots":{}}`. The page carries a "last updated September 24, 2013" note and states no rate limits or usage policy. It points to the Memento protocol and the CDX Server API for advanced querying — [archive.org/help/wayback_api.php](https://archive.org/help/wayback_api.php)
- The response includes a `status` field (HTTP status of the capture), so a "closest" snapshot can be a non-200 capture — [archive.org/help/wayback_api.php](https://archive.org/help/wayback_api.php)

**CDX Server API**
- Deployment endpoint `http://web.archive.org/cdx/search/cdx`; `url` is the only required parameter (URL-encode query strings). `matchType` = `exact` (default) | `prefix` | `host` | `domain`; a trailing `*` implies prefix, a leading `*.` implies domain — [internetarchive/wayback CDX README](https://github.com/internetarchive/wayback/blob/master/wayback-cdx-server/README.md)
- Filtering/selection: `from`/`to` (`yyyyMMddhhmmss`, inclusive), `filter` (regex on a field, `!` prefix inverts, e.g. `filter=statuscode:200`), `collapse` (dedupe adjacent rows on a field or field prefix, e.g. `collapse=timestamp:10`), `fl` (field list), `limit` (positive N = first N; **negative −N = last N**), `offset`, `fastLatest=true` ("returns latest results faster for exact matches"), `output=json`, `gzip=false` (gzip is on by default) — [CDX README](https://github.com/internetarchive/wayback/blob/master/wayback-cdx-server/README.md)
- Resumption/pagination: `showResumeKey`/`resumeKey`; `page`/`pageSize`/`showNumPages`/`showPagedIndex` (pagination only works against the secondary "zipnum" index); `showDupeCount`, `showSkipCount`, `lastSkipTimestamp` — [CDX README](https://github.com/internetarchive/wayback/blob/master/wayback-cdx-server/README.md)
- Default output columns: `urlkey timestamp original mimetype statuscode digest length`. Default absolute maximum of 150,000 records per query. Restricted URLs/fields are gated by a `cdx-auth-token` cookie holding API keys ("currently two restrictions/permission types are supported"). **No rate-limit specification appears in the README** — [CDX README](https://github.com/internetarchive/wayback/blob/master/wayback-cdx-server/README.md)

**Direct replay fetch and the raw modifiers**
- URL shape `web.archive.org/web/{timestamp}id_/{url}`. IA-forum explanation (post by user tutacat, 2025-12-29): with `id_` "you are requesting the *original* document as retrieved from the website … any and all links or references stay unchanged, the document is exactly the same as if you requested the page from the original server at that time"; caveat: "original links are for the live web … anything that is changed or dead will not work". `if_` "formats content for iframes" (links rewritten to archive URLs but toolbar/header stripped). Other modifiers listed without detail: `ij_`, `oe_`, `fw_`, `cs_`, `js_`, `im_`. `id_` and `if_` "strip the toolbar" — [archive.org forum: FAQ On "id_" Wayback Toolbar Removal](https://archive.org/post/1008502/faq-on-id_-wayback-toolbar-removal)
- The same modifier vocabulary in pywb (the open-source replay engine that shares conventions with Wayback): `id_` = identity, "no content rewriting is performed on the response, and the original, un-rewritten content is returned", though some original HTTP headers are re-emitted under a prefixed name; `mp_` = main-page replay (HTML); `js_`/`cs_` = hints to treat the resource as JavaScript/CSS when content-type is ambiguous; `im_`, `oe_`, `if_`, `fr_` = legacy hints (images, objects/embeds, iframes, frames), treated essentially like `mp_`. pywb's docs do not explicitly claim parity with IA's implementation — [pywb rewriter docs](https://pywb.readthedocs.io/en/latest/manual/rewriter.html)

**Save Page Now 2 (SPN2)** — from the public API doc (author Vangelis Banos; doc "Updated: 2026-07-22"), as extracted by the fetch tool (verbatim text of the Google Doc could not be captured; treat exact numbers as needing re-check against the doc):
- Capture: `https://web.archive.org/save` (POST or GET). Job status: `https://web.archive.org/save/status/{job_id}` (GET or POST). User status: `http://web.archive.org/save/status/user`. System status: `http://web.archive.org/save/status/system` — [SPN2 Public API doc](https://docs.google.com/document/d/1Nsv52MvSjbLb2PCpHlat0gkzw0EvtSgpKHu4mk0MnrA/edit)
- Auth: header `Authorization: LOW myaccesskey:mysecret` (S3-style IA keys), or cookies `logged-in-sig` + `logged-in-user` — [SPN2 doc](https://docs.google.com/document/d/1Nsv52MvSjbLb2PCpHlat0gkzw0EvtSgpKHu4mk0MnrA/edit)
- POST options: `capture_all=1` (also archive 4xx/5xx pages), `capture_outlinks=1`, `capture_screenshot=1`, `delay_wb_availability=1` (delay availability ~12 h), `force_get=1`, `skip_first_archive=1`, `if_not_archived_within=<timedelta>` (e.g. `3d 5h 20m`), `outlinks_availability=1`, `email_result=1`, `js_behavior_timeout=<N>` (default 5 s, max 30), `capture_cookie=`, `use_user_agent=`, `target_username`/`target_password`. "Anything other than '1' or 'on' is considered to be 'off'" — [SPN2 doc](https://docs.google.com/document/d/1Nsv52MvSjbLb2PCpHlat0gkzw0EvtSgpKHu4mk0MnrA/edit)
- Status responses: `"status":"success"` with `job_id`, `original_url`, `timestamp` (YYYYMMDDHHMMSS), `duration_sec`, `resources[]` (max 500), `outlinks{}`, `screenshot`; `"status":"pending"` with `job_id`, `resources[]`; `"status":"error"` with `exception`, `status_ext`, `message`, `job_id`, `resources[]`. Status results are retained only ~1 hour — [SPN2 doc](https://docs.google.com/document/d/1Nsv52MvSjbLb2PCpHlat0gkzw0EvtSgpKHu4mk0MnrA/edit)
- Documented caps (per the doc as extracted): captures/min 7 authenticated vs 3 anonymous; captures/day 30,000 authenticated vs 200 anonymous; 5 captures/day per URL; max concurrent sessions per user (user-specific); max capture time 50 s, overall 2 min; max 3 redirects; 2 GB max resource; ≤100 outlinks captured, ≤500 returned; daily bandwidth 5 GB authenticated / 2 GB anonymous; 100 GB/day per target host; 10 s network timeout; "artificial delay for >20 concurrent captures on same host: concurrent_number/5 seconds"; "delay after HTTP 429: 10–20 seconds" (this line almost certainly describes SPN2's own crawler backing off when the *target* site returns 429, not client guidance); ≤10 emails/user/day; outlink extraction timeout 30 s; overall capture timeout incl. outlinks 90 s — [SPN2 doc](https://docs.google.com/document/d/1Nsv52MvSjbLb2PCpHlat0gkzw0EvtSgpKHu4mk0MnrA/edit)
- `status_ext` error vocabulary includes: `error:too-many-requests` (HTTP 429), `error:user-session-limit`, `error:too-many-daily-captures`, `error:blocked-client-ip`, `error:blocked` (HTTP 999), `error:blocked-url`, `error:max-daily-bandwidth`, `error:max-daily-bandwidth-from-ip`, `error:max-daily-bandwidth-host`, `error:bandwidth-limit-exceeded` (509), `error:no-access` (403), `error:proxy-error`, `error:cannot-fetch`, `error:browsing-timeout`, `error:no-browsers-available`, `error:soft-time-limit-exceeded`, `error:job-failed`, `error:celery`, `error:service-unavailable` (503), `error:gateway-timeout` (504), `error:bad-gateway` (502), `error:invalid-url-syntax`, `error:invalid-host-resolution`, `error:too-many-redirects`, `error:filesize-limit`, `error:read-timeout`, `error:protocol-error`, `error:unauthorized`/`error:bad-request` (401), `error:method-not-allowed` (405), `error:not-found` (404), `error:not-implemented` (501), `error:http-version-not-supported` (505), `error:network-authentication-required` (511) — [SPN2 doc](https://docs.google.com/document/d/1Nsv52MvSjbLb2PCpHlat0gkzw0EvtSgpKHu4mk0MnrA/edit)
- SPN maintains a service block list ("Sorry. This URL is in the Save Page Now service block list and cannot be captured.") and a "limitations" list ("Sorry. We're currently facing some limitations when it comes to archiving this site.") — listed examples include Instagram, Twitter/X, ad/tracking endpoints, and `*/wp-admin/*` — [Archiveteam wiki: Save Page Now](https://wiki.archiveteam.org/index.php/Internet_Archive/Save_Page_Now)
- Third-party client libraries exist that encode these patterns: e.g. `spn-client` (Python, "process-wide rate pacing with a circuit breaker, dual-mode anonymous/S3-authenticated submission") — [MHammett/spn-client](https://github.com/MHammett/spn-client); `spn2` Go client — [RaghavSood/spn2](https://github.com/RaghavSood/spn2); edgi `wayback` (Python) for CDX/memento — [wayback docs](https://wayback.readthedocs.io/en/stable/usage.html)

### Inferences
- The Availability API is the cheapest single-lookup primitive (one small JSON), but because `closest` can be a 3xx/4xx capture, callers must check `status == "200"` and the `timestamp` before fetching; the CDX API with `filter=statuscode:200&filter=mimetype:text/html&limit=-1&fastLatest=true` gives the same answer with more control at the cost of hitting the endpoint IA staff say is capped at ~60/min (see KQ2).
- The `archive.org/wayback/available` host differs from `web.archive.org` (CDX, replay, SPN2); they may sit behind different rate-limit counters, but no source confirms this.
- For a recipe importer, the useful fetch is `https://web.archive.org/web/{timestamp}id_/{url}` — it returns the page bytes as originally served, so embedded schema.org JSON-LD and `<img src>` values are the *original* (live-web) URLs rather than `web.archive.org/web/...` rewritten ones. Without `id_`, all URLs inside the HTML (including JSON-LD image URLs) are rewritten to archive URLs and a toolbar is injected.

### Gaps
- IA's official current API index page (archive.org/developers) and any "2025–2026 Wayback Machine APIs" documentation could not be located/fetched in this session; the Availability API page still carries a 2013 date.
- The exact original-header prefix IA uses on `id_` responses (commonly reported as `x-archive-orig-*`) was not verified from a primary source here.

## Key Question 2 — How is each surface rate-limited, what does a 429 look like, and how should a client back off?

### Takeaway
IA staff have stated (via the #wayback-researchers Slack, quoted in the edgi `wayback` issue tracker) that CDX requests are limited to an average of 60/min per IP, that 429s are sent above that, that ignoring 429s for more than a minute triggers a 1-hour firewall block on the IP, and that repeat offenses double the block. SPN captures have separately documented per-minute/per-day caps. No source documents a `Retry-After` header, and since 15 Sept 2026 IA runs broader anti-automation protections with a rewritten 429 page and acknowledged false positives.

### Cited Findings
- IA staff statement relayed by the edgi `wayback` maintainers: CDX requests "are limited to an average of 60/min. Over that and we start sending 429s." If 429s are ignored for more than one minute, the requesting IP gets a **1-hour firewall block**, and subsequent violations **double the block duration** each time. The issue reporter fixed their blocks by lowering `search_calls_per_second` to 0.5 (noting 1.0 might suffice). No date for when the limit was introduced — [edgi-govdata-archiving/wayback issue #137](https://github.com/edgi-govdata-archiving/wayback/issues/137)
- The edgi `wayback` library's current defaults: `search_calls_per_second` = 0.4 for the CDX API and `memento_calls_per_second` = 8 for replay/memento fetches; it raises `RateLimitError` on a 429 with an optional `retry_after` attribute ("Recommended number of seconds to wait before retrying") **if provided by the server**; default `retries=6`, `backoff=2` s. "In general, this package's built-in limits should help you avoid ever hitting this, but if you are running multiple processes in parallel, you could go overboard." — [wayback docs (stable)](https://wayback.readthedocs.io/en/stable/usage.html)
- Older library defaults quoted in the same issue: 0.8 calls/s for `/cdx` and 1.33 calls/s for `/web/timemap` — [edgi wayback issue #137](https://github.com/edgi-govdata-archiving/wayback/issues/137)
- Note that replayed captures of *other sites'* 429 responses also come back as HTTP 429 from web.archive.org (with a `memento-datetime` header); a client must check for `memento-datetime` before treating a 429 as IA's own throttle — [edgi wayback issue #158](https://github.com/edgi-govdata-archiving/wayback/issues/158)
- Historical 429 body text (2019, user-quoted): "429 Too Many Requests – You have sent too many requests in a given amount of time." Reported even after 15+ minutes without requests. Later posts in the same thread: tk1961 (2026-07-18) "that error occurs because of an IP address block"; further reports 2025-06 through 2026-09-02 (Sekou Toons, Purple-Onion, Mmm891 2025-12-12 "been going on since 2019"). No IA staff reply in-thread — [archive.org forum: Error "429 Too Many Requests" despite no requests](https://archive.org/post/1103558/error-429-too-many-requests-despite-no-requests)
- A parallel forum thread ("Reason for new strict Wayback data cap?") reports the cap tightening over 2019–2020 (from none to "just 5 pages" per the poster, Oct 2019; another user from 2020-04-14) and a 2026-09-01 report of being unable to load even a single page; the block page tells users to "Please email info@archive.org if you have questions about why are you being blocked" — [archive.org forum post 1103806](https://archive.org/post/1103806/reason-for-new-strict-wayback-data-cap-http-429-too-many-requests)
- Official, 2026-09-15 (Mark Graham, Director of the Wayback Machine): IA implemented protections against "waves of high-volume automated traffic"; "rewrote the message you see when a request is blocked with a 429 error — the HTTP code that means 'too many requests'"; "Those protections sometimes catch real people by mistake"; users blocked in error should email `info@archive.org` with "your operating system, browser, and IP address". The post gives **no numeric limits, no auth/API-key policy, no timeframe** — [blog.archive.org: An Update on Wayback Machine Access](https://blog.archive.org/2026/09/15/an-update-on-wayback-machine-access/); secondary coverage: [Digital Information World, 2026-09](https://www.digitalinformationworld.com/2026/09/internet-archives-wayback-machine.html), [Aroged, 2026-09-16](https://www.aroged.com/2026/09/16/web-archive-comes-under-bot-attack-and-starts-blocking-regular-users/) (quotes Graham: "We're doing a better job of distinguishing between bots and people who rely on the Wayback…")
- Replay (`/web/…`) fetch concurrency (anecdotal, wayback-machine-downloader users, undated): 429s appear at concurrency "above 4"; `-c 3` or lower avoided them; one user never hit limits at `-c 4`; after a 429 "any subsequent attempt at loading the page automatically fails to connect"; a fork added automatic sleep on 429 — [hartator/wayback-machine-downloader issue #160](https://github.com/hartator/wayback-machine-downloader/issues/160)
- Save Page Now limit history (anecdotal, 2019): ~20 req/min mid-2019 → 5 req/min Oct 2019; an IA details page from Nov 2019 was quoted as "15 requests/minute, with a 5 minute block for the IP address exceeding this"; users saw 429 "after just a dozen or so requests" at concurrency 5 and even at concurrency 1; sleeping 5–13 s between requests worked — [buren/wayback_archiver issue #32](https://github.com/buren/wayback_archiver/issues/32)
- Other library trackers with the same symptom: waybackpy ("Raise Error if response is 429") — [akamhy/waybackpy issue #131](https://github.com/akamhy/waybackpy/issues/131); wayback-machine-scraper ("Error 429 + Scraper gives up") — [sangaline/wayback-machine-scraper issue #19](https://github.com/sangaline/wayback-machine-scraper/issues/19); IA's own browser extension shows a misleading "Please try again in ~10 min" when the *target* returns 429 — [internetarchive/wayback-machine-webextension issue #1110](https://github.com/internetarchive/wayback-machine-webextension/issues/1110)
- A 2026 design proposal (not measured data) for a GitHub-Actions-hosted archiver claims unauthenticated `/save/{url}` writes "face strict per-IP connection limits (~5–15 requests/hour)" on shared runner IPs, and proposes Availability pre-checks, a 3 s minimum inter-request delay, 2 retries with 2 s/4 s backoff, and a 15-minute circuit breaker after any 429; it did **not** confirm whether `Authorization: LOW` avoided 429s — [KoshiirRa/midgley issue #491](https://github.com/KoshiirRa/midgley/issues/491)

### Inferences
- Limits are **per source IP** for the read surfaces (CDX, replay, Availability): every source that names a basis names the IP (IA Slack quote; forum posts; block page asking for the user's IP address), and the escalation is a firewall block on the IP, which explains "429 despite no requests" — the IP is inside a 1-hour (or doubled) block window, not over a sliding request budget.
- Detecting IA's own throttle: HTTP 429 **without** a `memento-datetime` header (a 429 *with* that header is a replayed capture of the target site's 429). Treat any 429 as "stop for at least 60 s, then probe once"; if the probe also 429s, assume a firewall block and stop for ≥1 h. Because blocks double on repeat, aggressive retry loops are the worst possible client behavior.
- Because no source confirms a `Retry-After` header, code should honor it when present but must not depend on it; the edgi library's "if provided by the server" wording suggests it is often absent.
- Practical per-process budget consistent with the sources: ≤1 CDX request/s (edgi default 0.4/s), replay fetch concurrency ≤3 per IP, a single Availability call before any heavier call, and cache every CDX/Availability result (snapshots do not change retroactively).

### Gaps
- No primary source gives the **current (Sept 2026) 429 body text** or confirms `Retry-After` / any `x-archive-*` diagnostic headers; direct probing was blocked by the sandbox proxy.
- No IA statement exists on limits for the Availability API or for `/web/` replay fetches; the 60/min figure is explicitly about CDX.
- Whether the 2026-09 protections are Cloudflare-style JS challenges or IP-reputation blocks is undocumented; the blog post only says "protections".

## Key Question 3 — Does authentication or a contact User-Agent raise limits? Does anything let archive.org rate-limit per account instead of per IP?

### Takeaway
Only SPN2 is per-account: its quotas are explicitly keyed to the authenticated user (authenticated users get higher per-minute/per-day caps and a `/save/status/user` quota endpoint). For the read APIs there is no documented API key, no documented User-Agent policy, and no evidence that identifying yourself changes the per-IP limit — the only documented remedy is emailing info@archive.org.

### Cited Findings
- SPN2 caps differ by auth state (authenticated vs anonymous captures per minute and per day; daily bandwidth 5 GB vs 2 GB) and per-IP errors exist separately (`error:blocked-client-ip`, `error:max-daily-bandwidth-from-ip`), i.e. SPN2 accounts for both user and IP — [SPN2 doc](https://docs.google.com/document/d/1Nsv52MvSjbLb2PCpHlat0gkzw0EvtSgpKHu4mk0MnrA/edit)
- CDX auth exists only as a `cdx-auth-token` cookie with API keys for *restricted* URLs/fields (an access-control mechanism, not a rate-limit tier) — [CDX README](https://github.com/internetarchive/wayback/blob/master/wayback-cdx-server/README.md)
- The Availability API docs mention no authentication or usage policy — [archive.org/help/wayback_api.php](https://archive.org/help/wayback_api.php)
- The 2026-09-15 blog post's only remedy for wrongly blocked users is to email `info@archive.org` with OS, browser and IP; it mentions no allow-list, API key, or identification header — [blog.archive.org 2026-09-15](https://blog.archive.org/2026/09/15/an-update-on-wayback-machine-access/)
- IA staff's Slack statement about the 60/min CDX cap describes the limit and the IP firewall block without any account-based exception — [edgi wayback issue #137](https://github.com/edgi-govdata-archiving/wayback/issues/137)
- Analogy from another per-IP-limited service: in the ntfy.sh case, even after creating and verifying an account, the rate-limit basis stayed `"basis": "ip"` on the free tier, so authentication did not decouple the Worker from the shared egress IP's quota — [binwiederhier/ntfy issue #1963](https://github.com/binwiederhier/ntfy/issues/1963)

### Inferences
- For a recipe importer, the only way to get identity-based accounting at IA is to use SPN2 with `Authorization: LOW` — but SPN2 is a *write* (capture) operation with its own per-minute cap (single digits/min per the doc) and a 200/day anonymous ceiling, and a capture takes seconds to minutes to complete; it is a poor primitive for a synchronous "fallback fetch" and inappropriate for pages the live site is already refusing to serve (SPN2 will typically hit the same block).
- Setting a descriptive `User-Agent` with a contact URL/email is good practice and costs nothing, but there is no evidence it changes IA's rate limiting.

### Gaps
- No IA documentation on whether logged-in (cookie) sessions get higher read limits; forum users speculate but nothing official was found.
- No public statement on an "allow-list" process beyond the info@archive.org email, or on whether IA honors `From:` headers.

## Key Question 4 — Why is a Cloudflare Worker especially likely to hit archive.org's limit?

### Takeaway
Workers' outbound `fetch()` calls leave from Cloudflare's shared IP pool that every Workers tenant uses; there is no per-account or static egress IP outside Enterprise contracts. Because archive.org throttles and firewall-blocks per source IP, the Worker inherits whatever budget every other tenant on that egress IP has already consumed — and the 1-hour-doubling block can be tripped by neighbors. The `CF-Worker` header lets archive.org tell that a request came from a Worker (and from which zone), but there is no evidence archive.org uses it for anything.

### Cited Findings
- Cloudflare docs: "The `CF-Worker` request header is added to an edge Worker subrequest that identifies the host that spawned the subrequest"; its value is the zone that owns the Worker (e.g. `CF-Worker: example.com`); "`CF-Worker` is added to all Worker subrequests sent via `fetch()`" — [Cloudflare Fundamentals: HTTP request headers](https://developers.cloudflare.com/fundamentals/reference/http-request-headers/)
- Cloudflare community moderator (sjr, 2025-05-05) on a request for dedicated/static egress IPs for Workers: "Sharing IP addresses is normal across hosting and CDNs"; "Any dedicated IP addressing requires an Enterprise plan. You will need to contact Cloudflare Sales for pricing." No product in the thread offers dedicated egress for Workers' outbound `fetch()` — [Cloudflare Community: Dedicated IP / Static IP / Fixed egress IP for workers](https://community.cloudflare.com/t/dedicated-ip-static-ip-fixed-egress-ip-for-workers/795286)
- Same answer in an earlier thread (2024-10-04): static IP for Workers' external requests "Requires an Enterprise plan with Aegis…" — [Cloudflare Community: Static IP for external requests from Cloudflare Workers](https://community.cloudflare.com/t/static-ip-for-external-requests-from-cloudflare-workers/720952); a 2025 thread on fixed egress IPs (Magic NAT, Aegis) ended unresolved with no staff answer — [Cloudflare Community 757906](https://community.cloudflare.com/t/fixed-egress-ip-addresses-for-cloudflare-workers/757906)
- Cloudflare's own "known issues" page for Workers only documents that Workers cannot fetch raw IP addresses; it says nothing about egress IP sharing — [Workers known issues](https://developers.cloudflare.com/workers/platform/known-issues/)
- Empirical tenant-collision case #1: ntfy.sh free tier (250 msgs/day, "basis": "ip") was exhausted for a Worker that sent only 1–2 messages/day because "Cloudflare Workers' shared egress IPs routinely exhaust the ntfy.sh free-tier daily quota for unrelated users"; the response was "429 Too Many Requests … daily message quota reached"; authentication did not help — [binwiederhier/ntfy issue #1963](https://github.com/binwiederhier/ntfy/issues/1963)
- Empirical tenant-collision case #2 (2026-09-24): a brand-new isolated Cloudflare Worker/account received HTTP 429 from the adsb.lol API "on its first identified request", even with a detailed contact User-Agent and `From` header; the maintainer was asked for allow-listing or API keys — [adsblol/website issue #272](https://github.com/adsblol/website/issues/272)
- A 2020 Workers thread: a third party (Azure Cosmos) rate-limited "your 'IP' (Cloudflare) at an early load balancer"; resolution required Cloudflare relaxing an internal limit for that customer — [Cloudflare Community 188479](https://community.cloudflare.com/t/outbound-traffic-receives-response-with-429-status-code/188479)
- Related: a Worker's own *inbound* 429s can also come from Cloudflare's Workers abuse-protection or edge firewall, not the origin — [Cloudflare Community 413447](https://community.cloudflare.com/t/workers-abuse-protection-limit-throws-http-429-status/413447), [856364](https://community.cloudflare.com/t/workers-blocked-by-edge-firewall-429-too-many-requests-before-runtime-execution/856364) — distinguish these from archive.org's 429 by checking the response body/`server` header.
- The corresponding archive.org-side symptom (users blocked with zero personal request volume, attributed to IP blocks) is exactly what shared/VPN/datacenter IPs produce — [archive.org forum post 1103558](https://archive.org/post/1103558/error-429-too-many-requests-despite-no-requests)

### Inferences
- Mechanism chain: (1) archive.org counts requests per source IP and escalates to timed firewall blocks; (2) a Worker's source IP is one of Cloudflare's shared egress addresses used by many unrelated Workers scripts; (3) any other tenant hammering web.archive.org from that IP consumes the budget and can put the IP into a 1 h → 2 h → 4 h block; (4) the recipe app's first request lands inside that window and sees 429 "despite no requests". This matches the ntfy/adsb.lol observations of first-request 429s from fresh Workers.
- Adding identity (`User-Agent` with contact, `From:`) will not help because archive.org has no documented account-based accounting for reads; the `CF-Worker` header actually makes Worker traffic *more* identifiable, which could cut either way if IA ever decides to treat Workers traffic as a class.
- Escape hatches are architectural: proxy archive.org calls through a host with its own dedicated IP (a small VPS, a container platform with static egress, or a self-hosted service reached via Cloudflare Tunnel), or push the fallback to the client (the user's browser fetching `web.archive.org/web/…id_/…` directly has its own residential IP, though CORS and the `id_` response's original headers must be considered), or pay for Enterprise/Aegis.

### Gaps
- No Cloudflare *documentation page* (as opposed to community moderators) explicitly states "Workers subrequests egress from shared IPs"; the statement is supported by moderator answers and two empirical issues, not by an official spec.
- No community report was found that specifically pairs Cloudflare Workers with archive.org 429s; the evidence is by analogy from other per-IP-limited APIs plus archive.org's documented per-IP behavior.
- Whether archive.org blocks Cloudflare/datacenter IP ranges wholesale since the 2026-09 protections is unknown; IA's post does not say.

## Key Question 5 — Post-2024 context: did IA tighten limits or add challenges after the Oct 2024 attacks?

### Takeaway
The verifiable timeline in this session is: per-IP 429 throttling with escalating blocks already existed in 2019; user reports of being blocked at very low volumes cluster in 2025–2026; and on 2026-09-15 IA officially confirmed new protections against high-volume automated traffic with a rewritten 429 page and admitted false positives. No official document ties the tightening to the Oct 2024 DDoS/breach or names datacenter-IP blocking.

### Cited Findings
- 2019: forum reports of 429s and progressively stricter caps (Sept–Oct 2019, Apr 2020) — [forum 1103558](https://archive.org/post/1103558/error-429-too-many-requests-despite-no-requests), [forum 1103806](https://archive.org/post/1103806/reason-for-new-strict-wayback-data-cap-http-429-too-many-requests)
- 2025–2026: repeated reports in the same threads (Jun 2025, Nov 2025, Dec 2025, Jul 2026, Sep 1–2 2026) of blocks with no personal request volume, attributed to IP blocks — [forum 1103558](https://archive.org/post/1103558/error-429-too-many-requests-despite-no-requests)
- 2026-09-15 official: protections against "waves of high-volume automated traffic", rewritten 429 message, false positives acknowledged, email-to-unblock process — [blog.archive.org 2026-09-15](https://blog.archive.org/2026/09/15/an-update-on-wayback-machine-access/)
- Parallel trend on the *supply* side: since 2025 major publishers block IA's crawlers (NYT hard-blocks and lists `archive.org_bot` in robots.txt; Gannett/USA Today Co. sites added `archive.org_bot` and `ia_archiver-web.archive.org` to robots.txt in 2025 and some show "excluded from Wayback Machine"; Guardian excluded articles from APIs and Wayback URLs; FT, Reddit, Le Monde, HuffPost FR, The Athletic also block) over AI-scraping concerns — [Nieman Lab, 2026-01-28](https://www.niemanlab.org/2026/01/news-publishers-limit-internet-archive-access-due-to-ai-scraping-concerns/); Forbes covered the same trend 2026-04-14 (fetch returned 403; title only) — [Forbes](https://www.forbes.com/sites/anishasircar/2026/04/14/why-major-news-sites-are-blocking-the-internet-archives-wayback-machine/)

### Inferences
- The Sept 2026 blocking wave is the most likely proximate cause of a *new* 429 problem in a Worker deployed in Sept 2026; the shared-IP mechanism (KQ4) makes Workers the archetypal "real traffic caught by mistake" case, but IA's remedy (email with your IP) is unworkable for a shared egress pool.

### Gaps
- The Oct 2024 DDoS/data-breach events and their blog posts were not re-verified in this session (blog.archive.org was reachable only via the fetch tool for the 2026 post); no source found links 2024 to the 2026 policy.
- No evidence either way on JS challenges (Cloudflare Turnstile-style) versus pure IP-reputation blocking.

## Key Question 6 — Is archive.org a good fallback for recipe pages (freshness, opt-outs, images, JSON-LD)?

### Takeaway
Archive.org can serve original HTML (with `id_`) including whatever JSON-LD the page carried at capture time, but coverage is opportunistic: a given recipe URL may have no capture, a stale one, or only a non-200 capture, and site owners can exclude themselves (some large publishers now do). Only one recipe site's robots.txt could be verified in this session (foodnetwork.com: no IA-crawler rule), so per-site opt-out status for the recipe vertical remains largely unknown.

### Cited Findings
- IA help center: "Pages may not be archived due to robots exclusions and some sites are excluded by direct site owner request"; other reasons content is missing: password/form-gated pages, and "When a dynamic page contains forms, JavaScript, or other elements that require interaction with the originating host, the archive will not contain the original site's functionality" — [help.archive.org: Wayback Machine General Information](https://help.archive.org/help/wayback-machine-general-information/)
- Publisher opt-outs are increasing (NYT, Gannett/USA Today network, Guardian, FT, Reddit, etc.), using robots.txt entries for `archive.org_bot` / `ia_archiver-web.archive.org`, API exclusions, and URL-level "excluded from the Wayback Machine" messages; the article does not say whether older snapshots were removed — [Nieman Lab, 2026-01-28](https://www.niemanlab.org/2026/01/news-publishers-limit-internet-archive-access-due-to-ai-scraping-concerns/)
- foodnetwork.com `robots.txt` (fetched 2026-09-28): groups for `*`, `Mediapartners-Google`, `Pinterest` (Crawl-delay 5), `Googlebot-News`; **no `ia_archiver`, `archive.org_bot`, or any "archive" user-agent and no AI-crawler groups** — [foodnetwork.com/robots.txt](https://www.foodnetwork.com/robots.txt)
- `id_` returns the original document with original (live-web) link/image URLs, so archived images referenced by original URL will load only if the live host still serves them; the non-`id_` replay rewrites every URL to `web.archive.org` — [archive.org forum: FAQ on id_](https://archive.org/post/1008502/faq-on-id_-wayback-toolbar-removal)
- The Availability API returns the *closest* capture and its `status`, so the returned snapshot may be old or non-200 — [archive.org/help/wayback_api.php](https://archive.org/help/wayback_api.php); the CDX `from`/`to`, `filter=statuscode:200`, negative `limit` and `fastLatest` parameters exist to select a recent successful capture — [CDX README](https://github.com/internetarchive/wayback/blob/master/wayback-cdx-server/README.md)
- IA's 2017 position that search-engine-oriented robots.txt "don't work well for web archives" (title of official blog post; content not fetched here) — [blog.archive.org 2017-04-17](https://blog.archive.org/2017/04/17/robots-txt-meant-for-search-engines-dont-work-well-for-web-archives/)

### Inferences
- Freshness: because recipe pages are edited (ingredient tweaks, added notes, changed images), a snapshot months old may differ from the live page, but the recipe core (ingredients/instructions in JSON-LD) is usually stable; a `from=` cutoff (e.g. last 24 months) plus `statuscode:200` is a reasonable staleness gate.
- Images: with `id_`, `<img>`/JSON-LD image URLs point at the live CDN; if the live site blocks the Worker, image fetches will likely fail too, while the non-`id_` replay would serve `web.archive.org/web/{ts}im_/…` copies (each another rate-limited request). For an importer that only needs recipe text, `id_` is still the right choice; image retrieval through IA multiplies request count against a per-IP limit.
- NYT Cooking is owned by the New York Times, which hard-blocks IA crawlers; new captures of cooking.nytimes.com are therefore unlikely (inference from the Nieman Lab report; not verified for that subdomain).

### Gaps
- Could not verify robots.txt or exclusion status for Dotdash Meredith (Allrecipes, Serious Eats, Simply Recipes, EatingWell, Food & Wine), Condé Nast (Bon Appétit, Epicurious), Hearst (Delish), or major independent recipe blogs — the sandbox's fetch tools were blocked for those hosts. No published study of Wayback coverage/staleness for recipe sites was found.
- No source quantifies how stale typical recipe-page captures are, or how often JSON-LD survives; the "JSON-LD survives in `id_` responses" claim follows from `id_` returning original bytes but was not empirically tested here.

## Key Question 7 — Alternatives: archive.today, Common Crawl, Google/Bing cache, Perma.cc, Memento aggregators, Ghostarchive

### Takeaway
Google's and Bing's caches are gone (Google: link removed early 2024, `cache:` operator dead by Sept 2024; Bing: cache links removed Dec 2024). archive.today has no documented API and is entangled in a years-long Cloudflare-DNS/CAPTCHA dispute. Common Crawl is the only alternative with a documented programmatic index, but its CDX endpoint is "heavily rate limited", answers abuse with 503s and 24-hour IP blocks, and its data is periodic crawl snapshots rather than on-demand copies. None is a drop-in real-time fallback.

### Cited Findings
- Google removed the cache link from result snippets in January 2024 and fully disabled the `cache:` operator by September 2024; about two weeks earlier it added Wayback Machine links to the "About this result" panel. Danny Sullivan: "It's been removed. I know, it's sad…" — [Search Engine Land, 2024-09-24](https://searchengineland.com/google-search-completely-kills-the-cache-feature-446904)
- Microsoft removed cache links from Bing results the week of 2024-12-11 "after several months of testing", citing that "the internet has evolved for better reliability, and many pages aren't optimized for cache viewing"; the article does not say whether `cc.bingj.com` copies remain reachable — [Search Engine Land, 2024-12-11](https://searchengineland.com/bing-officially-removes-cache-link-from-search-results-449220); a browser-extension tracker recorded "Bing Cache has been shut down" (title only, not fetched) — [dessant/web-archives issue #107](https://github.com/dessant/web-archives/issues/107)
- archive.today (archive.ph/.is/.li…): users on Cloudflare's 1.1.1.1 resolver get a different A record (`1.1.1.4` vs `23.137.249.79` via Google DNS) and an infinite CAPTCHA loop; the operator attributes this to resolvers lacking RFC 7871 EDNS-client-subnet; the problem has persisted since at least 2019, with comments through Feb–Aug 2026 saying it is unresolved — [ardislu gist: archive.today and Cloudflare DNS](https://gist.github.com/ardislu/b2f2b4b439c5da2f7ccb6bb42e7a8882); HN threads on the CAPTCHA loop — [HN 38024906](https://news.ycombinator.com/item?id=38024906), [HN 38173709](https://news.ycombinator.com/item?id=38173709), [HN 38246073](https://news.ycombinator.com/item?id=38246073); Cloudflare community thread — [archive.today & related sites failing again](https://community.cloudflare.com/t/archive-today-related-sites-failing-again/623376)
- Common Crawl FAQ: the CDX API at `https://index.commoncrawl.org` "is frequently abused and therefore heavily rate limited"; "If you receive HTTP 503 responses, please slow down your request rate"; if blocked, wait 24 hours; always use HTTPS; sleep between calls; do not run multiple threads from the same IP; avoid proxy networks; send an RFC 9110-formatted User-Agent; for volume, query the URL index via Amazon Athena or Spark; `cc-downloader` and `cdx-toolkit` are cited as polite clients — [commoncrawl.org/faq](https://commoncrawl.org/faq)
- Common Crawl 2023 incident: an aggressive downloader pushed >40 Gbps and forced global throttling (~128 KB/s) with 503 "Slow Down" from CloudFront on the data bucket; the index server 504'd; staff (Sebastian Nagel) recommended "limit the index to 1 request/sec, and implement retries" and noted users "sending 100k or more requests per hour while the server is able to successfully respond just few thousands" — [Common Crawl group: Apology for the Rate Limit / 503](https://groups.google.com/g/common-crawl/c/BvMGYUY-dro); status page — [status.commoncrawl.org](https://status.commoncrawl.org/); original index announcement — [commoncrawl.org blog](https://commoncrawl.org/blog/announcing-the-common-crawl-index)
- Forum users now recommend archive.is as the fallback when Wayback blocks them (Purple-Onion, 2026-09-02) — [archive.org forum 1103558](https://archive.org/post/1103558/error-429-too-many-requests-despite-no-requests)

### Inferences
- Common Crawl is usable as a *batch* fallback (look up the URL in the latest `CC-MAIN-*` index, then range-GET the WARC record from `data.commoncrawl.org`/S3 in `us-east-1`), but at ≤1 index request/s per IP, with 503/24 h-block escalation, from a shared Worker egress IP it has the same tenant-collision exposure as archive.org; and CC coverage of any specific long-tail recipe URL in the most recent crawl is not guaranteed.
- archive.today is not viable for automation: no API, DNS/CAPTCHA gating, and a Worker cannot solve a CAPTCHA.
- With Google and Bing caches gone, the realistic automated set is: Wayback (best coverage, per-IP limits), Common Crawl (batch, periodic), and — for on-demand snapshots of a page the app *can* reach — SPN2 or your own storage.

### Gaps
- Memento TimeTravel (`timetravel.mementoweb.org`) could not be fetched (the sandbox classifies it as a proxy/relay); its 2026 operational status and limits are unverified.
- Perma.cc and Ghostarchive were not researched within the tool budget; no claims made.
- Common Crawl's current (2026) crawl cadence, `CC-MAIN-2026-xx` IDs, and per-IP numeric limits are not stated in the FAQ; the "1 request/sec" figure is a 2023 staff recommendation.
- Whether `cc.bingj.com` still serves any cached copies in 2026 is unknown.

## Key Question 8 — Legal / Terms of Use for automated access and re-serving archived content

### Takeaway
IA's terms page could not be read in this session (JavaScript-only render; the Wayback copy was blocked by the sandbox), so no clause can be quoted. The operative, documented constraints are technical (rate limits, IP blocks, SPN block lists) plus IA's stated goal of distinguishing "abusive bots from people".

### Cited Findings
- IA maintains a Terms of Use page (`archive.org/about/terms.php`) and announced an update to it in 2014 (title only; content not fetched) — [blog.archive.org: Update to Terms of Use, 2014-12-30](https://blog.archive.org/2014/12/30/update-to-terms-of-use/)
- IA's 2026-09-15 post frames the current blocking as protection against "high-volume automated traffic" and asks blocked *people* to write in — it does not offer a sanctioned path for automated clients — [blog.archive.org 2026-09-15](https://blog.archive.org/2026/09/15/an-update-on-wayback-machine-access/)
- Archived content is third-party copyrighted material; IA's help center notes site owners can be excluded "by direct site owner request", i.e. IA honors takedown/exclusion — [help.archive.org](https://help.archive.org/help/wayback-machine-general-information/)

### Inferences
- Re-serving an archived recipe page's text in a personal/commercial app raises the same copyright questions as scraping the live page; IA's involvement adds no license. Low-volume, cached, single-user-initiated lookups are the pattern most consistent with IA's "people, not bots" framing.

### Gaps
- The actual Terms of Use text (automated access, redistribution, commercial use clauses) was not retrievable; treat this as unverified and read `archive.org/about/terms.php` in a browser before relying on it.

## Consolidated client recommendations (derived from the cited findings above)

- Use `GET https://archive.org/wayback/available?url=<url>` first; require `closest.status == "200"` and a `timestamp` newer than your staleness cutoff. Fall back to `GET https://web.archive.org/cdx/search/cdx?url=<url>&output=json&filter=statuscode:200&filter=mimetype:text/html&from=<YYYYMMDD>&limit=-1&fastLatest=true` only when you need control over recency — at ≤1 request/s per IP (IA staff: ~60/min average before 429s) — [edgi wayback #137](https://github.com/edgi-govdata-archiving/wayback/issues/137), [CDX README](https://github.com/internetarchive/wayback/blob/master/wayback-cdx-server/README.md).
- Fetch the body via `https://web.archive.org/web/<timestamp>id_/<url>` (original bytes, original URLs, no toolbar); keep concurrency ≤3 per source IP — [id_ FAQ](https://archive.org/post/1008502/faq-on-id_-wayback-toolbar-removal), [wayback-machine-downloader #160](https://github.com/hartator/wayback-machine-downloader/issues/160).
- On 429: check for `memento-datetime` (replayed 429 ≠ throttle); honor `Retry-After` if present; otherwise stop ≥60 s, then ≥1 h with doubling, with jitter; never retry in a tight loop (blocks double) — [edgi wayback #158](https://github.com/edgi-govdata-archiving/wayback/issues/158), [edgi wayback #137](https://github.com/edgi-govdata-archiving/wayback/issues/137), [wayback docs](https://wayback.readthedocs.io/en/stable/usage.html).
- Cache Availability/CDX answers and fetched snapshots indefinitely (captures are immutable), so each recipe URL costs IA at most two requests ever.
- Do not expect identity headers to help; if the Worker's shared egress IP is blocked, the only documented paths are email to `info@archive.org` (impractical for shared IPs) or moving the archive.org calls to a host with its own IP — [blog.archive.org 2026-09-15](https://blog.archive.org/2026/09/15/an-update-on-wayback-machine-access/), [Cloudflare Community 795286](https://community.cloudflare.com/t/dedicated-ip-static-ip-fixed-egress-ip-for-workers/795286).
- SPN2 (`POST https://web.archive.org/save/<url>` with `Authorization: LOW key:secret`, `if_not_archived_within=…`, then poll `/save/status/<job_id>`) is per-account and useful for *creating* a capture the app can later read, but it is slow, capped at single-digit captures/min, and cannot capture what the live site refuses to serve — [SPN2 doc](https://docs.google.com/document/d/1Nsv52MvSjbLb2PCpHlat0gkzw0EvtSgpKHu4mk0MnrA/edit).
