# Recipe importer: image pipeline, Cloudflare-native ingestion architecture, and legal/etiquette layer (as of 2026-09-28)

Scope note: this file covers (A) recipe image discovery/fetch/storage, (B) the Cloudflare architecture around a URL-ingestion pipeline, and (C) US-focused legal/etiquette considerations. It deliberately does NOT cover schema.org ingredient/instruction parsing, bot-detection mechanics, archive.org, or Gemini prompting (other researchers). All Cloudflare numbers below were read from the live docs pages this week; each bullet carries the page's "Last updated" date where the page showed one. **Section C is background information, not legal advice.**

## (A) Images: where recipe images live, how to fetch them from a Worker, and how to store/serve them

### Takeaway
Recipe pages expose the hero image redundantly (JSON-LD `image` — often an array of 1:1/4:3/16:9 crops because Google asks for that — plus `og:image`, plus the recipe card `<img>` which is frequently lazy-loaded via `data-src`/`data-srcset` or native `loading="lazy"`), and step images via `HowToStep.image`; the safest hero pick is JSON-LD `image` → first `og:image` → largest in-card `<img>`. From a Worker you can then re-host into R2 (egress-free, $0.015/GB-month, 10 GB free) and resize with the Images binding (`env.IMAGES.input(stream).transform().output()`, 5,000 unique transformations/month free), which avoids hotlink breakage, Referer-based hotlink protection, and the privacy leak of pointing your users' browsers at the source site's CDN.

### Cited Findings

**A1. Where images live in the markup**

- Google's Recipe structured-data spec makes `image` a *required* property of `Recipe`, typed `URL` or `ImageObject` (repeatable); it states "Image URLs must be crawlable and indexable", "Images must represent the marked up content", and recommends "Multiple high-resolution images (minimum of 50K pixels when multiplying width and height)" in aspect ratios "16x9, 4x3, and 1x1". Note: "Specifying the `image` property in `Recipe` markup has no impact on the image chosen for a text result image" — so the JSON-LD array is the publisher's deliberate set of hero crops, not something Google derives. — [Google Search Central: Recipe structured data](https://developers.google.com/search/docs/appearance/structured-data/recipe)
- `HowToStep.image` is *recommended* (not required) on Recipe steps, typed `ImageObject` or `URL`, and Google lists ".jpg, .png, or .gif" as supported formats for step images. `video` (`VideoObject`) is also a recommended Recipe property. — [Google Search Central: Recipe structured data](https://developers.google.com/search/docs/appearance/structured-data/recipe)
- Open Graph: `og:image` is "An image URL which should represent your object within the graph"; structured sub-properties are `og:image:url` ("Identical to og:image"), `og:image:secure_url`, `og:image:type` (MIME type), `og:image:width`, `og:image:height`, `og:image:alt`. Multiple images are expressed by repeating the `<meta>` tag, and "The first tag (from top to bottom) is given preference during conflicts"; sub-properties must follow their root tag and "Whenever another root element is parsed, that structured property is considered to be done and another one is started." — [ogp.me](https://ogp.me/)
- WordPress core (5.5+, the base for most food blogs using WP Recipe Maker/Tasty): "By default, WordPress will add `loading="lazy"` to all `img` tags that have `width` and `height` attributes present" via `wp_filter_content_tags()`; it only adds the attribute when both dimension attributes exist and it back-fills missing `width`/`height`. This is native browser lazy-loading — the real `src`/`srcset` stay in place, so a non-JS fetcher sees the real URLs. — [Make WordPress Core: Lazy-loading images in 5.5](https://make.wordpress.org/core/2020/07/14/lazy-loading-images-in-5-5/)
- JavaScript lazy-load libraries (still common on ad-heavy blogs) move the real URL into a data attribute and leave `src` as a placeholder; the widely used `lazysizes` library is the canonical example of the `data-src`/`data-srcset` + `class="lazyload"` convention, and Andrea Verlicchi's 2020+ analysis discusses when `data-src` is still needed versus native `loading="lazy"`. — [lazysizes](https://afarkas.github.io/lazysizes/index.html); [Verlicchi: Do we still need lazy loading libraries and data-src?](https://www.andreaverlicchi.eu/en/blog/do-we-still-need-lazy-loading-libraries-data-src/) *(attribute names from the library's documented convention; the lazysizes page itself was not fetched this session — see Gaps)*
- WP Recipe Maker markup is built from shortcodes ("The 'blocks' in a WP Recipe Maker template are actually shortcodes") and every template's styles are prefixed `.wprm-recipe-template-{template-name}` because several cards can appear on one page; `.wprm-recipe-name` is confirmed as an element class. — [Bill Erickson: Custom recipe templates for WP Recipe Maker](https://www.billerickson.net/custom-recipe-templates-for-wp-recipe-maker/)
- Tasty Recipes supports per-step images and videos inside the recipe card (support article "How do I add step-by-step videos and images to my recipe card?"), so step images from Tasty sites will also surface as `HowToStep.image` in its JSON-LD. — [WP Tasty support](https://support.wptasty.com/en/articles/3746446-how-do-i-add-step-by-step-videos-and-images-to-my-recipe-card)

**A2. Fetching images from a Worker: hotlink protection, image CDNs, negotiation**

- Cloudflare Hotlink Protection (used by many blogs on Cloudflare) "denies access to requests when the HTTP referer does not include your website domain name (and is not blank)" — i.e., **a request with no `Referer` header is allowed**; it covers only `gif, ico, jpg, jpeg, png`; site owners can exempt images by putting them in a directory named `hotlink-ok` or via Configuration Rules. — [Cloudflare docs: Hotlink Protection](https://developers.cloudflare.com/waf/tools/scrape-shield/hotlink-protection/) (Last updated Aug 3, 2026)
- Jetpack / WordPress.com Site Accelerator ("Photon") URLs have the form `https://i0.wp.com/[original-domain]/[path]/[image.jpg]?[params]`; documented GET params: `w` (width px), `h` (height px), `crop` (x-offset,y-offset,width,height in %), `resize` ("Resize and crop an image to the exact width,height"), `fit` ("Fit an image to a containing box… aspect ratio is maintained"), `lb`/`ulb` (letterbox), `filter` (negate, grayscale, sepia, edgedetect, emboss, blurgaussian, blurselective, meanremoval), `brightness`, `contrast`, `colorize`, `smooth`, `zoom`, `quality`, `strip`. Mechanistic consequence: you can strip `?w=…&resize=…` or set your own `w=` to get the original or a specific size from the same URL. — [WordPress.com Developer: Site Accelerator (Photon) API](https://developer.wordpress.com/docs/photon/api/)
- Cloudflare's own image transformation service refuses non-HTTPS or badly escaped origin URLs (`Cf-Resized` codes 9406/9419), reports origin 4xx as 9408 ("access denied"), and reports "origin returned non-image content (HTML, error page, etc.)" as 9412 — a useful taxonomy of what goes wrong when fetching third-party images (403 from hotlink/bot rules, HTML interstitials instead of bytes). — [Cloudflare docs: Images troubleshooting](https://developers.cloudflare.com/images/reference/troubleshooting/)
- Format negotiation in a Worker is driven by the `Accept` header; Cloudflare's own example is `if (/image\/avif/.test(accept)) format="avif" else if (/image\/webp/.test(accept)) format="webp"`. — [Cloudflare docs: Transform via Workers](https://developers.cloudflare.com/images/transform-images/transform-via-workers/) (Last updated Jul 2, 2026)

**A3. Storing and serving: R2**

- R2 Standard: **$0.015/GB-month** storage; **Class A ops $4.50/million** (writes/lists), **Class B ops $0.36/million** (reads); **egress free** ("Egressing directly from R2… does not incur data transfer (egress) charges and is free", covering Workers API, S3 API and public bucket domains). Free tier (Standard only): **10 GB-month/month, 1 million Class A, 10 million Class B**. Infrequent Access: $0.01/GB-month, $9.00/M Class A, $0.90/M Class B, $0.01/GB retrieval, 30-day minimum. 401-rejected requests are not billed; usage rounds up to the next billing unit. — [Cloudflare docs: R2 pricing](https://developers.cloudflare.com/r2/pricing/) (Last updated Aug 7, 2026)
- R2 limits: max object 5 TiB ("4.995 TiB" multipart, up to 10,000 parts); single-part upload 4.995 GiB; 1,000,000 buckets/account; **100 custom domains per bucket**; object key 1,024 bytes; object metadata 8,192 bytes; **concurrent writes to the same key limited to 1/second (excess → HTTP 429)**; REST API 1,200 requests per 5 minutes account-wide. — [Cloudflare docs: R2 limits](https://developers.cloudflare.com/r2/platform/limits/) (Last updated Jun 8, 2026)
- Public buckets: "Public access through `r2.dev` subdomains is rate-limited and should only be used for development purposes"; a custom domain "allows you to use Cloudflare Cache to accelerate access to your R2 bucket" plus Access and WAF token authentication; objects are not edge-cached by default beyond default-cacheable file types, so add a Cache Rule / "Cache Everything" if you want everything cached. — [Cloudflare docs: R2 public buckets](https://developers.cloudflare.com/r2/buckets/public-buckets/) (Last updated Sep 25, 2026)

**A4. Storing/serving: Cloudflare Images (storage, delivery, transformations, binding)**

- Pricing: **Images Transformed: first 5,000 unique transformations/month free, then $0.50 per 1,000 unique transformations/month**; **Images Stored: $5 per 100,000 images stored/month**; **Images Delivered: $1 per 100,000 images delivered/month**. The free 5,000 "applies only to image optimization outside of Cloudflare Images storage" (i.e., transforming your own R2/remote images); exceeding it returns error **9422** with no charge. "A unique transformation is a request to transform an original image based on a set of supported parameters"; repeats within the calendar month count once, and `format` variants of the same transformation count as one. Remote images are billed only on Transformed; images stored in Cloudflare Images are billed on Stored + Delivered. Using the Images *binding* counts toward Images Transformed; a delivery URL counts toward Images Delivered. — [Cloudflare docs: Images pricing](https://developers.cloudflare.com/images/pricing/) (Last updated Jul 8, 2026)
- Images binding (Workers): configure `"images": { "binding": "IMAGES" }` in wrangler; `env.IMAGES.input(stream)` accepts image bytes **up to 20 MB** from any source (R2, `fetch()` bodies, request bodies) and returns a chainable handle; `.transform({ width, height, blur, … })` (chainable; order of ops preserved), `.draw()` for overlays, `.output({ format: "image/webp", quality })` then `.response({ headers })`; **`.info(stream)` returns `format, fileSize, width, height` and is free**. Billing rule: "Each unique combination of source image and parameters is billed only once per calendar month." Docs example: `(await env.IMAGES.input(response.body).transform({ width: 800 }).output({ format: "image/webp" })).response({ headers: { "Cache-Control": "public, max-age=3600, stale-while-revalidate=86400" } })`. `wrangler dev` runs a low-fidelity offline mode (width/height/rotate/format only); `--remote` gives production parity. — [Cloudflare docs: Images binding](https://developers.cloudflare.com/images/transform-images/bindings/) (Last updated Sep 2, 2026)
- Transform via `fetch(url, { cf: { image: { fit: "scale-down", width: 800, height: 600, format: "avif"|"webp", quality, metadata, gravity } } })`: available "on any zone that hosts a Worker" with image optimization enabled; each transformation is billed to the Worker-owning account; the `Via` header contains the string `image-resizing` on requests coming from another Worker (check it to avoid loops); "Do not set up the image optimization worker for the entire zone (`/*`)"; failures return 400/404/502. — [Cloudflare docs: Transform via Workers](https://developers.cloudflare.com/images/transform-images/transform-via-workers/) (Last updated Jul 2, 2026)
- Transformation input limits (images outside Cloudflare Images storage): **100 megapixels max area** ("for example, 10,000×10,000"), **100 MB max file size**, animated GIF/WebP limited to 50 megapixels across all frames; `Cf-Resized` header error codes: 9401 bad params, 9402 too large/connection interrupted, 9403 request loop, 9404 image not found, 9406/9419 non-HTTPS or unescaped URL, 9408 origin 4xx, 9412 origin returned non-image, 9413 exceeds 100 MP, 9422 transformation quota exceeded, 9520 unsupported format, 9529 processing timeout; absence of `Cf-Resized` means no resize was attempted. — [Cloudflare docs: Images troubleshooting](https://developers.cloudflare.com/images/reference/troubleshooting/)

**A5. Worker-side size limits that bound image handling**

### Inferences (labelled; not directly sourced unless noted)

- **Discovery order for the hero image.** (1) JSON-LD `Recipe.image` (string, `ImageObject{url,width,height}`, or array; if array, prefer the entry whose width/height matches the display aspect you want — publishers following Google's guidance ship 1:1, 4:3, 16:9 crops of the *same* photo, so any one is a valid hero and the others are free thumbnails). (2) First `og:image` (OG spec says first wins) with `og:image:width/height` for size sanity. (3) `twitter:image` (Twitter card tag; same idea, not fetched this session). (4) `<link rel="image_src">` (legacy; not fetched this session). (5) In-card `<img>` inside the recipe-plugin container: read, in order, `data-lazy-src`, `data-src`, `data-srcset`/`srcset` (pick the largest `w` descriptor), `src`; also `<picture><source srcset type="image/webp|avif">` where the `<img>` fallback is usually JPEG. This order is an inference from A1: JSON-LD/OG are declared intentionally, whereas in-card `<img>` requires lazy-load unwrapping.
- **Step images:** take `HowToStep.image` from JSON-LD when present (Google recommends it, Tasty and WPRM both emit it), keyed by step index; fall back to `<img>` elements inside the instructions list of the recipe-plugin container. Because JSON-LD step images are typically a strict subset of in-card images, prefer JSON-LD to avoid picking up ad creatives interleaved between steps.
- **Rejecting junk images (heuristics, from A1 facts):** discard anything whose declared or measured size is below Google's own floor for recipe images (50K px area, e.g. < ~224×224) — this also kills 1×1 tracking pixels; discard SVG/ICO and anything with `logo|icon|avatar|badge|sprite|pixel|ad[s]?|banner|placeholder|blank|spacer|loading` in the path or filename; discard data: URIs shorter than a few KB (typical lazy-load placeholders are tiny base64 GIFs); prefer images whose aspect ratio is between 1:2 and 2:1; prefer JPEG/WebP/AVIF over PNG/GIF for the hero (photographs), and use `env.IMAGES.info()` — which is free — to measure actual pixel dimensions before committing bytes to R2. If `og:image:width/height` are present, trust them for pre-filtering to avoid fetching at all.
- **Fetching:** send no `Referer` header (Cloudflare Hotlink Protection allows blank Referer; sending your own app's domain as Referer is exactly what gets blocked — A2). Send `Accept: image/avif,image/webp,image/*,*/*;q=0.8` so CDNs that negotiate (Photon, Cloudflare, Imgix, Cloudinary) return a modern format, but expect that the same URL can then yield different bytes on different fetches — hash *after* normalizing through your own transform, not the raw bytes, if you dedupe by hash. Check `Content-Type` starts with `image/` and that the first bytes match a known magic number (JPEG `FF D8 FF`, PNG `89 50 4E 47`, WebP `52 49 46 46 … 57 45 42 50`, GIF `47 49 46 38`, AVIF/HEIF `ftyp` at offset 4) — Cloudflare's own 9412 error exists precisely because origins return HTML challenge pages with 200 status. Whether image requests are bot-blocked as often as HTML requests is not something I found data on (see Gaps); mechanistically, WAF/bot rules are usually written against HTML routes and image CDNs (i0.wp.com, Cloudinary, Imgix) are separate hostnames with their own policies, so the expectation is *less* blocking, but a site behind Cloudflare "Block AI Bots"/Super Bot Fight Mode applies to the whole zone. Other researchers cover bot blocking.
- **Signed/expiring URLs** (e.g., Cloudinary/Imgix signed URLs, Mediavine or Shopify CDN with expiry params): these are exactly why hotlinking breaks; if the URL contains `expires=`, `X-Amz-Signature`, `sig=`, `token=`, treat it as re-host-or-lose and fetch immediately during import.
- **Re-host vs hotlink.** Re-hosting into R2 costs ~nothing at recipe-app scale (a 300 KB WebP hero ≈ $0.0000045/month at $0.015/GB-month; 10 GB free covers ~30,000 such images) and eliminates: (a) breakage when the source rotates its CDN URLs or enables hotlink protection; (b) the privacy leak where every recipe view sends the user's IP, `Referer` and cookies to the source site's ad-tech CDN; (c) mixed-content and CORS problems. Legally, however, re-hosting makes *you* the party storing and displaying a copy of a copyrighted photograph, while embedding/inline-linking is, in the Ninth Circuit, not direct infringement under the "server test" — see C2. For a *private, per-user* archive the exposure is similar to a user saving the photo to their own device; for a *public* gallery it is materially different (see C1/C2).
- **Thumbnails/dedupe:** derive `hero.webp` (e.g., 1200 wide, `fit: "scale-down"`) and `thumb.webp` (e.g., 400×400 `fit: "cover"`) at import time with the Images binding (2 unique transformations per recipe, so 5,000 free/month ≈ 2,500 imports/month before $0.50/1,000 kicks in), store both in R2 under a content-addressed key such as `img/<sha256-of-normalized-original>.webp` so re-imports of the same recipe (or the same photo across sites) don't duplicate storage. `crypto.subtle.digest("SHA-256", buffer)` is available in Workers (WebCrypto; not separately sourced here). Do not rely on R2 to dedupe; it has no content-addressing of its own.
- **Firebase Storage** only makes sense if you want the images next to a Firebase-hosted front end and are already on Blaze; R2 is cheaper on egress ($0 vs $0.12/GB on legacy buckets) and needs no billing account for the first 10 GB.

## (B) Cloudflare-native architecture for a robust URL-ingestion pipeline

### Takeaway
Everything needed for fetch→extract→store exists as Workers bindings with a usable free tier: Workflows (durable steps with built-in retries, free on Workers Free, 1,024 steps/instance, 365-day sleeps) is the best fit for the per-import pipeline; Queues (Workers Paid, $0.40/M ops, 3 retries default, DLQ, 24 h delayed delivery) or Workflows handle async decoupling; a SQLite-backed Durable Object per source host (available on the Free plan since 2025; alarms retried 6× with backoff) is the right single-threaded place for per-host rate limiting, circuit breaking and idempotency; KV/Cache API cache fetched HTML and extraction results; D1 holds recipe metadata; Workers Logs (3-day free / 7-day paid retention) with structured `console.log` objects give per-host failure tracking. The 2026 limit changes that matter: Paid Workers now allow 10,000 subrequests per invocation by default (up to 10 million via `limits.subrequests`), CPU time is configurable to 5 minutes, and Workflows step/storage billing started Aug 10, 2026.

### Cited Findings

**B1. Workers limits relevant to ingestion (page last updated Sep 5, 2026)**

- CPU time per invocation: **Free 10 ms** (HTTP and Cron); **Paid: 30 s default, configurable up to 5 min** for HTTP; Cron on Paid: 30 s for triggers firing more often than hourly, 15 min for ≥ hourly. — [Workers limits](https://developers.cloudflare.com/workers/platform/limits/)
- Duration/wall-clock: "There is no hard limit on duration for HTTP-triggered Workers. As long as the client remains connected, the Worker can continue processing." For Cron, Queues and Durable Object triggers the wall-clock limit is **15 minutes**. — [Workers limits](https://developers.cloudflare.com/workers/platform/limits/)
- Memory: **128 MB per isolate**, both plans. — [Workers limits](https://developers.cloudflare.com/workers/platform/limits/)
- Subrequests: **Free: 50 external subrequests + 1,000 to Cloudflare services per invocation**; **Paid: 10,000 by default, raisable "up to 10 million by setting the new `subrequests` limit in your Wrangler configuration file"** (change dated Feb 11, 2026; motivation given: long-running Workflows and DO websockets "could often exceed this limit and error"; you can also set the limit *lower* "to protect against runaway code or unexpected costs"). — [Changelog: Workers are no longer limited to 1000 subrequests (2026-02-11)](https://developers.cloudflare.com/changelog/post/2026-02-11-subrequests-limit/); [Workers limits](https://developers.cloudflare.com/workers/platform/limits/)
- Simultaneous open connections: **6** per invocation (both plans); additional `fetch()` calls queue until one of the 6 completes/returns headers. — [Workers limits](https://developers.cloudflare.com/workers/platform/limits/)
- Request body: 100 MB (Free/Pro/Business), up to 5 GB Enterprise; response body: no enforced limit; env vars 64 (Free)/128 (Paid) at 5 KB each; Workers per account 100 (Free)/500 (Paid); Cache API: 512 MB max object, 50 (Free)/1,000 (Paid) calls per request. — [Workers limits](https://developers.cloudflare.com/workers/platform/limits/)

**B2. Cloudflare Queues (pages last updated Apr 21, 2026)**

- Pricing: **$0.40 per million operations**; "An operation is counted for each 64 KB of data that is written, read, or deleted" (a 127 KB message = 2 ops); each retry costs a read op; DLQ writes count. **Workers Free: 10,000 ops/day** (≈300k/month); **Workers Paid: 1,000,000 ops/month included**. Cost formula given: `((messages × 3) − 1,000,000) / 1,000,000 × $0.40` assuming write+read+delete per message. — [Queues pricing](https://developers.cloudflare.com/queues/platform/pricing/)
- Limits: message **128 KB** (incl. ~100 bytes metadata); batch **max 100 messages** (default 10); batch wait **max 60 s** (default 5 s); **max_retries up to 100 (default 3)**; `delaySeconds` **max 24 hours**; retention configurable up to 14 days (page notes 24 h on Free — flagged, see Gaps); **5,000 messages/s per queue**; push consumer concurrency **max 250**; 10,000 queues/account; 25 GB backlog per queue; **consumer wall time 15 min**; pull-based visibility timeout 12 h; exceeding throughput makes `send()`/`sendBatch()` throw "Too Many Requests". — [Queues limits](https://developers.cloudflare.com/queues/platform/limits/)
- Retry semantics: "When a single message within a batch fails to be delivered, the entire batch is retried, unless you have explicitly acknowledged a message"; `msg.ack()`, `batch.ackAll()`, `msg.retry({ delaySeconds: 3600 })`, `batch.retryAll({ delaySeconds: 600 })`; first call wins per message; per-message delay overrides queue-level `delivery_delay`; **when `max_retries` is exhausted the message is deleted unless a `dead_letter_queue` is configured**, in which case it is written there. — [Queues: batching, retries and delays](https://developers.cloudflare.com/queues/configuration/batching-retries/)
- Consumer concurrency autoscaling considers backlog size and growth, the ratio of failed to successful invocations, and `max_concurrency` (1–250; recommended to leave unset); "Retrying messages with `retry()` or calling `retryAll()` on a batch will not count as a failed invocation" — so retry-with-delay does not throttle your consumer. — [Queues: consumer concurrency](https://developers.cloudflare.com/queues/configuration/consumer-concurrency/)

**B3. Durable Objects (pricing page last updated Aug 25, 2026; alarms page Apr 21, 2026)**

- Availability: **SQLite-backed Durable Objects are available on both Workers Free and Paid**; the older KV-backed storage backend is Paid-only. Free plan: **100,000 DO requests/day, 13,000 GB-s/day**. Paid: 1 million requests/month included then **$0.15/million**; 400,000 GB-s/month then **$12.50/million GB-s**. SQLite storage (Paid; billing began January 2026): 25 billion rows read/month included then $0.001/M; 50 million rows written then $1.00/M; 5 GB-month then $0.20/GB-month. — [Durable Objects pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/)
- Alarms: "Each Durable Object is able to schedule a single alarm at a time by calling `setAlarm()`" (`setAlarm(scheduledTimeMs)`, calling again overrides); alarms have "guaranteed at-least-once execution and are retried automatically when the `alarm()` handler throws", with exponential backoff starting at 2 s, **up to 6 retries**; the handler receives `alarmInfo { retryCount, isRetry }`; if you need indefinite retries, catch inside `alarm()` and reschedule yourself. — [Durable Objects: Alarms](https://developers.cloudflare.com/durable-objects/api/alarms/)

**B4. Workers KV (pages last updated Apr 21, 2026)**

- Limits: key 512 B, value **25 MiB**, metadata 1,024 B; **writes to the same key limited to 1/second**; 1,000 operations per Worker invocation; 1,000 namespaces; minimum `cacheTtl` **30 seconds** (as the limits page currently reads); Free: 100,000 reads/day, 1,000 writes/day (to different keys), 1 GB storage. — [KV limits](https://developers.cloudflare.com/kv/platform/limits/)
- Pricing: Free per day — 100k reads, 1k writes, 1k deletes, 1k lists, 1 GB. Paid per month — 10M reads then **$0.50/M**; 1M writes then **$5.00/M**; 1M deletes then $5.00/M; 1M lists then $5.00/M; 1 GB then $0.50/GB-month; billing is per key ("Bulk read operations are billed by the amount of keys read"). — [KV pricing](https://developers.cloudflare.com/kv/platform/pricing/)

**B5. Cache API (page last updated Aug 14, 2026)**

- The Cache API works on custom domains and Pages Functions but **does not work on `*.workers.dev` subdomains** (nor in the dashboard editor/Playground), and Workers behind Cloudflare Access cannot use it. `caches.default` is one object but storage is **local to the data center** that wrote it ("do not replicate globally"); `cache.delete()` likewise only affects the invoking data center. ### Inferences (labelled)

- **Product-to-stage mapping.** Request Worker (validate + normalize URL, dedupe check, enqueue, return job id) → Workflow instance per import (steps: `fetch`, `parse`, `llm-normalize`, `images`, `persist`, `notify`) → Durable Object per source host (rate limit/circuit breaker/idempotency) → KV or Cache API for raw HTML/extraction caches → R2 + Images binding for photos → D1 for recipe/user metadata → Workers Logs for host failure tracking. Queues remain useful as the ingress buffer if you want producer/consumer decoupling with backpressure, but for a per-URL pipeline Workflows already give you durable retries and state, and are free on Workers Free where Queues' monthly billing is Paid-only (B2, B7).
- **Why Workflows fit fetch→extract→store:** each `step.do()` is checkpointed, retries are configurable per step (up to 10,000), a step's wall-clock is unlimited (so a slow third-party render/API is fine), `step.sleep()` can implement `Retry-After` waits of any length without burning CPU, and the instance's persisted state (100 MB free) can carry the fetched HTML between steps. Watch the **1 MiB step-result cap** (B7): don't return full HTML from a step — write it to KV/R2 inside the step and return the key. Also note Free plan's **3,000 steps/day** and 1,024 steps/instance.
- **Retry/backoff mechanics for 429/503:** (1) honor `Retry-After` (seconds or HTTP-date) exactly, capped (e.g., 1 h) — with Workflows use `step.sleep("retry-after", ms)`; with Queues use `msg.retry({ delaySeconds })` up to 24 h; (2) otherwise exponential backoff with full jitter: `delay = rand(0, min(cap, base × 2^attempt))`, base 1–2 s, cap 5–10 min, 4–6 attempts; (3) treat 403/401/451 as terminal for the *direct* strategy and escalate the ladder rather than retry; (4) treat 5xx and network errors as retryable; (5) treat 200-with-HTML-challenge (e.g. body contains a challenge page, or `Content-Type: text/html` where an image was expected — cf. Cloudflare's own 9412 code in A2) as a soft failure that escalates. These are standard patterns, not Cloudflare-sourced.
- **Per-host rate limiting and circuit breaker in a Durable Object:** derive the DO id with `env.HOST_LIMITER.idFromName(hostname)`; because a DO is single-threaded per id, a token bucket in memory/SQLite (e.g., 1 request per 2–5 s per host, burst 2) plus a breaker state machine (`closed` → `open` after N consecutive 429/403 within a window → `half-open` after cooldown) is race-free. Use the single alarm (B3) to flip `open`→`half-open`; because alarms retry at most 6 times, catch exceptions and re-`setAlarm` yourself. Free-tier budget: 100k DO requests/day is far above a personal app's import rate.
- **Idempotency:** key = canonical URL hash (after stripping tracking params, lowercasing host, removing fragment, resolving redirects, honoring `<link rel="canonical">` when same-host); store `import:<hash>` → `{status, recipeId, updatedAt}` in KV (or the host DO / D1) so a double-submit or a Workflow retry doesn't re-fetch or re-write. If you use Workflows, pass the canonical hash as the *instance id* so `env.MY_WORKFLOW.create({ id })` refuses duplicates.
- **Caching layers:** raw fetched HTML → KV with `expirationTtl` 24–72 h (value ≤ 25 MiB; KV writes are the expensive op at $5/M paid, 1k/day free, so cache once per import, not per attempt); extraction result (normalized recipe JSON) → D1 as the source of truth, KV as a read cache; `robots.txt` per host → KV with 24 h TTL (matches RFC 9309's caching guidance, C4). The Cache API is a poor fit for the ingestion side because it is per-data-center and does not work on `workers.dev` (B5); it is fine for serving R2-backed images behind a custom domain.
- **Notifying the client:** the simplest, cheapest option is polling `GET /imports/:id` backed by KV/D1 (Workflows also expose `instance.status()` via the binding); SSE from a Worker works because HTTP Workers have no wall-clock limit while the client stays connected (B1), but each open SSE stream is a live invocation; a Durable Object WebSocket (Hibernation API) is the scalable push option and is on the Free plan. Not separately sourced beyond B1/B3.
- **Observability pattern:** log one structured object per stage with `{ jobId, host, stage, strategy, status, elapsedMs, error }` and filter in Workers Logs by `host` to see which hosts fail and how; 200k events/day free is enough for thousands of imports/day at ~6 events per import. Also persist the outcome per host in D1 (`host_stats(host, strategy, ok, fail, last_error, updated_at)`) so the fetch ladder can consult it — Workers Logs retention is only 3–7 days (B9).

**Reference pipeline sketch (adapt as needed)**

1. **Ingress Worker** (`POST /imports`): validate URL (https only; reject private/loopback IPs and `localhost`; reject obviously non-recipe hosts if you keep a denylist), strip `utm_*`, `fbclid`, `gclid`, `mc_cid`, `ref`, `igshid`; lowercase host; drop fragment; compute `canonHash`; check `import:<canonHash>` in KV → if found and fresh, return existing `recipeId`; else `env.IMPORT_WF.create({ id: canonHash, params: { url, userId } })`; return `202 { jobId }`.
2. **Workflow step `resolve`**: call host DO `acquire()` (token bucket + breaker); `fetch(url, { redirect: "manual" })` loop to resolve redirects (≤ 5); honor `<link rel="canonical">` if same registrable domain; store final URL.
3. **Step `fetch` (strategy ladder)**: direct fetch with identifying UA → (on 403/challenge/empty body) rendered fetch (Browser Rendering or third-party API, covered elsewhere) → third-party fetch API → mark `needs_user_assist` (client-side paste/share-sheet). Each rung is a separate `step.do` with its own retry policy; store HTML in KV `html:<canonHash>` and return only the key.
4. **Step `parse`**: JSON-LD `Recipe` first, then microdata/OG fallbacks (covered elsewhere); emit candidate image list per A-Inferences.
5. **Step `normalize`**: Gemini call (covered elsewhere); CPU-light, wall-clock heavy → fine in a step.
6. **Step `images`**: for hero + up to N step images: DO `acquire()` on the image host, fetch with no `Referer`, sniff magic bytes, `env.IMAGES.info()` to size-check (free), `env.IMAGES.input().transform().output()` → `env.BUCKET.put("img/<sha256>.webp", body, { httpMetadata: { contentType: "image/webp", cacheControl: "public, max-age=31536000, immutable" } })`; skip if key exists (`head()`).
7. **Step `persist`**: D1 transaction writing `recipes`, `recipe_images`, `imports`; KV `import:<canonHash>` → done.
8. **Step `notify`**: write status for polling; optional DO WebSocket push.
9. **Cron** (`0 * * * *`): re-drive `imports` rows in `needs_retry` with `next_attempt_at <= now` (for failures outside a Workflow's own retry budget), and roll up `host_stats`.

## (C) Legal and etiquette considerations (US-focused; Atlanta, GA user) — background information, NOT legal advice

### Takeaway
US law treats an ingredient list as unprotectable fact and bare functional directions as unprotectable process (Publications International v. Meredith, 7th Cir. 1996; Lambing v. Godiva, 6th Cir. 1998; Tomaydo-Tomahhdo v. Vozary, N.D. Ohio 2015, aff'd 6th Cir.), while headnotes/expressive prose and **photographs are fully protected** — so a personal-use importer that stores a user's own copy is on much firmer ground than one that republishes text and photos publicly. On access law, scraping public pages is unlikely to violate the CFAA after Van Buren (2021) and hiQ (9th Cir. 2022), and the Ninth Circuit held in Amazon v. Perplexity (Aug 4, 2026) that a user-directed agent's access is the *user's* access; the live risk has shifted to breach-of-terms (which mostly binds logged-in users per Meta v. Bright Data, 2024) and to publisher norms — Cloudflare now blocks "Agent" bots by default on ad-monetized pages for new zones (Sept 15, 2026), and the 2021 Recipeasly episode shows the community reaction to ad-stripping. Practical etiquette: identify yourself, one page per user action, cache, link back, never republish.

### Cited Findings

**C1. Copyright in recipe text and photos**

- US Copyright Office FAQ: "A mere listing of ingredients is not protected under copyright law. However, where a recipe or formula is accompanied by substantial literary expression in the form of an explanation or directions, or when there is a collection of recipes as in a cookbook, there may be a basis for copyright protection." — [U.S. Copyright Office FAQ: What does copyright protect?](https://www.copyright.gov/help/faq/faq-protect.html)
- *Publications International, Ltd. v. Meredith Corp.*, 88 F.3d 473, 478–82 (7th Cir. 1996): recipes in a copyrighted recipe book were held excluded from protection under 17 U.S.C. § 102(b). *Lambing v. Godiva Chocolatier*, 142 F.3d 434 (6th Cir. 1998) (unpublished): "[R]ecipes are functional directions for achieving a result and are excluded from copyright protection under 17 U.S.C § 102(b)." *Barbour v. Head*, 178 F. Supp. 2d 758, 762–64 (S.D. Tex. 2001): declined to rule recipes unprotectable as a matter of law where they contained "light-hearted or helpful commentary". *Tomaydo-Tomahhdo LLC v. Vozary*, No. 1:14-cv-00469 (N.D. Ohio): "[T]he identification of ingredients necessary for the preparation of food is a statement of facts. There is no expressive element deserving copyright protection…" — [National Law Review: Mixing Things Up — Let's Talk Recipes (Part One, Copyright)](https://natlawreview.com/article/mixing-things-let-s-talk-recipes-part-one-four-part-series-copyright); district-court opinion PDF at [GovInfo](https://www.govinfo.gov/content/pkg/USCOURTS-ohnd-1_14-cv-00469/pdf/USCOURTS-ohnd-1_14-cv-00469-0.pdf); Sixth Circuit affirmance (2015, unpublished) at [ca6.uscourts.gov 15a0705n.06](http://www.opn.ca6.uscourts.gov/opinions.pdf/15a0705n-06.pdf) (not retrievable this session — redirect loop; see Gaps)
- Photographs: the Ninth Circuit "server test" (*Perfect 10 v. Amazon*, 2007) holds that "[f]or a display to be actionable, it must display a *copy*" that is "stored on *that computer*", so a site that *embeds/inline-links* an image hosted elsewhere does not directly infringe; *Hunley v. Instagram* (9th Cir., July 17, 2023) reaffirmed this, holding an embedding website "does not have a copy of the images for purposes of the Copyright Act". District courts in the Second Circuit went the other way: *Goldman v. Breitbart News* (S.D.N.Y. 2018), *Nicklen v. Sinclair Broadcasting* (S.D.N.Y. 2021), *McGucken v. Newsweek* (S.D.N.Y. 2022) rejected the server test. — [Davis Wright Tremaine: "Server Test" Is Reaffirmed (For Now) in Hunley v. Instagram](https://www.dwt.com/insights/2023/08/server-test-instagram-case-ninth-circuit)
- The 2021 **Recipeasly** episode: a site that stripped ads and personal introductions from food-blog recipes drew immediate backlash ("stealing content, eliminating context and creator revenue" — Kat Kinsman); a blogger quoted earning ~1.5p per page view from ads; the founder posted "Given the feedback, we are taking recipeasly.com down as we re-examine our impact" and the site was offline by March 1, 2021. — [Yahoo News (PA/Independent): Food website that 'fixed' recipes by removing adverts taken down after backlash](https://ca.news.yahoo.com/food-website-fixed-recipes-removing-222534398.html); also reported by [The Washington Post](https://www.washingtonpost.com/food/2021/03/02/recipeasly-food-bloggers-controversy/)
- Fair use for AI training remains case-by-case: the U.S. Copyright Office's 2025 generative-AI training report "declined to adopt a categorical rule", and *The New York Times Co. v. Microsoft* (S.D.N.Y., filed 2023) is ongoing. — [Ropes & Gray, May 2026: Web Scraping in the Age of AI](https://www.ropesgray.com/en/insights/alerts/2026/05/web-scraping-in-the-age-of-ai-guidance-for-data-owners-and-scrapers)

**C2. Web-scraping / access law (CFAA, contract, trespass) — chronology**

- *Van Buren v. United States* (2021) narrowed the CFAA: one "exceeds authorized access" only by entering areas of a computer that are off-limits, not by using accessible information for an improper purpose. — [Ropes & Gray, May 2026](https://www.ropesgray.com/en/insights/alerts/2026/05/web-scraping-in-the-age-of-ai-guidance-for-data-owners-and-scrapers)
- *hiQ Labs v. LinkedIn* (9th Cir., April 2022, on remand after Van Buren): "access to public information online likely cannot be a violation of the CFAA"; where no login is required "that computer has erected no gates to lift or lower in the first place." Caveats noted by EFF: individualized cease-and-desist letters can revoke authorization under *Facebook v. Power Ventures*, and contract/trespass-to-chattels theories remain. — [EFF: Scraping Public Websites (Still) Isn't a Crime](https://www.eff.org/deeplinks/2022/04/scraping-public-websites-still-isnt-crime-court-appeals-declares). Ropes & Gray adds that LinkedIn ultimately prevailed against hiQ on **breach of contract** because its user agreement barred scraping, and that "the narrowing of the CFAA following Van Buren and hiQ has made contract-based enforcement the primary legal tool for data owners." — [Ropes & Gray, May 2026](https://www.ropesgray.com/en/insights/alerts/2026/05/web-scraping-in-the-age-of-ai-guidance-for-data-owners-and-scrapers)
- *Meta Platforms v. Bright Data* (N.D. Cal., Jan. 23, 2024, Judge Chen): summary judgment for Bright Data on Meta's breach-of-contract claim; Meta's terms (barring collecting data "using automated means") govern only logged-in use — "Bright Data did not 'use' Facebook and Instagram when it engaged in public logged-off scraping"; the provisions exist "to prevent account holders who have privileges and access to Meta services from abusing their access", so a logged-out scraper stands "in the same shoes as a visitor". — [Farella Braun + Martel: Major Decision Affects Law of Scraping — Meta v. Bright Data](https://www.fbm.com/publications/major-decision-affects-law-of-scraping-and-online-data-collection-meta-platforms-v-bright-data/); Meta later filed to drop the case — [PR Newswire, Feb 2024](https://www.prnewswire.com/news-releases/meta-files-notice-to-drop-web-scraping-case-against-bright-data-302071400.html)
- *Ryanair DAC v. Booking Holdings* (D. Del.): July 2024 jury found Booking.com liable under the CFAA for exactly $5,000 of "loss" (the statutory minimum); on **Jan. 22, 2025** Judge Williams granted judgment as a matter of law for Booking.com, finding only $2,457.72 of cognizable loss (customer-service costs did not qualify) and criticizing a jury instruction that allowed harm "even if no actual technological harm has occurred", contrary to *Van Buren*'s focus on "the corruption of files". — [Eric Goldman blog (guest post), Mar 2025: Court Overturns a Bad Jury Verdict Against Scraping](https://blog.ericgoldman.org/archives/2025/03/court-overturns-a-bad-jury-verdict-against-scraping-ryanair-v-booking-guest-blog-post.htm); [Cooley press coverage, Jan 22, 2025](https://www.cooley.com/news/coverage/2025/2025-01-22-cooley-secures-decisive-win-for-bookingcom-in-computer-fraud-and-abuse-act-case)
- Clickwrap vs browsewrap: clickwrap agreements (button/checkbox) are "generally upheld as enforceable"; browsewrap enforceability turns on "whether there was actual or constructive notice, whether notice was conspicuous". Other cited contract wins for site owners: *Meta v. BrandTotal* (N.D. Cal. 2022); *Reddit v. Anthropic* (filed June 2025, breach of User Agreement alleged). Trespass to chattels requires damage/impairment (*eBay v. Bidder's Edge*, N.D. Cal. 2000). Practical guidance quoted: comply with terms, robots.txt and technical protections; "scraping purely factual information is less likely to create legal exposure"; although "robots.txt cannot enforce the instructions it provides to bots", recent scholarship argues contract/tort doctrines may reach violators. — [Ropes & Gray, May 2026](https://www.ropesgray.com/en/insights/alerts/2026/05/web-scraping-in-the-age-of-ai-guidance-for-data-owners-and-scrapers)
- **Amazon.com Services v. Perplexity AI**, No. 26-1444 (9th Cir. **Aug. 4, 2026**): vacated a March 9, 2026 preliminary injunction against Perplexity's Comet agentic browser; Amazon unlikely to succeed on CFAA/CDAFA because "It is the user who 'accesses' Amazon's computers, with the help of the Assistant to carry out specific acts on Amazon.com" — the agent is a tool under user direction. Critical fact: "Perplexity itself does not directly communicate with Amazon's servers"; communications route through the user's computer, distinguishing *Facebook v. Power Ventures* where the defendant's own systems transmitted. Perplexity's refusal to send an identifying user-agent string did not change the CFAA analysis. The court "expressly left open" terms-of-service/contract theories, and noted the outcome could differ if "the company's servers communicated directly with the defendant's servers." — [Cooley, Aug 6, 2026](https://www.cooley.com/news/insight/2026/2026-08-06-ninth-circuit-rules-on-ai-agent-access-to-third-party-websites-under-cfaa); [Justia opinion](https://law.justia.com/cases/federal/appellate-courts/ca9/26-1444/26-1444-2026-08-04.html); [Ninth Circuit PDF](https://cdn.ca9.uscourts.gov/datastore/opinions/2026/08/04/26-1444.pdf)

**C4. Etiquette norms: robots.txt, identification, AI-preference signals, Cloudflare defaults**

- RFC 9309 (Robots Exclusion Protocol): "Crawlers are automated clients"; "These rules are not a form of access authorization." (§1/§1.3). Product-token matching is case-insensitive and tokens contain only `a-z`, `A-Z`, `_`, `-` (§2.2.1). Parsers "MUST" handle at least 500 KiB (§2.5). Caching: "Crawlers SHOULD NOT use the cached version for more than 24 hours, unless the robots.txt file is unreachable" (§2.4). If robots.txt is *unavailable* (4xx) "the crawler MAY access any resources on the server" (§2.3.1.3); if *unreachable* (5xx/network) the crawler "MUST assume complete disallow" (§2.3.1.4). — [RFC 9309](https://www.rfc-editor.org/rfc/rfc9309.html)
- IETF AI Preferences WG: `draft-ietf-aipref-vocab-08` (Sept 14, 2026; intended Proposed Standard) defines **`train-ai`** ("Using an asset to modify the learned parameters of a generative AI model"), **`ai-use`** ("Using an asset as input to a generative AI model, where the asset is not directly provided by the user"), and **`search`**, each `allowed`/`disallowed`/`unknown`; attachment (HTTP header / robots.txt line) is in companion `draft-ietf-aipref-attach`. — [IETF datatracker: draft-ietf-aipref-vocab](https://datatracker.ietf.org/doc/draft-ietf-aipref-vocab/); [draft-ietf-aipref-attach](https://datatracker.ietf.org/doc/draft-ietf-aipref-attach/); [IETF blog on the WG](https://www.ietf.org/blog/aipref-wg/)

- Cloudflare **pay per crawl** (announced July 1, 2025, private beta): site returns `HTTP 402 Payment Required` with `crawler-price: USD XX.XX`; the crawler retries with `crawler-exact-price` (or pre-commits with `crawler-max-price`), and a charged 200 carries `crawler-charged: USD XX.XX`; crawlers must be registered via Web Bot Auth (Ed25519 key, JWK directory, HTTP Message Signatures: `signature-agent`, `signature-input`, `signature`); publishers set "a flat, per-request price across their entire site" and choose Allow/Charge/Block per crawler; "Cloudflare acts as the Merchant of Record". — [Cloudflare blog: Introducing pay per crawl](https://blog.cloudflare.com/introducing-pay-per-crawl/)

"Agent" is defined as "automated behavior that is acting, usually in real time, on a person's behalf, to get something done right now… This includes chat fetch bots (e.g., ChatGPT-User) and browser-use agents (e.g., Gemini or Claude driving Chrome)." Cloudflare proposes transitive trust via RFC 7239 `Forwarded: for='openai';use='reference'`. Existing zones keep prior settings (third-party summary). — [Cloudflare blog: Your site, your rules](https://blog.cloudflare.com/content-independence-day-ai-options/); [shattered.io summary of the Sept 15, 2026 defaults](https://shattered.io/cloudflare-ai-crawler-default-20-bots-2026/)

**C5. Privacy basics (users' URLs, stored content, EU/CA users)**

- CCPA applies to for-profit businesses that "Have a gross annual revenue of over $25 million" (inflation-adjusted in practice), or "Buy, sell, or share the personal information of 100,000 or more California residents or households", or "Derive 50% or more of their annual revenue from selling California residents' personal information"; "Personal information does not include publicly available information". — [California AG: CCPA](https://oag.ca.gov/privacy/ccpa)
- GDPR/CCPA can be implicated by scraping that collects personal data ("both of which impose obligations regarding the collection, processing, and use of personal data"). — [Ropes & Gray, May 2026](https://www.ropesgray.com/en/insights/alerts/2026/05/web-scraping-in-the-age-of-ai-guidance-for-data-owners-and-scrapers)

### Inferences (labelled; not legal advice)

- **What the copyright cases mean for this importer.** Storing the ingredient list and a normalized, de-prosed set of directions for a user's private use is the lowest-exposure configuration: ingredients are facts (Tomaydo-Tomahhdo; USCO FAQ) and functional directions are process (Lambing; PIL v. Meredith), while *Barbour* shows that chatty commentary can be protectable — so an LLM normalization step that discards headnotes/anecdotes and rewrites steps tersely reduces (not eliminates) copied expression. Photographs are protected regardless; **re-hosting a photo makes a copy**, so for a private per-user archive the analogy is a user saving a photo (fair-use-like personal use, untested for apps), whereas any *public* display of re-hosted text + photos (shared recipe pages, discovery feeds, SEO pages) is the Recipeasly configuration and should be avoided or done only with embedding/linking rather than copies. The server test protects *embedding* only in the Ninth Circuit; Atlanta is in the Eleventh Circuit, which — as far as I found — has no controlling decision, and S.D.N.Y. courts reject the test, so do not treat hotlinking as a legal safe harbor either.
- **Access law for user-initiated single-page import.** After Van Buren/hiQ, fetching a publicly reachable recipe page is very unlikely to be CFAA "unauthorized access"; the remaining hooks are (a) breach of terms — which, per Meta v. Bright Data, tends to bind *logged-in* users, so never import via a user's authenticated session cookies for paywalled sites like NYT Cooking; (b) a cease-and-desist naming your service (Power Ventures line) — honor it and add the host to a denylist; (c) trespass to chattels — needs measurable impairment, which one page per user click cannot cause. Note the Amazon v. Perplexity distinction: a fetch performed by *your Worker* is your servers communicating directly with the publisher (the Power Ventures-like posture), unlike a browser extension/share-sheet import that runs on the user's device; the Ninth Circuit flagged exactly this as the fact that could change the analysis. This is an argument for offering a client-side import path (share sheet / bookmarklet / extension) for hosts that block the Worker, and for keeping server-side fetches strictly single-page, user-triggered, and low-volume.
- **Does robots.txt bind user-triggered fetches?** RFC 9309 addresses "automated clients… crawlers" that "recursively traverse links"; a single fetch on explicit user request is closer to a browser than a crawler, and the RFC itself says it is not access authorization. Reasonable etiquette: read robots.txt (cache 24 h per §2.4), and *respect `Disallow` for any crawling/prefetching/link-following you do*, but treat the user's one-page import like a user agent action; if you nonetheless want to be conservative, honor a host's `User-agent: *` `Disallow: /` and any rule naming your product token, and surface to the user why an import was refused. Bulk crawling (seeding a catalog, prefetching every link on a blog) is a different activity — there the RFC, Cloudflare's Training/Agent defaults, `noai`/aipref signals, and ToS anti-scraping clauses all apply squarely.
- **Identification and rate:** send `User-Agent: <AppName>/<version> (+https://yourapp.example/bot; contact@yourapp.example)` (product token limited to `[A-Za-z_-]` so it can be matched in robots.txt), never spoof a browser UA (Amazon's complaint against Perplexity was precisely UA non-identification; it did not decide the case but it is the norm), keep per-host concurrency at 1 and interval at seconds (the DO limiter in B), cache HTML so re-imports of the same URL don't refetch, and back off on 429 using `Retry-After`. Cloudflare's Sept 2026 defaults mean an *identified* agent bot will be blocked on ad-monetized pages of new zones unless the publisher allows it or (in future) a pay-per-crawl arrangement exists; an *unidentified* fetch may pass but is the etiquette-losing option — this tension is unresolved and is exactly why a user-device fallback path matters.
- **`noai`/`noimageai`/aipref:** these signal preferences about AI *training* and AI *use* of content; a per-user importer that feeds one page through Gemini for extraction is "ai-use"-adjacent. Cheap compliance: if the page carries `noai`/`noimageai` or an aipref `ai-use=disallowed` signal, skip the LLM step (fall back to JSON-LD-only parsing) and skip re-hosting images, and tell the user. The IETF vocabulary is still a draft (v08, Sept 2026), so treat detection as best-effort.
- **Attribution/linking:** store and display source URL, site name, and author (from JSON-LD `author`/`publisher`, OG `og:site_name`), link back prominently, never strip the source, and don't build public SEO pages from imported content. This is both the etiquette bloggers ask for (Recipeasly backlash) and helpful under any fair-use analysis (commercial substitution is the factor that hurts).
- **Privacy:** a user-entered URL can be a private/authenticated link (Google Docs, a paywalled page with a session token, a Dropbox share); the Worker will fetch it without the user's cookies, so it will usually fail rather than leak — but log URLs with query strings redacted, don't retain HTML longer than needed (KV TTL), and let users delete imports (which should cascade to R2 objects). GDPR applies if you offer the service to EU users (Art. 3 territorial scope — not fetched this session); CCPA thresholds above are unlikely to be met by a small app but California's "publicly available information" exclusion helps for recipe-page content, not for your own users' data. Provide a privacy policy, data-deletion path, and a DMCA agent designation (17 U.S.C. § 512 — not fetched) if users can share imported content with others.
